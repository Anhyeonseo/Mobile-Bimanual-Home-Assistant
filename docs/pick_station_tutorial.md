# SO-ARM101 자연어 물체 집기 튜토리얼

### 소파 옆 수납장으로 주행해서 집기

로봇을 최하단에 두고 빈 팔을 차체 안쪽에 접는다. 웹에서 **소파 옆 수납장 · 지도 주행 후 집기**를 선택하고 지도에 현재 로봇 위치와 바라보는 방향을 차례로 누른다. 물체 이름을 입력하고 준비 상태를 확인한 뒤 시작한다.

11월 실험의 LDS-01 지도와 Nav2로 수납장을 봤던 위치(관측 28)까지 이동한다. 기존 현장 주행 범위는 출발점에서 1.2 m 이내다. 도착과 바퀴 주차가 확인되면 같은 제어기 세션에서 하단 RGB-D로 물체와 상승 공간을 확인한다. 상단에서 새로 촬영한 좌표로 기존 통합 파지를 실행하고 필요한 경우 좌우 정렬 후 다시 촬영한다. 실행이 끝나면 지우개가 실제로 들려 유지됐는지 확인한다.

## 2026-11-23 웹 실행 기준

현재 웹의 기본 리프트 높이 모델은 `encoder_no_sag`다. 과거 최상단 높이를 일괄 630 mm로 두던 `field_effective`는 명시적으로 선택할 때만 사용한다. 이번 저장 실행(`rgbd-13476`)은 엔코더 환산 654.589 mm인데 630 mm로 팔을 계획했고, 현장에서는 물체 위 1–3 cm에서 닫혔다. 높이 차이는 의심 원인이며 실제 손가락 절대 위치를 측정해 확정한 결과는 아니다. 물체·상판 좌표나 카메라 외부 보정 파일에 임의 오프셋을 적용하지 않는다. 준비·계획·실행 검증에는 같은 선택 모델을 전달한다. 새 웹의 시작 로그에서 `리프트 높이: 엔코더 환산 · 630mm 처짐 보상 없음`을 확인한다. 진행 중인 요청에 변경된 높이를 끼워 넣지 않으며, 새 서버에서 새 촬영으로 요청한다.

GraspNet 후보는 물체 이름별 규칙 없이 관측 점군으로 검사한다. 관측 폭이 집게 범위 안인데 접촉 중심이 치우쳐 대칭 개방 폭만 초과한 경우, 같은 관측 파지선에서 중심을 맞추고 단면을 다시 검사한다. 후보 32개 중 기본 16개는 균형 점수, 8개는 모델 점수, 나머지 8개는 다른 접촉 위치를 남기는 데 사용한다(중복 후보가 부족하면 실제 수는 더 적다). 관절 한계·IK 잔차·집게 실측 범위·상판 및 전체 경로 충돌 검사는 유지한다. `proposal_selection`에는 거절 원인, 중심 보정 수, 예산을 초과한 서로 다른 후보 수를 기록한다. 지우개 외 물체의 실물 성공률은 아직 검증되지 않았다.

웹 실행과 저장 촬영 검사는 같은 실행 전 검증 함수(`pick_plan_validation.validate_pick_plan`)를 사용한다. 기존 파지 실행기(`build_carry_session`, `UnifiedArmAdapter`)는 그대로 재사용한다. 경로 실패가 알려진 IK/접근 조건 때문이면 **현재 위치 경로 없음 · 재배치 검토**를 표시한다. 미검사 후보·보정·좌표계·계획기 오류는 별도로 분류한다. 현재 버전은 베이스 좌우 자동 이동을 실행하지 않는다. 이동 후에는 새 촬영부터 다시 계획해야 한다.

물체보다 위에서 집는 증상을 구분하기 위해 경로 보고서에 `contact_height_review`를 남긴다. 웹에는 관측 물체 높이와 계획 TCP 높이를 같은 관측 상판 기준으로 표시한다. 이는 실제 손가락 높이의 측정이 아니다. 보정 시험 범위 밖의 자세도 표시하며, 확인되지 않은 높이 오프셋을 자동으로 더하거나 빼지 않는다. 최근 완료 요청의 영상·계획·실행 기록은 `bash tools/run/collect_pick_request.sh`로 장치 제어 없이 복사할 수 있다. 실제 실행 단계에 진입한 기록을 고르려면 `--executed`를 붙인다.

21:43 정지 기록에서 리프트 상태 응답의 수신은 0.146 ms였지만 프레임 해석 구간이 wall 89.276 ms / 해당 스레드 CPU 2.062 ms로 늘어났다. 현재 웹은 RealSense SDK 촬영을 별도 프로세스에서 수행하여 제어 스레드와 Python GIL을 공유하지 않는다. 원본 노출 시각은 IPC로 그대로 전달하며 지연된 영상의 유효기간을 연장하지 않는다. 카메라/추론 자식 프로세스는 가능한 경우 허용 CPU 중 하나를 제외하고 nice 값을 5 낮은 우선순위로 조정한다. PyTorch 연산 스레드는 최대 2개다. 이는 OS 전체의 전용 코어 예약이나 실시간 보장이 아니며, 실물 STOP 재발 여부는 재검증해야 한다. 시작 로그의 `카메라 별도 프로세스 준비 완료` 및 `추론 CPU 사용 제한 적용`에서 실제 적용 정보를 확인한다.

일반 실행은 아래 한 명령으로 시작한다. 배포와 사전점검 후 출력된 웹 주소를 열고 터미널은 유지한다.

```bash
bash ~/Mobile-Bimanual-Home-Assistant-edit/tools/run/open_pick_station.sh
```

현재 리프트가 **최하단**이면 웹에서 **하단 관측 → 최상단 상승 → 집기**를 직접 선택한다. 기본 선택은 최상단 시험이며 브라우저가 이전 선택을 기억하므로, 시작 전에 반드시 실제 위치와 맞춘다. 빈 양팔·받침과 상승 통로를 현장에서 확인한 뒤 확인란을 체크하고 `리모컨을 집어줘` 같은 요청을 보낸다. 이 확인란과 집기 요청은 실제 장치 준비·상승·팔 실행으로 이어질 수 있다.

자동 상승은 설치된 펌웨어와 프로필 조합을 검사한다. 호스트가 지원하는 조합은 `pick_calibration.RISE_BOARDS`가 기준이다. `0x2492e / CRC 2696088964`는 이 상승 목표를 지원하지 않는다. 거절된다면 화면의 실제 펌웨어·CRC와 오류를 확인하며, 최상단이라고 허위 등록하거나 STOP 조건을 지우지 않는다. 이 문서의 과거 설치 기록으로 현재 STM32 버전을 단정하지 않는다.

**최상단 · 실물 파지**는 이미 최상단인 경우의 별도 팔 시험이다. 준비 후 근거리 RGB-D 한 장에서 탐지와 파지 후보를 계산한다. 물체 깊이 또는 주변과의 경계가 불분명할 때만 현재 자세에서 한 번 더 촬영한다. 그때는 새 사진으로 물체와 후보를 다시 구한다. 두 번째 관측도 불분명하면 화면에 이유를 표시하고 팔을 유지한다. 결과는 **동작 완료 · 사용자 확인 필요**이며 자동으로 물체 파지 성공을 증명하지 않는다. 다음 시험은 물체를 제거한 뒤 웹의 **다음 시험 준비**를 사용한다.

물체 윤곽 바깥의 깊이점은 바로 옆 세 픽셀이 모두 같은 물체로 관측되고 네 점의 깊이가 한 표면으로 이어질 때만 물체 쪽으로 연결한다. 이때 연결할 수 없는 외곽점은 장애물로 남겨 집게와 들어 올릴 물체의 경로를 검사한다. 다른 물체의 분할 영역이나 물체 안쪽의 빈틈과 겹쳐 장면을 구분할 수 없으면 재촬영한다.

웹과 `check_pick_regressions.py`는 이제 `tools/lib/pick_planning.py`의 동일한 계획 설정을 사용한다. 전체 진입 간격은 관측 물체 폭보다 10 mm 크고, 고정 손가락 쪽 여유 6 mm와 움직이는 쪽 4 mm를 계획한다. 닫힘 중 예상되는 물체 이동과 충돌 검사를 포함한다. 실제 접촉·마찰 오차가 검증됐다는 뜻은 아니다. 요청 폴더의 `checked/planning-options.json`에 사용 설정을 남긴다. 상단 도착 증거가 있으면 수직 접근, 그 외에는 도구 축 접근을 선택하며, 원본 촬영 정보는 바꾸지 않는다.

실행 직전 `heartbeat failed`와 STOP이 발생하면 요청의 **제어기 최초 정지 원인·통신 기록**을 연다. `mobile_board.source=1`은 호스트가 전달한 실제 관측 증거의 기한 만료다. 메시지만으로 heartbeat 패킷 자체가 끊겼다고 단정하지 않는다. 새 버전은 `execution_phase`와 최근 160회의 `service_trace`를 기록한다. `gap_ms`는 상태 갱신 호출 사이의 공백이고 `duration_ms`는 한 갱신 처리 시간이다. 번들 읽기, 실행 자료 준비, 실시간 관측 확인, 경로 전송 단계를 구분한다. 실행 자료 검사는 보조 작업에서 기다리며 기존 250 ms 기한과 관측 시각 검사를 유지한다. 이 변경만으로 실제 장치의 지연 원인이 해결됐다고 간주하지 않는다.

이하에는 초기 개발·배포·CLI 사용 기록도 포함한다. 현재 웹의 작업 선택과 최상단 시험 동작은 이 절을 우선한다.

### 비활성 상태에서 통신 지연만 확인

웹 서버를 종료한 뒤 노트북 터미널로 실행한다. STOP 잠금 상태 또는 작업 준비 전임을 조회로 확인한 상태만 허용한다. 이 검사를 위해 STOP을 새로 걸거나 해제하거나 STM32를 재시작하지 않는다.

```bash
bash ~/Mobile-Bimanual-Home-Assistant-edit/tools/run/check_pick_serial_timing.sh
```

현재 로컬 조회 프로그램을 Jetson 임시 파일로 전송하고 기본 5초씩 CPU 무부하/합성 부하를 비교한다. 마지막에 출력하는 `REPORT` JSON을 보관한다. 기존 제어 프로세스가 포트를 소유하면 거절하며, 그 프로세스를 종료시키거나 STOP 상태를 변경하지 않는다. heartbeat·증거 갱신·토크·이동 명령도 보내지 않는다. 먼저 기존 장치 점검과 동일한 `P → HELLO`로 binary-v2 통신 및 지원 펌웨어·12관절을 확인한다. 이 통신 모드 진입은 리셋이나 STOP 해제가 아니다. STOP이 없으면 매 반복에서 commissioning flags=0, boot_id=0, reason=0 및 executor_active=false, settling=false를 요구한다. 이 경로는 `MODE: unprepared_controller_query_only`로 표시하며 리프트 세션 생성 없이 상태·준비 상태·runtime 조회만 비교한다. 준비된 제어기나 활성 경로는 거절한다. 토크 OFF를 확인하는 검사가 아니다.

요청별 송신(`write`), 수신 처리(`read`), 프레임 해석(`decode`) 시간과 해당 스레드 CPU 시간을 기록한다. 실제 요청 헤더에서 `414d0105`는 AM 베이스 상태 조회, `414c0104`는 AL 리프트 상태 조회다. wall 시간만 크고 CPU 시간이 작으면 I/O 대기 또는 스케줄링/GIL 대기일 수 있으며 USB 고장으로 단정하지 않는다. 이 검사의 합성 CPU 부하는 GraspNet과 동일하지 않고, STOP 상태에서 정상이라고 실행 중 지연이 없다고 증명할 수는 없다. 다음 웹 요청의 정지 보고서도 `transport_before_stop`에 같은 계측을 보존한다.

목표는 탑뷰 D415로 사용자가 지정한 물체를 찾아 고정된 베이스에서 왼팔로 한 번 집고 결과를 확인하는 것이다. **1~3단계는 카메라와 컨트롤러를 뽑은 채로 할 수 있다.** 4단계부터 로봇을 연결한다. 명령 앞에 표시한 컴퓨터와 작업 폴더를 확인한다.

### 노트북 터미널에서 GraspNet 파지

현재 프로젝트 노트북에서는 아래 명령으로 이미 준비한 Jetson GraspNet 실행기를 연다. 첫 터미널은 유지한다. `start`만으로 모터를 켜거나 파지를 시작하지 않는다.

```bash
python3 ~/Mobile-Bimanual-Home-Assistant-edit/tools/run/graspnet_pick.py start
```

두 번째 터미널에서 상태와 카메라 후보를 먼저 확인한다. `status`의 `accepting`이 `true`, `candidate_source`가 `graspnet`이어야 한다. `inspect`는 최상단에서 카메라만 사용하며 실제 파지를 하지 않는다.

```bash
python3 ~/Mobile-Bimanual-Home-Assistant-edit/tools/run/graspnet_pick.py status
python3 ~/Mobile-Bimanual-Home-Assistant-edit/tools/run/graspnet_pick.py inspect "리모컨"
```

실물 상태가 맞고 제어기·보정 문제를 해결한 다음, 실제 최상단·양팔 받침·빈 집게를 현장에서 확인하고 파지를 요청한다. 아래 명령은 검사를 통과하면 실제 팔을 움직인다. 최하단에서 시작할 때는 확인 옵션을 `--supported-empty-bottom`으로 바꾼다. 옵션은 리프트를 해당 위치로 이동시키는 명령이 아니다.

```bash
python3 ~/Mobile-Bimanual-Home-Assistant-edit/tools/run/graspnet_pick.py pick "리모컨" --supported-empty-top
```

요청 ID, 단계와 최종 결과가 터미널에 표시된다. `SUCCEEDED`와 `physical_success: true`가 함께 있어야 실제 성공이다. `UNVERIFIED`나 `STOP_UNCONFIRMED`는 성공이 아니다. 결과가 나와도 첫 터미널을 유지한다. 물체를 잡고 있을 수 있으므로 자동 복귀·집게 열기·재시도를 하지 않는다.

```bash
python3 ~/Mobile-Bimanual-Home-Assistant-edit/tools/run/graspnet_pick.py cancel
```

`cancel`은 중단 요청이며 STOP 완료 보증이 아니다. 파지 명령에서 Ctrl+C를 누르거나 응답이 끊기면 중단을 요청하며 파지 요청을 재전송하지 않는다. 첫 터미널에서 Ctrl+C를 누르면 실행기가 정상 종료 절차로 STOP을 요청한다. 필요한 받침과 실물 정지 상태를 먼저 확인한다.

11월 18일 이번 실행은 리프트 엔코더 **2389**가 기존 최상단 실측 범위 **1727–1882**를 벗어나 파지 경로 실행 전에 중단됐다. STOP 잠금은 관측했지만 STOP 완료 검증은 남아 있다. 이 CLI는 두 조건을 우회하거나 보정값을 변경하지 않는다. `start`가 준비 완료여도 제어기 재시작 가능 상태와 실제 파지 준비 완료를 뜻하지 않는다.

기본 Jetson은 `hyper@192.168.35.2`, 준비한 배포 폴더는 `/home/hyper/robot/releases/pick-graspnet-cli-20261118`, 포트는 18769다. 포트 충돌 시 모든 명령에 `--port 18770`처럼 **하위 명령 앞에** 같은 포트를 지정한다. 다른 배포본은 `start --remote-root /절대경로`로 선택하되, GraspNet과 이 CLI의 모델 상태 표시를 지원해야 한다. 알려지지 않은 한국어 명칭의 번역기가 없으면 영어 물체명으로 입력한다.

### 노트북에서 웹으로 실물 파지

다음 명령이 배포본을 준비하고 Jetson 웹과 SSH 터널을 열어 브라우저를 시작한다. 같은 버전은 기존 릴리스를 재사용한다. 기본 18768 포트가 사용 중이면 18769–18788 중 노트북과 Jetson 양쪽에서 가능한 포트를 자동 선택한다. 화면에 출력된 주소를 사용하고 서버 터미널을 열어 둔다.

```bash
bash ~/Mobile-Bimanual-Home-Assistant-edit/tools/run/open_pick_station.sh
```

최하단 시작 작업은 **하단 관측 → 상승 → 집기**다. 과거 설치 보드 `0x2492e / CRC 2696088964`는 자동 이동 한계가 610 mm여서 이 작업을 장치 준비 전에 거절한다. 상단 등록 높이를 이동 목표로 쓰지 않는다. 사용자가 재확인한 기존 행정 30,717 카운트를 기준으로 확장된 프로필(CRC 3399362976)을 지원한다. 현재 설치 여부는 실제 보드 응답으로 확인한다. 리프트를 실제 최하단에 두고 빈 양팔·준비용 받침을 확인한다. 상승 통로에 손이나 받침이 걸리지 않도록 준비한다. 하단에서 촬영·GraspNet 후보를 확정하고, 관측 장면으로 상승 경로를 검사한 뒤 리프트를 올린다. 도착 후 영상은 물체가 그대로 있는지 확인하는 용도이며, 물체 좌표와 후보는 하단 관측을 유지한다. MoveIt 계획 시작점에는 상승 후 실측 관절·리프트 상태를 별도로 사용한다.

상승 목표는 하단 기준 30,717 엔코더 카운트다. 현 프로토콜의 거리 필드에는 이를 제어기 환산값 654588로 전송한다. 이 숫자는 실제 높이 측정값이 아니다. 기계적 끝에 부딪혀 원점을 찾는 동작은 아니다. 상단의 유효 계획 높이 630 mm는 기존 편 팔 현장 보정을 유지한다. 엔코더 이동 구간과 팔 계획용 높이를 서로 독립적으로 기록한다. 새 자동 상승 경로의 실기 확인은 남아 있다. 상승 후에는 자동 하강이나 재시도를 하지 않는다.

상승 후 계획에서만 실패한 시험은 `PICK_RESUME_FROM=<이전 요청 폴더> bash tools/run/pick_kit.sh web`으로 열고 **이전 하단 관측 → 현재 상단에서 이어 집기**를 선택할 수 있다. 베이스·물체·주변이 그대로이고 리프트가 실제 최상단인지 확인한다. 원본 사진·깊이·후보를 보존하고 현재 제어기 기준과 팔 자세만 다시 연결한다. 물체 재탐지와 상승은 반복하지 않으며, 이미 팔 실행을 시작한 요청은 이 기능의 대상이 아니다.

상판은 현재 촬영한 평면을 사용한다. 과거 수납장의 base Z 730.8–739.9 mm를 일치 조건으로 사용하지 않는다. 화면의 상판 높이는 보정 파일의 바닥 기준이며 새 바닥 관측값은 아니다. 높이가 달라도 팔의 도달성·실측 오차 여유·전체 경로 충돌 검사를 통과해야 실행한다. 과거 보정 시험의 관절 각도 범위는 도달 가능 범위가 아니다. 편 팔 자세를 우선 선택하고, 과거 범위 밖 여부는 보고서와 실행 로그에 남긴다.

집게 계산·접촉 검사·모터 명령은 `nominal_stock_tcp_section`으로 통일했다. 앞쪽 실측 간격을 안쪽 단면에 대입하지 않는다. 카메라·팔 관절 보정은 유지하지만 이 집게 곡선은 명목 CAD 모델이며 실측 보정을 대신했다고 해석하지 않는다. 기본 8개 후보가 모두 실패하면 남은 후보도 검사하며, 완성 경로를 찾으면 즉시 끝낸다. Cartesian 관절 분기가 급변하면 연속 5DOF IK와 같은 충돌 검사로 대안을 시도한다. 상판 충돌과 최상단 실측 여유 검사는 유지한다.

이미 해당 높이에 있는 경우에만 기존 **최상단 · 실물 파지** 또는 **최하단 · 실물 파지**를 선택한다. 받침과 빈 그리퍼를 현장에서 확인하고 물체 요청을 입력한 뒤 **집기 요청**을 누른다. 최상단 실물 파지는 팔 자세를 유지한 상태에서 근거리 촬영으로 시작하고, 그 시점의 관절과 리프트 관측을 경로에 연결한다. 중단·탐지 실패·경로 거절·파지 후 확인 결과는 같은 화면에 표시된다. **최상단 · 카메라 검사**를 선택하면 모터를 켜지 않고 탐지와 후보까지만 살펴볼 수 있다.

웹 요청마다 Grounding DINO와 SAM이 요청한 물체의 마스크를 만들고, GraspNet이 주변 점군에서 자세를 예측한다. 그중 마스크와 실측 깊이에 대응하는 후보를 SO-ARM101의 손가락 폭과 접촉 위치로 거른다. 촬영 모드에 맞는 카메라 외부 보정과 팔 관절 보정을 적용하고, 최상단은 실측 상판을 확인하고 편 팔 자세를 우선한다. MoveIt이 검사한 경로를 실행한 뒤 접촉 피드백과 새 영상으로 결과를 판정한다. 웹 상단의 모델 표시에서 **GraspNet**을 확인할 수 있다.

웹 모드는 단계 총 처리시간 제한을 0으로 설정해 완료까지 기다린다. 화면 상단에 광각·근거리 촬영, 탐지·분할, GraspNet 계산, 장치 준비의 현재 작업을 표시한다. 작업 중단 버튼과 제어기·센서 상태 검사는 대기 중에도 동작한다. 제어기 준비가 거절되면 실패한 조건과 측정값을 화면에 표시한다.

웹의 받침 확인에는 **준비 중 필요한 경우 모터 힘을 한 번 끄는 것**이 포함된다. 제어기는 초기 상태인데 모터 힘이 켜져 있으면, 받쳐 고정한 빈 양팔·리프트라는 이번 요청의 확인을 받고 한 번 해제한다. 실제 토크 OFF와 정지 상태를 읽은 뒤 기존 자세 유지 준비로 이어진다. 이미 OFF이면 해제를 보내지 않으며, 확인 실패 시 자동 재시도나 리셋은 하지 않는다. 전원 재시작만으로 토크 OFF를 가정하지 않는다.

감독하의 리프트 상승은 경과 시간만으로 중단하지 않는다. 엔코더 목표 도달까지 현재 진행률을 표시하며, 제어기 고장·관측 단절·사용자 중단은 그대로 처리한다. 상승 최초 오류와 정지 확인 실패는 별도로 기록한다.

### 물체를 지정하는 방법

웹 입력창에 물체 이름이나 한 물체를 집는 문장을 입력한다. 예를 들어 `테이프를 집어줘`, `지우개`, `pick up the silicone brush`를 입력할 수 있다. 화면에서 해석된 영어 탐지어를 확인한다. 같은 요청의 탐지·후보·실행 번들·파지 후 확인에 이 탐지어를 사용한다.

`AMBIGUOUS_TARGET`이면 검출 결과를 보고 **`오른쪽 지우개를 집어줘`**, **`화면 왼쪽 파란 컵을 집어줘`**, 또는 **`pick up the right eraser`**처럼 화면 위치를 지정할 수 있다. 왼쪽·오른쪽은 새로 촬영한 이미지의 좌우이며 로봇 팔 선택이 아니다. 영어 탐지어에는 위치를 섞지 않고, 같은 종류의 검출 상자 중 겹치지 않는 가장 왼쪽/오른쪽을 선택한다. 선택된 물체의 깊이가 부족하면 다른 물체로 바꾸지 않고 재관측을 요청한다. 검출 상자가 겹치면 계속 모호함으로 거절한다. 위치 지정은 새 촬영 작업에서 사용하며 이전 관측 이어가기는 대상 변경을 허용하지 않는다. 다른 물체와의 상대 위치(예: 컵 옆의 지우개)나 복수 작업은 현재 처리하지 않는다.

일상 사물과 색상은 내장 어휘로 해석한다. 새로운 한국어 명칭은 기존 로컬 Qwen을 통해 영어로 변환한다. 웹 시작 명령은 설치된 번역기를 자동으로 연결한다. 번역기만 별도로 시험할 때는 노트북에서 다음 명령을 실행한다. 영어 물체명은 모델 서버 없이 바로 입력할 수 있다.

```bash
cd ~/Mobile-Bimanual-Home-Assistant-edit/output/pick-kit/current
bash tools/run/pick_kit.sh language
```

다른 PC에서는 `PICK_LANGUAGE_DIR`에 기존 Qwen3-4B-Q4_K_M.gguf와 해당 PC용 `llama-build/bin/llama-server`가 있는 폴더를 지정한다. 이 두 파일은 인식 배포본과 별도다. 웹이 Jetson에서 실행되는 경우 노트북 번역기를 쓰려면 웹 터널을 열 때 SSH에 `-R 127.0.0.1:18767:127.0.0.1:18767`도 넣는다. Jetson에서 같은 포트로 모델 서버를 운영하는 경우에는 역방향 터널을 생략한다.

노트북의 기존 편집본에서 새 버전을 배포하고 장치 없이 사전점검만 하려면 다음 두 줄을 사용한다. 이 명령은 새 Jetson 폴더를 만들고 끝나면 노트북 셸로 돌아온다.

```bash
cd ~/Mobile-Bimanual-Home-Assistant-edit
bash tools/run/stage_pick_station.sh
```

장치가 연결된 날에는 위 명령에 `--check-hardware`를 붙이면 사전점검 통과 후 STM32 상태도 조회한다. 출력의 펌웨어와 프로필 CRC32를 함께 확인한다. 초기 부팅 상태에서 등록된 boot ID가 0이면 리프트·STOP 조회는 생략된다.

다음에 웹 데모를 열 때는 기존 웹 서버·터널을 종료한 후 노트북에서 다음을 실행한다. 복사된 버전에 기록된 경로를 사용한다.

```bash
cd ~/Mobile-Bimanual-Home-Assistant-edit/output/pick-kit/current
pick_dir=$(cat output/last-jetson-release) &&
  ssh -t -o ExitOnForwardFailure=yes -L 127.0.0.1:18768:127.0.0.1:18768 -R 127.0.0.1:18767:127.0.0.1:18767 hyper@192.168.35.2 "cd '$pick_dir' && bash tools/run/pick_kit.sh demo"
```

## 1. 노트북에서 배포본과 웹 확인

현재 노트북의 편집본은 `~/Mobile-Bimanual-Home-Assistant-edit`에 있다. 팀원에게는 `output/pick-kit/`의 **pick-station.tar.gz와 pick-station.tar.gz.sha256**을 함께 전달한다. 압축본 하나에 상주 집기 코드, 보정, 가중치, 메시, 저장 영상과 이 튜토리얼이 들어 있다.

**프로젝트 노트북**에서는 아래 폴더를 연다.

```bash
cd ~/Mobile-Bimanual-Home-Assistant-edit/output/pick-kit/current
```

**압축본을 받은 팀원**은 Ubuntu 24.04 노트북에서 두 파일을 `~/Downloads`에 저장한 뒤 아래 명령으로 새 작업 폴더에 푼다. 새 버전을 받을 때도 매번 새 폴더를 사용한다.

```bash
cd ~/Downloads
pick_extract=$(mktemp -d "$HOME/pick-team-XXXXXXXX") &&
  sha256sum -c pick-station.tar.gz.sha256 &&
  tar -xzf pick-station.tar.gz -C "$pick_extract" &&
  cd "$pick_extract/pick-station"
pwd -P
```

**이후 두 경우 모두** 배포 폴더에서 기존 환경으로 아래 명령을 실행한다. 현재 프로젝트 노트북은 사용하던 추론 Python과 ROS Jazzy를 자동으로 선택한다. 데모 웹만 열 때는 Python 3로 충분하다.

```bash
bash tools/run/pick_kit.sh preflight
```

마지막 줄이 `OFFLINE_PREFLIGHT_PASSED`이면 이 컴퓨터의 소프트웨어 점검을 통과했다. 매번 새 `output/preflight/<실행>/report.json`을 만든다. 각 검사 옆에 찍힌 로그가 실패 원인을 담고 있다. 모델 준비에는 시간이 걸릴 수 있다.

수동으로 웹도 확인한다.

```bash
bash tools/run/pick_kit.sh demo
```

[노트북 데모 웹 열기](http://127.0.0.1:18768) → 모드가 **demo**인지 확인 → `지우개를 집어줘` 입력 → **집기 요청** → 촬영, 탐지, 후보, 계획, 실행, 확인 순서와 최근 요청을 본다. 두 번째 요청도 받으면 정상이다. 종료는 서버 터미널에서 `Ctrl+C`. 샘플 영상에 찍힌 리모컨과 동기화된 관절 기록은 이 배포본에 없어서 이 사진만으로 실기 실행 번들을 만들 수 없다.

**코드를 수정했거나 폴더가 없을 때만** 노트북 원본에서 다시 패키징한다.

```bash
cd ~/Mobile-Bimanual-Home-Assistant-edit
python3 tools/setup/package_pick_station.py --archive
```

`KIT_READY` 뒤에 나온 폴더가 새 버전이다. `output/pick-kit/current`가 이 버전을 가리킨다. 다른 노트북에서 재생성할 때는 `--artifacts`에 `graspnet-baseline`, `models/checkpoint-rs.tar`, `models/huggingface`를 담은 디렉터리, `--meshes`에 원본 `base_link.STL`, `vertical_link.STL`, `wheel1.STL` 폴더, `--snapshot`에 동일한 **near 프로필**의 리모컨 RGB-D 폴더를 지정한다. 이미 만든 배포본을 받았다면 재생성할 필요가 없다.

## 2. Jetson에 소프트웨어만 복사

Jetson만 켜고 노트북과 네트워크로 연결한다. 노트북 데모를 종료한 후 **같은 노트북 터미널, 1단계의 배포 폴더**에서 실행한다. 양쪽 컴퓨터에 rsync가 필요하다. 없다면 해당 Ubuntu에서 `sudo apt install rsync`로 설치한다. 전송이 끝나면 Jetson의 새 배포 폴더에 셸이 열린다.

```bash
pick_kit=$(pwd -P)
pick_host=hyper@192.168.35.2
test -f "$pick_kit/SHA256SUMS" &&
  pick_dir=$(ssh "$pick_host" 'mkdir -p "$HOME/robot/releases" && mktemp -d "$HOME/robot/releases/pick-station-XXXXXXXX"') &&
  rsync -a --partial --exclude=/output/ --exclude=/.venv/ --exclude=__pycache__/ "$pick_kit/" "$pick_host:$pick_dir/" &&
  mkdir -p "$pick_kit/output" &&
  printf '%s\n' "$pick_dir" > "$pick_kit/output/last-jetson-release" &&
  printf 'Jetson 설치 경로 %s\n' "$pick_dir" &&
  ssh -t -o ExitOnForwardFailure=yes -L 127.0.0.1:18768:127.0.0.1:18768 "$pick_host" "cd '$pick_dir' && exec bash -i"
```

재접속 시 같은 노트북 셸에서 마지막 `ssh` 줄만 실행한다. 새 셸을 열었다면 `pick_host`와 `pick_dir`에 위에서 사용한 주소와 **출력된 경로**를 지정한다. Jetson 데모와 실기 웹은 같은 SSH 터널을 사용한다. 노트북에서 보는 Jetson 주소는 [127.0.0.1:18768](http://127.0.0.1:18768)다. 터널 양쪽과 브라우저 포트를 동일하게 유지한다. 포트가 이미 사용 중이면 노트북 데모나 이전 터널을 해당 터미널에서 정상 종료한 뒤 재접속한다.

## 3. Jetson에서 장치 없이 예행연습

**Jetson 셸, 방금 복사한 폴더.** 이 로봇에는 ROS Jazzy, MoveIt, 인식·제어용 Python이 준비돼 있다. 새 가상환경을 만들거나 apt·pip를 실행할 필요 없이 다음 명령으로 시작한다.

```bash
bash tools/run/pick_kit.sh preflight
```

실행기는 Jetson에 기록된 `~/robot/shared/runtime/s4-jazzy/env.sh`와 `install/setup.bash`를 읽고, 기존 `~/realsense-grounding/.venv/bin/python`에서 추론한다. 같은 Python 버전의 `~/robot/shared/venvs/s4-jazzy` 제어 모듈도 참조한다. 검사 첫 줄에서 선택된 경로를 볼 수 있다. 별도로 활성화한 가상환경이나 배포본의 기존 `.venv`가 선택되면 출력된 Python을 확인한다.

다른 계정에 같은 구조로 설치했다면 `PICK_JETSON_HOME`에 그 홈 디렉터리를, 다른 Python을 사용한다면 `PICK_PYTHON`에 해당 실행 파일의 절대경로를 지정한다. `bash tools/run/pick_kit.sh env`는 장치를 열거나 모델을 로드하지 않고 현재 Python에서 찾지 못한 모듈과 파일을 출력한다. `DEPENDENCIES_PRESENT`는 경로 확인 결과이고, 실제 추론과 MoveIt 동작까지는 `preflight`에서 확인한다.

Jetson에서도 `OFFLINE_PREFLIGHT_PASSED`를 확인한 뒤 `bash tools/run/pick_kit.sh demo`를 실행한다. 노트북에서 [Jetson 데모 열기](http://127.0.0.1:18768) → 집기 요청 → 다음 요청 대기까지 확인한다. **여기까지가 실물 연결 전 완료 지점이다.** 데모는 `Ctrl+C`로 종료한다.

## 4. 처음 연결하는 날

1. **장치 통신과 새 사진.** D415·STM32를 Jetson에 연결하고, 리모컨을 카메라 시야에 놓는다. SSH 터널은 열어 두고 **노트북의 두 번째 터미널**에서 1단계와 같은 배포 폴더로 이동한다. 아래 명령은 2단계에서 저장한 Jetson 경로와 기존 S4 제어 Python을 사용한다. 제어 Python의 경로가 바뀌었으면 `JETSON_PICK_PYTHON`에 실제 절대경로를 지정한다. 결과에 `CACHED_STATUS_READ`와 `RGBD_CAPTURED`가 함께 표시되면 노트북에 출력된 `SNAPSHOT` 폴더의 `color.png`를 열어 리모컨이 보이는지 확인한다. 진단 사진은 근거리 프로필, 아래 실기 경로 계획은 보정된 광각 프로필을 사용한다.

   ```bash
   pick_dir=$(cat output/last-jetson-release) &&
     bash tools/run/check_pick_hardware.sh --root "$pick_dir" --capture
   ```

2. **새 촬영으로 계획만 확인.** 기존 팔·리프트 제어 프로그램을 정상 종료한다. 양팔을 지지하고 그리퍼가 비어 있으며 **리프트가 실제 최하단**인지 현장에서 확인한다. 리프트가 올라가 있거나 이전 STOP에서 토크를 유지 중이면 이 명령의 시작 조건이 성립하지 않는다. 준비 명령은 실제로 토크를 걸어 자세를 유지하고 최하단 원점을 등록한다. 이 튜토리얼의 리프트 상승 명령값은 0이다.

   ```bash
   # Jetson 배포 폴더에서
   bash tools/run/pick_kit.sh plan-only --supported-empty-bottom
   ```

   [Jetson 웹](http://127.0.0.1:18768)에서 `live`와 계획 전용 안내를 확인한다. 준비 완료 후 **집기 요청**을 누른다. 이번 촬영의 탐지 이미지, 후보, 경로 검사와 최종 `PLANNED_ONLY`가 확인되면 성공이다. 대상이 보이더라도 팔이 닿지 않으면 경로가 거절될 수 있다. `output/pick-station/<실행>/<요청 ID>/`에서 해당 요청의 원본과 거절 이유를 확인한다.

3. **첫 실제 파지.** 계획 전용 서버를 종료하면 통합 STOP 절차가 실행된다. 정지 상태에서 토크가 유지될 수 있으므로 기존 장비의 감독된 복구 절차에 따라 다시 시작 조건을 확보한다. 제어기가 새 무전원 또는 준비 상태이고 기구가 지지된 빈손·최하단임을 확인한 **다음 세션**에서 아래 명령을 쓴다. 사람이 비상정지를 조작할 수 있는 위치에서 작업 공간과 경로를 확인한다.

   ```bash
   # Jetson 배포 폴더에서
   bash tools/run/pick_kit.sh pick --supported-empty-bottom
   ```

   웹에서 한 번 요청하면 새 촬영·계획·검증 뒤 팔이 움직인다. `SUCCEEDED`는 새 RGB-D와 그리퍼 관측으로 파지를 확인한 경우다. `UNVERIFIED`는 영상이나 그리퍼 증거가 부족한 경우다. 실물 실행 후 물체를 들고 있거나 상태가 불명확하면 다음 집기가 차단된다. 놓기·빈손 복귀, 550 mm 리프트 이동, 오른팔 또는 베이스 이동은 이 실행기의 범위 밖이다.

### 적용한 보정과 실기 범위

`yeoeun/extrinsic-calibration`의 `05b1ae6` 기준으로 카메라 변환, 양팔 관절 영점·장착 위치, 리프트 영점과 배율, 광각 프로필, 높이 모델, 왼쪽 그리퍼 보정 연결을 사용한다. 새 촬영과 계획에 같은 보정 ID를 기록한다. 0x2492D 보드(프로필 CRC32 2430209922)는 84.000 mm/회전을, 0x2492E(2696088964)는 87.287 mm/회전을 사용해 LS 높이를 보고한다. 실기 집기 실행기는 초기 조회에서 이 조합을 확인하고 관측 높이 환산 시 모델 배율을 한 번만 적용한다. [보정 브랜치 현장 기록](https://github.com/Anhyeonseo/Mobile-Bimanual-Home-Assistant/blob/05b1ae603e6b1fbe57a99992db17ba85ac86e7fb/docs/EXTRINSIC_CALIBRATION_HANDOFF_20261118.md)

11월 18일 현장 기록의 630 mm는 최상단·왼팔을 편 자세·약 735 mm 상판에서의 계획 높이다. 실물 최상단 요청은 펌웨어 0x2492E, 해당 CRC, 사용자의 기계적 최상단 확인, 신선한 정지 관측과 실제 상단 등록을 확인한다. 1727–1882는 당시 엔코더 관측값이며 허용 오차로 측정된 범위가 아니다. 한 바퀴 안의 raw 값만으로 물리 높이를 판정하지 않는다. 실제 최상단을 확인한 요청에서 이번 등록의 raw·부트 ID·리프트 세션·보정 ID를 함께 기록하고, 이후 raw 기준 2 mm 초과 변화나 재시작·세션 변경을 거절한다. 범위 밖이라는 이유로 숫자에 맞춰 리프트를 움직이거나 현재 위치를 확인 없이 최상단으로 간주하면 안 된다.

보고서에 제어기의 상단 등록 높이와 보정된 모델 높이를 함께 보존한다. 관측 상판과 충돌하는 경로는 거절한다. 예전에 시험한 자세 범위 밖이라는 이유만으로 경로를 거절하지 않는다. 자세 범위 기록이 실제 정확도를 보증하지는 않는다. 팔꿈치를 접은 자세의 15–20 mm 오차, 줄자 행정 635/639 mm를 전역 오프셋으로 쓰지 않는다. 현장 성공 예시는 세운 지우개 1회이며 일반 파지에서는 관측된 물체의 폭과 표면으로 접촉 위치를 계산한다.

최근 진단으로 찍은 근거리 RGB-D에 다른 물체 요청을 검사하려면 노트북의 배포 폴더에서 `bash tools/run/pick_kit.sh inspect-target /절대경로/cam '테이프를 집어줘'`를 실행한다. 출력 폴더에 검출 사진과 후보 JSON이 남는다. 카메라와 모터 접근은 없다.

## 막힌 단계에서 확인할 것

| 결과 | 다음 조치 |
| --- | --- |
| `files` 실패 | 같은 버전을 다시 복사하고 `sha256sum --quiet -c SHA256SUMS`로 확인한다. 배포 폴더 안에서 파일을 편집했다면 노트북 원본에서 수정·재패키징한다. |
| `dependencies` 또는 `geometry` 실패 | `bash tools/run/pick_kit.sh env`와 해당 로그에서 선택된 Python, 누락 모듈·MoveIt 패키지·STL 경로를 확인한다. Jetson의 사용자 경로가 바뀌었다면 기존 ROS 설정을 불러오고 기존 추론 Python을 지정한 후 재점검한다. |
| `perception` 실패 | `perception.log`에서 누락된 모델 파일, 라이브러리 import 오류, 후보 거절 중 무엇인지 확인한다. 예제에는 고정한 두 모델과 near 촬영본이 함께 있어야 한다. |
| `web`·MoveIt 항목의 `Operation not permitted` | TCP 소켓이 허용되는 노트북 일반 터미널이나 Jetson 셸에서 동일한 `preflight`를 실행한다. MoveIt 서비스 시간 초과면 `resident/move_group.log` 또는 `planning/move_group.log`를 확인한다. |
| SSH 연결 실패 또는 장치 점유 | Jetson 전원·주소·사용자와 USB 연결을 확인한다. 기존 제어기나 뷰어를 쓰고 있다면 해당 세션에서 정상 종료한 후 재시도한다. |
| `PARTIAL_STATUS`, 리프트 fault, STOP 미확인 | `comparison.json`의 `controller.errors`, `lift`, `stop_proof`를 확인한다. 장비 담당자와 현 상태를 확인한 뒤 다음 세션을 준비한다. |
| `baseline` 또는 포트 오류 | 기본 baseline은 `/home/hyper/robot/shared/diagnostics/s4-trial-20261114/baseline.json`이다. 이 로봇의 승인된 파일이나 시리얼 경로가 다르면 `PICK_BASELINE`, `PICK_SERIAL`에 실제 값을 지정한다. |

ROS와 추론 환경이 없는 새 Ubuntu 24.04 장비를 처음 준비할 때만 배포 폴더에서 `bash tools/run/install_pick_environment.sh`를 실행할 수 있다. 이 선택 설치는 sudo와 인터넷 연결을 사용한다. 프로젝트 Jetson과 노트북의 일반 실행 절차는 1~3단계다.

**최상단 고정 · 수납장 주행 후 집기**는 양팔을 접고 리프트를 실제 최상단에 둔 상태에서 시작한다. 지도에서 현재 차체 위치와 방향을 지정한다. 현재 팔 엔코더와 상단 보정으로 주행 공간을 검사하고, 수납장 앞에서 바퀴 정지·주차가 확인되면 근거리 촬영과 파지를 시작한다.
