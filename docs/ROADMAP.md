# 개발 로드맵

기준일: 2026-09-15. 목표는 ALOHA Mini 1으로 **거실 소파의 리모컨을 찾아 침대의 지정 영역에 배달**하는 Classical 시스템이다. 기존 [Bimanual-Pick-And-Place](https://github.com/Anhyeonseo/Bimanual-Pick-And-Place)를 이식하고, 완료 후 리더암 시연 기반 VLA와 비교한다.

## 문서 운영과 완료의 의미

- 이 문서: 우선순위·의존성·통과 기준·다음 작업의 단일 목록. 일정 변경도 여기에서 수정한다.
- [CURRENT_STATUS](CURRENT_STATUS.md): 실제 구현·시험 결과와 남은 연결. 계획을 완료 상태로 적지 않는다.
- [ARCHITECTURE](ARCHITECTURE.md): 통신·모듈·상태·단위·관절 제한 계약. 하드웨어 실측과 출처는 [hardware/README](../hardware/README.md).
- README는 시작 안내만 유지한다. 날짜별 개발 메인 문서를 추가하지 않는다. 상세 로그·bag·시험 결과는 코드 리비전과 보정 ID를 붙인 산출물로 보관한다.

**부품 도착 전 목표:** 실제와 같은 명령/피드백 계약으로 실행기를 구성하고, 가짜 장치·기록 센서로 정상/실패를 재현하며, 설치·실행 절차를 PC에서 재현 가능한 상태로 만든다. 실제 보드 호환성 확인은 후속 단계다. 단순 계획 출력이나 가짜 성공만으로 통합 완료라 하지 않는다.

**부품 도착 후 목표:** 같은 실행기에 실물 전송을 연결하고 방향·한계·TF·제동·하중을 검증한다. 관절 최대 범위와 리프트 정지/하중 유지는 단순한 마지막 보정 작업이 아니라 첫 구동의 선행 조건이다.

현재 진행 모드는 **하드웨어 완전 미연결(PC 전용)**이다. 센서·Jetson/Pi·STM32도
연결하지 않는다. 아래 2주는 가짜 장치·저장/합성 입력·host 시험·크로스 빌드로
진행하고, 센서/보드 실연결은 후속 하드웨어 검증 단계로 분리한다.

### 작업 시간과 탐색 완료 기준

- Nav2는 LDS-01 기반 2D 주행을 맡고, 리프트 장착 D415는 정지 후 집기 관측을 맡는다.
- 탐색은 미확인 영역을 우선하고 빈 시점은 즉시 다음 후보로 넘어간다. RGB 후보가
  애매하거나 깊이가 불량할 때만 같은 시점을 제한 재시도한다. 기본 후보는 최대
  32개, 시점당 촬영 기본 2회(설정 상한 3회), 전체 기본 120초다. 실측 전 후보값이다.
- 총 시간과 촬영 횟수를 보고서에 기록한다. 전체 실행 예산은 기본 300초 후보이며 준비 대기/단계 전환에도 누적한다. 만료 시 하중을 유지하며 정지하고, 단계별 대기/실행 시간을 상태에 기록한다. 이후 실제 Nav2 이동·리프트 이동·정지
  대기·인식·MoveIt 계획·팔 실행의 구간 시간을 분리 측정하고 p50/p95를 기록한다.
  모의 시간으로 실물 완료 시간이나 인식 성능을 약속하지 않는다.
- 통과 조건: 정면 미발견 후 다른 시점 발견, 완전 가림 시 부재 단정 금지, 오래된
  영상/TF·리프트 이동 전 좌표 거절, 유한 종료, 미접수/진행 중 이동의 취소 확인.

### 이번 마감과 다음 연결 작업

현재 추가 구현: 모터 ID/모델/baud/mode 점검 및 명시적 모드 변경 코어,
두 슬롯 부팅 ID 저장, AL/LS 리프트 명령, 실제 zero 전송 이후 hold 판정,
하위 단계별 탐색 이동 실행기, RGB-D 수신/OBB 깊이 표본 포트, MoveIt 계획→팔 실행
포트, 팔 heartbeat 유지용 실행 루프, 휴대폰 입체 점유 지도 화면이다.
단위 시험/크로스 빌드가 통과한 것과 전체 보드 연결이 끝난 것은 구분한다.

특히 **모바일 주기 모드 진입 뒤 기존 팔 초기화의 blocking service 호출이
차단되는 연결 문제**, 기존 양팔 torque-off 정지와 모바일 하중 유지 정지의
차이, 정지 중 양팔 피드백 공급은 우선 해결 대상이다. 보드 기본값은 계속
미설정이며, 외부 interlock 공급 없이 자동 활성화되지 않는다.

### PC에서 다음에 닫아야 하는 통합 경계

새 모듈의 단위 시험을 전체 로봇 완성으로 집계하지 않는다. 다음 네 항목은
**부품 없이도 더 개발할 수 있는 소프트웨어 작업**이며, 실측만 남았다고 하지 않는다.

1. **F2 주기 실행:** 기존 팔의 UART 소유권과 모바일 router/HAL 계층에 주기 DMA writer를 연결했다. 실제 arm ISR epoch·guard를 적용하고 blocking 서비스를 차단하며 TX/quiet 완료·대기열 기한·오류/정지·명시 재활성화를 fake HAL에서 시험했다. main loop/ISR/host stop hook은 들어갔지만 기본 미설정이다. 추가로 circular DMA 기반 주기 READ·공통 해독·4축 mode/상태 집계와 정지 중 읽기, 출력/수신 방향 검사까지 연결했다. 다음은 실측 설정과 모드 변경·부팅 초기화 및 독립 높이/전체 정지 증거 연결이다.
2. **F3/L1 wire 경계:** v2 envelope와 실제 host parser handler는 등록했고 Python/C 왕복을 검사했다. endpoint는 기본 미연결이다. 장치 mode/상태 readback과 C→ROS 상태 해독을 검사했다. 다음은 부팅 ID 생성·모드 변경/검증 절차·리프트 높이 명령·정지 hold 출력을 연결하는 일이다. `system_stop` 코어의 성공 증거를 실제 팔/리프트 feedback으로 공급해야 한다.
3. **N1/P1 실행 경계:** 정지 후 RGB-D 계약과 유한 시점 탐색 코어/PC 시나리오는 구현했다. 다음은 탐색의 MOVE_TO_VIEW를 운반 자세→Nav2→리프트→실측 정지 어댑터에 연결하는 일이다. 기존 fetch의 `search`는 계속 정지를 요구하므로 새 이동 코어를 그대로 끼워 넣지 않고 하위 단계별 조건으로 통합해야 한다. 이어서 실제 Nav2 planner/controller와 합성 scan/odom, MoveIt의 합성 조립체 IK/OMPL/월드 충돌은 실제 서비스로 검사했다. 다음은 RGB-D detector·그립퍼 접근 방향·manipulation port와 실측 충돌 형상을 연결하는 일이다. Nav2/AMCL 주행과 MoveIt 계획은 합성 입력 기반 실제 서버 시험이다. P&P는 계산/계획 단계의 부분 이식이며 집기 실행은 남아 있다.
4. **I1 통합 실행:** 앱용 RobotApplication→ROS skill port→실제 Nav2/AMCL→C 장치 모형을 한 실행으로 묶었다. 중복 요청/동시 작업 차단·도착·취소/하위 액션 종료·정지 이후 제어권 반환을 검사했다. HTTP 인증/permit/상태/취소도 같은 경로에 연결했고 scan/TF 손실 시 정지를 검사한다. 다음은 장애물 변경·장치 재부팅 및 fetch 탐색/팔 실행까지 연결하는 일이다.

각 항목은 기존 팔 회귀를 유지하며 PC에서 닫은 뒤 실물 H0–H6으로 진행한다.

## 우선순위와 의존성

```text
F1 프로토콜/소유권 → F2 UART 연결 → F3 전체 정지/진단 → I1 실제 실행기
       └────────→ B1 베이스 기구학 / L1 리프트 제어 ─────┘
S1 보드·센서 → S2 RGB-D·TF ─────────────────────────────┤
R1 조립체·관절 범위 → N1 주행 + P1 기존 P&P 이식 ──────┤
                                               I2 배달 → E1 평가 → V1 VLA
```

F 계열은 최우선이다. UART 소유권·명령 유효 기간·정지가 정해지기 전에 새 모터 writer를 기존 루프에 추가하지 않는다. 센서 입력 계약과 P&P 코드 검토는 F 계열과 독립적으로 진행할 수 있다. 아래 일수는 작업 배분 목표이며 완료 약속이 아니다. 각 통과 기준을 충족한 뒤 다음 단계로 이동한다.

## 작업별 구현 범위와 검증

### F1. 펌웨어 host 계약·구성

- STM32 한 대가 두 UART의 유일한 소유자다. 같은 Waveshare 버스에 별도 LeRobot Host를 동시에 연결하지 않는다.
- 팔 v2 12축을 16축으로 확장하지 않는다. 모바일 4축 명령·feedback·arm/stop/status를 별도 메시지로 추가하고 capability/version을 새로 정의한다. 구형 펌웨어에는 모바일 활성화를 거절한다.
- 명령은 session, sequence, STM32 기준 만료 시각/동기화 방식, 단위, 대상 그룹을 명시한다. 네트워크에서 지연된 명령을 UART 수신 시각만으로 새 명령으로 취급하지 않는다.
- 전원 인가 상태는 disabled. 장치별 ID·mode·오류·피드백 확인 후 활성화한다. EEPROM 설정·ID 변경·homing은 일반 부팅과 분리한다.
- **시험:** C/Python golden frame 상호 일치, 잘못된 길이·CRC·ID·중복·순서 역전·session 교체·timer wrap·지원하지 않는 capability 거절.

### F2. 공유 UART·실시간 처리

- `shared_bus`/`bus_router`는 대기열·시간 예산을, 보드 `servo_transport`는 기존 코드까지 포함한 물리 UART 소유권을 담당한다. 서비스·IT 피드백·DMA는 공통 전송 함수를 사용한다. `ClaimQueued`가 둘을 함께 확보한 뒤 HAL로 보내며 TX/RX/quiet 완료 뒤 `CompleteQueued`로 해제한다. deadline/abort 실패 시 정지 차단을 유지하고 `RecoverQueued`·확인된 `ResumeQueued`만 허용한다.
- STM32 main loop가 소유권을 변경하고 ISR은 완료 사건만 전달한다. 팔 5 ms tick과 telemetry 슬롯을 기준으로 wire time+turnaround+timeout+복구 시간을 배정한다.
- STOP은 대기 작업보다 먼저 실행하되 진행 중 DMA를 덮어쓰지 않는다. 중단이 필요하면 HAL abort·RX 정리·idle 확인 후 진행한다. 오류 후 단순 busy 해제로 복구하지 않는다.
- **시험:** 가짜 UART의 지연·누락·중복 callback, 좌우 독립성, STOP 대기, queue 포화, arm slot 침범, 최악 부하의 지연/누락 계수. 도착 후 로직 분석기/실제 진단으로 동일 시간 예산 확인.
- `binary_control.c`는 v1 진단, v2 세션/실행, 모바일 명령, 정지/진단 단위로 점진 분리한다. 기존 후보별 wire 동작 시험을 유지하며 대규모 일괄 재작성은 피한다.

### F3. 정상 정지·고장 정지·재시작

- 구현한 `mobile_supervisor`는 session/sequence·시간 제한·피드백·mode·원점·리프트 경계를 검사하고 이상 시 4축 요청을 0으로 만든다. 실제 전송·감속·하중 유지는 다음 연결이다.
- 정상 취소: 새 목표 차단 → 바퀴 0/감속 전송 → 새 피드백으로 정지 확인 → lift/팔 하중 유지 확인 → 취소 완료. 전송 완료를 정지 완료로 보고하지 않는다.
- 기존 팔 `Host_PerformV2CoordinatedStop`은 torque disable이므로 물체를 든 정상 취소를 그대로 대체하지 못한다. hold 모드와 기존 비상/고장 경로의 의미를 분리해 설계한다.
- 통신 단절·tracking fault·저전압·과전류·온도·리프트 원점 상실을 원인별 기록하고 latch한다. clear/재활성화는 새 session과 실제 상태 확인을 요구한다. 전원 상실 대책은 기계·전원 설계와 함께 검증한다.
- **시험:** host 종료/케이블 단절, wheel 1개 응답 상실, arm fault 중 base 이동, lift limit 접근, stop 도중 재명령, 전원 재인가. 코드·fake 장치 시험과 실제 제동/하중 시험을 별도로 통과한다.

### B1. 베이스 기구학·피드백·odometry

- 3륜 옴니 정/역기구학을 ROS `vx, vy` m/s, `wz` rad/s로 통일한다. 공식 코드의 deg/s와 설치 방향을 변환한다. 바퀴 반경·배치 반경·방향·속도 스케일은 설정으로 둔다.
- 속도 포화 시 바퀴별 개별 절단으로 방향을 바꾸지 않도록 공동 비율 제한을 검토한다. 가속/감속 상한을 둔다.
- **실측 wheel velocity**와 관측 시각으로 odometry를 적분한다. 명령 echo는 실측으로 사용하지 않는다. 지연·누락 시 불확실성과 진단을 표시한다.
- **시험:** 순수 전후·좌우·회전·혼합 입력과 역변환, 단위·부호·포화·시간 역행; 실물 직선/횡이동/회전의 거리·각도 오차 기록.

### L1. 리프트

- `UNHOMED → HOMING → READY → MOVING → HOLDING / FAULT` 상태, 별도 homing 요청·취소·최대 시간·전류/정체 판정을 구현한다. 부팅 때 자동 하강하지 않는다.
- 엔코더 wrap 누적과 높이 변환, 전원/통신 상실 시 원점 유효성, 상하 한계·제동 거리·기구 여유·높이 목표 도달 판정을 정의한다.
- `lift_controller`에 wrap 누적·접촉 dwell·homing timeout·높이 목표·접근 시 속도 감소·hold 증거 확인을 구현했다. 현재 접근 속도 감소는 검증된 제동 거리 모델이 아니다. 실물 hold 출력과 제동 모델 연결이 필요하며 속도 0 또는 torque off를 자동으로 HOLDING으로 바꾸지 않는다.
- **시험:** wrap 양방향, encoder 점프/누락, 잘못된 원점, homing timeout/정체 오탐, 경계 접근·취소; 실물 높이 반복성·정지 후 처짐·하중별 유지 측정.

### R1. 전체 관절 공간·로봇 모델

- 목표는 SO-ARM의 기구적으로 가능한 전체 범위다. 이전 작업에 맞춘 **관절 범위**와 기계적 끝점/배선 여유를 구분한다. 팔 베이스 아래의 집기도 전체 형상과 환경을 기준으로 계획한다.
- 기존 v1 점검 범위, v2 실측 범위, URDF 범위/영점이 다르다. 현재 canonical JSON은 과거 실측 근거이며 새 조립체 기계 최대 범위가 아니다.
- 지금: 설정 생성/불일치 차단·범위 비교·좌표 변환을 준비한다. 도착 후: 좌우 개별 영점·방향·끝점·케이블 간섭을 측정하고 raw/urad 한계와 모델 좌표를 함께 갱신한다. 신규 수치를 검증 없이 과거 승인 기록에 넣지 않는다.
- base/lift/양팔/센서의 조립체 URDF와 collision geometry를 만든다. 치수 미확정값은 후보값으로 표시하며 실물용 launch에는 실측 설정을 요구한다. 그리퍼 servo 범위와 jaw gap은 별도 보정한다.
- **시험:** 경계 양끝과 바깥값, shoulder 4095→0, 실제↔모델 좌표 왕복, lift 높이별 TF, 자기 충돌/베이스 간섭; 실물 무부하 저속으로 범위 확인.

### S1–S2. 보드·센서·인식

PC 단계에서는 입력/시간/TF 계약·저장/합성 자료와 오류 처리를 구현한다. 아래 실제
보드/센서 연결과 성능 측정은 하드웨어를 연결하는 후속 단계의 통과 조건이다.

- 온보드 한 대 원칙, 영상/VLM을 고려해 Jetson을 우선 검토한다. 실제 RAM·JetPack/Ubuntu·ROS·GPU/USB·냉각·전원 확인 후 환경을 고정한다. Pi 5는 대안이다.
- 현재 PC 검증은 Jazzy다. JetPack 6.2의 Ubuntu 22.04를 그대로 Jazzy native 환경으로 가정하지 않는다. Humble 이식 또는 Jazzy 컨테이너의 GPU/USB 접근을 먼저 시험한다. [장비별 출처와 확인 목록](../hardware/README.md)을 따른다.
- 리프트 장착 D415 RGB/depth/CameraInfo와 LDS-01 두 대를 독립 장치명·topic·frame으로 기록한다. 첫 위치 추정은 LiDAR 한 대로 만들고 두 번째는 가림 보완을 측정한 뒤 연결한다. IMU는 미보유이므로 선택 사항과 비용을 분리한다.
- 인식 결과에는 object ID, pose, frame, 관측 시각, calibration ID, 깊이 유효성/불확실성을 포함한다. lift/base 이동 후 재관측한다. 소파 틈·깊이 누락·가림과 침대의 변형을 실패 사례에 넣는다.
- **시험:** 센서 동시 기록·재연결·오래된/미래 프레임·누락 TF·깊이 이상치·대상 없음, 센서+추론 부하에서 제어 주기 유지. 실물 장착 뒤 외부 보정과 접근성 확인.

### N1·P1. 주행과 기존 Classical P&P

- 주행은 베이스 단독 방향/정지 → odometry → LiDAR 지도/위치 추정 → Nav2 왕복 → 반복 정차 순서다. IMU가 없어도 되는 초기 추정 구성을 명시하며 장치가 있는 척 발행하지 않는다.
- Nav2와 미세 정렬기는 한 번에 하나만 베이스 명령을 소유한다. 도착 결과와 실측 정지는 별도 조건이다. 위치 추정 상실/장애물/좁은 통로에서 timeout·취소를 시험한다.
- P&P 원본 리비전·의존성·인식→변환→계획→실행 경로를 기록하고 인터페이스를 이식한다. 고정 작업대 좌표/보정/전달 자세를 새 로봇 기본값으로 복사하지 않는다.
- **시험:** 기록 RGB-D로 인식·계획 회귀; 실물 정지 플랫폼에서 집기→유지→놓기; reach 실패/잘못된 깊이/그리퍼 미집기/물체 낙하. 양팔 전달은 대표 작업에 필요할 때만 사용한다.

### I1–I2. 전체 작업 실행기

- 현재 15단계 replay와 추가한 simulation 실행기를 기준으로 실제 navigation/alignment/lift/perception/manipulation 어댑터를 구현한다. 시작/진행/완료/취소·고유 goal ID·timeout·유한 재시도를 공통화한다.
- 제어 소유권과 연속 상태 감시는 별도 책임이다. 시작 순간 조건만 확인하지 않고 주행 중 운반 자세·하중, 조작 중 base/lift 정지, 관측/TF의 최신성을 감시한다.
- **시험:** 정상 15단계, 각 단계에서 취소, 단계 결과 누락/중복/이전 goal 도착, 물체 상실, 접근 불가, 한계 도달, 통신 장애. 자동 재시도는 상태가 회복되고 정해진 횟수/시간 안에서만 허용한다.
- 초기 실물은 접근 쉬운 지정 면 간 배달, 이후 소파→침대다. 가구 접근·파묻힘·그리퍼 공간 문제를 알고리즘 오류와 구분한다.

### D1. 배포·운영·재현성

- OS/ROS/SDK/원본 의존성 리비전·펌웨어 profile/해시·설정 해시를 한 실행 기록에 남긴다. 후보와 검증된 설정을 구분하고 검증된 배포본으로 되돌릴 절차를 만든다.
- 진단에는 장치별 마지막 관측 나이, mode, 통신 오류/복구, 명령 sequence/session, stop 원인, 주기 지연, 원점 유효성을 포함한다.
- 부팅/서비스 자동 재시작은 장치 연결·진단까지만 한다. 모터 자동 활성화·이전 작업 자동 재개·자동 homing은 하지 않는다.
- **시험:** PC의 깨끗한 환경에서 설치/빌드/오프라인 실행, 합성/기록 입력 장시간 실행, 프로세스 종료·재시작, 설정 누락/불일치. 실제 센서 장시간 기록은 연결 후 별도 검증한다. 첫 실물 배포는 위 F3·B1·L1 시험을 개별 실행할 수 있어야 한다.

## E1. Classical 평가와 VLM/VLA 확장

Classical 평가: 조작 성공률, 전체 배달 성공률, 소요 시간, 정차/높이 오차, 재시도·사람 개입·물체 분실, 통신/정지 실패를 기록한다. 위치·물체 방향·가구 높이·조명·표면 조건을 구분한다.

VLM은 후속 이미지/언어 해석 모듈이다. 지원하는 물체/장소의 정형 요청 또는 후보를 출력하고 제어 루프와 분리한다. 오래된 추론 결과·지원하지 않는 요청·모호한 장소는 실행에 사용하지 않는다. 모델 지연·메모리는 센서/제어 동시 부하에서 측정하며 온보드 추론 가능 규모는 미확정이다.

VLA는 Classical 전체 배달 이후 진행한다.

1. 리더암·카메라 구성을 확인하고 영상/언어/관절 상태/행동/시각/성공 결과를 동기화해 수집한다. 학습·평가 배치를 분리한다.
2. 모델·데이터 규모·학습 장치를 선택한다. 초기 정책 제어는 **정지한 base/lift 위의 팔·그리퍼**로 한정한다.
3. 주행·정렬·리프트·제한·결과 판정은 공통화하고 같은 배치/재시도 예산으로 Classical과 비교한다. 데이터 수집/학습 비용도 기록한다.
4. Classical 복구를 사용한 VLA 시도는 별도 집계한다. 정책 변경 전 팔·물체 상태를 확인한다.

추가 물건 정리·빨래·변형체와 전신 동시 학습 제어는 이후 범위다.

현재는 UI와 분리된 navigate_to 요청·지도 descriptor·상태/취소·중복 요청 처리와
인증 HTTP gateway가 구현돼 있다. map revision/floor/frame/바닥 높이·장애물
여유·경로를 검사하고 배달 작업과 제어권을 공유한다. 인증 HTTP→앱 작업 관리자→실제 Nav2 서버의 PC 연결은 구현했다. 휴대폰 브라우저용 입체 점유 지도 화면과 경로 확인·이동·취소를 추가했다. 실측 mesh와 네이티브 앱 패키징은 아직 없다. 현재 gateway는 simulation 전용이다.

1. **PC에서 먼저:** 앱 요청 예제로 지도 검사→가짜 주행→상태/취소를 회귀 시험한다.
   지도 교체·오래된 클릭·작업 중 재요청·정지 확인 누락을 포함한다.
2. **gateway:** bearer 인증·3초 유효 permit·재시작 후 request ID 보존·취소 API를 구현했다.
   상태 조회는 polling이며 stream은 후속 선택 사항이다. 기본 loopback, LAN은 TLS 필수다.
   앱에 모터 명령/제한 변경 권한을 노출하지 않는다.
3. **3D 보기:** 시각화 mesh/점군과 주행용 바닥 map의 좌표·revision을 함께 관리한다.
   바닥 raycast로 선택하고 x/y/yaw 목표를 미리 표시한다. 가구 위 클릭은 이동 목표로
   자동 변환하지 않는다. 목적지 선택→진행→취소를 앱의 첫 기능 범위로 둔다.
4. **실제 adapter:** Nav2 goal/result와 합성 C 정지 feedback을 공통 실행기에 연결했다. 다음은 센서 시각/위치 추정 손실과 실측 정지 계약을 실제 장치에 연결한다.
   앱이 없어도 동일 요청을 PC에서 시험할 수 있게 유지한다.
5. **실물 평가:** 지정점 정차 오차·방향·경로 차단·위치 추정 상실·앱 재연결을 시험한다.

A1은 Classical 배달과 독립적인 사용자 진입점이며 VLM을 필요로 하지 않는다.
3D 맵을 보여주는 것과 3D 공간을 자유롭게 이동하는 것은 별개로 다룬다.
