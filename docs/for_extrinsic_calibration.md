# 구조 정리

## 전체 흐름

(1) 외부 보정: eye-to-hand 캘리브레이션
- 로봇 몸체(base)기준으로 카메라가 어디에 어떤 자세로 있는가(base_from_optical, 6축)을 구함
- 카메라 6축 뿐만 아니라, 관절 영점, 오른팔 장착, 리프트 배율과 영점까지 같은 데이터로 한번에 추정했다.
- 이를 통해 카메라 인지 모델에서 계산한 특정 좌표의 위치를 이 캘리브레이션 값을 통해 변환해서 물리 세계 좌표를 알아낼 수 있다.


(2) Jeston 반영
- Jeston 의 릴리스 폴더에 있는 프로필 JSON파일에 보정값을 넣는다. 

(3) MoveIt 좌표 계산
- 카메라가 RGB-D 영상을 보내면 좌표 게산은 호스트 코드가 한다. 변환 결과는 로봇 몸체(base) 좌표로, MoveIt은 이 base좌표 안에서, 프로필로 만든 로봇 모델(카메라 위치, 팔 장착, 리프트 높이 포함)로 궤적을 게산한다.
- MoveIt이 내놓는 것은 모델 상의 관절 각도로 이를 실제 raw값으로 바꿀때는 프로필의 관절 영점(home_model_rad)이 들어간다. 관절 영점 보정이 반영되는 것이 이 단계이다. 

(4) STM32 반영
- Jetson이 시리얼로 raw 관절 목표값을 순서대로 보내면 펌웨어가 안전 검사(관절 관계, 한 틱당 이동량, 통신 오류 정지)를 하면서 서보에 전달한다.


## 리프트 계산 부분

원래는 리프트 계산 부분을 아래 공식과 같이 공식적으로 나온 값을 바탕으로 구했다.(서보의 12비트 엔코더 사양, 한바퀴 이동은 AlohaMini공식 설정값)

h = (raw − 원점 raw) × meters_per_count
meters_per_count = 84mm(한 바퀴 이동, 설계값) ÷ 4096(한 바퀴 엔코더 수) ≈ 0.0205mm/count

- 최상단에서 최하단까지 내려가는 동안 엔코더 30,717 count 이동거리는 약 640mm로 가정했고 한 바퀴 = 85.34mm로 공식값보다 1.6% 크다.(현서오빠가 구한 값), 그런데 런타임은 이 값을 쓰지 않고 공식값을 쓰고 있는 중 

30,717 count는 엔코더로 센 확실한 숫자입니다. 그런데 11/17 배율을 곱하면 전체 행정이 654.6mm가 되고, 리프트 상단 등록에 쓴 CAD 값 643.8mm와 약 11mm 차이가 납니다. 즉 지금 프로필 안에서도 배율(측정)과 상단 높이(CAD)가 서로 모순

- 11/17 보정에서 실제로는 한 바퀴에 3.9% 더 이동한다는 것을 찾아, 이 값을 이미 0.0213mm/count로 고쳤다. 
- 그런데 이 보정은 다음과 같은 방식으로 구했다.
    - 보정을 5·30cm에서만 해서, 64cm 상단은 외삽 구간
    - 시험 때 상단에서 측정 안 된 CAD 높이(64.4cm)로 원점을 등록


## 로봇 몸체 관련 부분
- base_link는 바퀴와 차체로 정의된 좌표계인데, 보정 사진에는 바퀴가 나오지 않는다.
- 카메라로 직접 볼 수 있는 건 팔 마커와 바닥·탁자 평면뿐이다.
- 몸체의 높이, pitch, roll 는 바닥 평면이 고정인 채로 측정이 되고, 몸체의 앞뒤·좌우 위치, 방향(yaw)은 CAD: 왼팔 장착 위치와 왼팔 base 영점을 CAD 값으로 고정한다.
- 그러나 집기와는 이 base_link오차는 관계가 없다. 
- 왼팔 CAD 장착값이 실제와 몇 mm 달라도, base_link 정의가 그만큼 옮겨질 뿐 카메라와 팔은 같이 옮겨진다. 그래서 둘 사이 관계는 그대로
- 차체 기준으로 영향이 있는 부분은 주행과 이동 후 저장된 관측을 다시 쓸 때, 차체가 움직인 만큼 좌표를 옮기는 계산

## 3. 원인 진단 (유력한 순서)

**H1. 목표점이 처음부터 낮게 잡힘 — 가장 유력**
- 테이프 목표 79.38cm, 같은 장면의 수납장 평면 80.13cm로 7.5mm 차이가 난다. 숫자 근거가 있는 유일한 원인이다.
- 카메라가 약 45° 아래로 보기 때문에, 깊이 오차는 위아래와 앞뒤 오차로 함께 나타난다. "아래로 + 앞뒤도"라는 증상을 하나로 설명한다.
- D415 깊이는 RGB가 아니라 적외선 스테레오로 잰다. 검은 무광(또는 광택) 테이프, 작은 표적 경계, RGB–깊이 정렬 오차, 한 픽셀 노이즈가 후보다. 평면은 수천 픽셀을 평균해서 정확했다.
- 이 원인이 주라면, 오차의 상당 부분은 시험 방법에서 생긴 것이고 팔 정확도의 문제가 아니다.

**H3. 리프트 높이 — 유력**
- 리프트 배율이 측정 방법마다 다르다.

| 방법 | 한 바퀴당 | 30,717 count의 전체 행정 |
|---|---|---|
| 공식 설정값 (런타임 원래 값) | 84.0mm | 630mm |
| 11/01 위아래 측정 (행정 640mm는 대략값) | 85.3mm (+1.6%) | 640mm |
| CAD `travel_m` (상단 등록에 사용) | — | 643.8mm |
| 11/17 카메라 보정 (현재 프로필) | 87.3mm (+3.9%) | 654.6mm |

- 보정은 30cm까지만 했고, 시험은 64cm에서 측정 안 된 CAD 높이로 상단 등록했다.
- 현재 프로필 안에서도 배율(측정)과 전체 행정(CAD)이 약 11mm 모순이다.
- 방향 문제가 있다. 11/17 배율이 맞다면 실제 상단은 등록값보다 높아서 팔이 **위로** 가야 하는데, 관측은 아래였다. 그래서 30cm 위에서 배율이 다르거나, H1처럼 아래 방향 원인이 더 크다. 다만 상단 등록 코드가 저장소에 없어 부호를 직접 확인하지는 못했다.
- 리프트는 카메라와 팔 사이에 있어서, 리프트 높이 오차는 팔 끝 위아래 오차로 1:1로 들어간다.

**H2. 손끝 오프셋·손목 회전 영점 — 가능, 크기 불명**
- 보정은 그리퍼에 붙인 마커 위치를 맞춘 것이다. 마커 자세는 미지수 6개로 같이 추정했다.
- 손끝은 마커로 관측한 적이 없고, CAD `gripper_frame_link` 오프셋으로 계산한다.
- 손목 회전 영점은 마커 자세에 흡수돼서 구해지지 않는다(`calib_model.py` 머리말).
- 11/17 손끝 접촉 시험은 리프트 회전수 기록 오류(0.29m 대 실제 약 0.55m)와 잔차 12mm로 판정하지 못했다.
- 이 원인이면 손목 자세에 따라 위아래·앞뒤 오차가 바뀐다.

**참고: 중력 처짐**
- 약 5mm이고 런타임에 반영되지 않았다. 처짐을 넣으면 10.5mm에서 5.1mm로 준다.
- 위 세 원인을 다 잡아도 이만큼은 남는다.

## 1. 출발 전 (데스크탑)

### 1-1. 펌웨어: 오늘은 S4로 한다

11/16–17에는 자동 투어와 촬영 도구가 S3 기준이라 S3(0x24911)를 임시로 설치하고 촬영했다. 오늘은 **S4(0x2492D) 그대로** 한다.

| 블록 | S3 가능 | 이유 |
|---|---|---|
| B 깊이 비교 | 가능 | 카메라만 씀 |
| C 손끝 접촉 | 가능 | 토크 OFF 읽기만 함 |
| D 리프트 단계 | 어려움 | S3는 리프트 토크가 없어 단계 높이를 유지하지 못함(11/16에 7.6mm 하강) |
| E 점 이동 재시험 | 불가 | 현서 실행 도구는 S4용. 문제가 난 조건도 S4 |

- 펌웨어를 S3로 바꿨다가 S4로 되돌리면 두 번 기록해야 한다. 모터 전원 차단, 백업, 기록, 검증이 필요하고, 복구 후 영점 활성화와 리프트 기준 등록도 다시 해야 한다.
- 11/17 보정 데이터는 리프트 토크가 없는 S3 상태에서 찍었다. 실제 사용 조건인 S4에서 측정해야 리프트 유격 방향 같은 차이가 섞이지 않는다. 이 차이가 실제로 있는지는 아직 확인한 적이 없다.

**촬영 도구 S4 호환 (2026-11-18 복구 완료, 실물 미검증)**
- 브랜치를 원격으로 덮어쓴 뒤의 `raw_shot.py`, `pose_check.py`, `live_cam.py`는 S3만 허용해서 S4에서 거부됐다.
- 보관해 둔 `capture_common.py`를 다시 합쳤다.
  - S3·S4 모두 허용
  - 깊이 노출 16ms 고정. 런타임 높이 모델과 같은 값이다. 11/15에 자동 노출은 탁자 높이를 6–9mm 다르게 쟀다.
  - 정지 잠금 상태에서도 읽기 전용 촬영은 거부하지 않고 기록한다. 원격 쪽 동작을 유지한 것이다.
- `helpers.sh`는 `REL`(릴리스 경로)을 명시해야 하고, 세션 폴더는 `helpers.sh`가 있는 폴더다. `rawshot NAME LIFT_M left|right ATT`로 팔 마커 그룹도 기록한다.
- 가짜 제어기 응답으로 S3 허용, S4 허용, 다른 펌웨어 거부, 정지 잠금 처리를 확인했다. **S4 실물에서는 아직 실행해 보지 않았다.** 도착 후 `pose`가 첫 확인이다.
- `tour`, `sweep`, `platform_check.py`, `rest_check.py`는 여전히 S3 전용이다. 오늘은 쓰지 않는다.
- 대안: `pose`가 S4에서 거부되거나 현서가 읽기 전용 조회를 허용하지 않으면, 처음에 S3로 C만 찍고 S4로 복구한 뒤 D·E를 한다.

## 2. 현장 순서 (약 3.5시간, 위에서부터. 시간이 모자라면 E를 줄인다)

### A. 상태 확인 (15분)

- [ ] 모터 전원 ON, 양팔 토크 OFF, 받침, 집게 빈 상태
- [ ] `REL=<릴리스 경로> source ~/cal_20261118/helpers.sh`
- [ ] `pose`: 펌웨어 0x2492d, 관절 범위 확인
- [ ] 릴리스 폴더의 `calibration_id`가 `s2-dev-4683680…`인지 확인
- [ ] 리프트 최하단 raw 값을 읽어서 11/17 값(3900)과 비교
- [ ] `camshot TEST-1` → 노트북에서 사진 확인

### B. 목표점 깊이 (카메라만, 20분) — H1

같은 면 위에 **검은 테이프 / 흰 종이 십자 / 손끝 표적지(ArUco)**를 나란히 둔다.

- 높은 수납장: `camshot DEPTH-H-01` … `05` (배치를 바꿔 가며)
- 낮은 탁자: `camshot DEPTH-L-01` … `05`

분석에서 표적마다 세 값을 비교한다: ① 픽셀 깊이(주변 중앙값), ② 시선과 평면의 교점, ③ ArUco PnP.

- 판정: 검은 테이프만 평면과 수 mm 이상 차이 나면 H1 확정이다. 이후 목표점은 ArUco PnP나 평면 교점으로 정한다.
- 분석 스크립트는 새로 만들어야 한다. 현장에서는 촬영만 한다.

### C. 손끝 접촉 (리프트 최하단, 낮은 탁자, 60분) — H2

- **리프트 최하단**에서 한다. 원점이 분명하고 회전수 모호성과 리프트 하강이 없어서 리프트 오차가 섞이지 않는다.
- 낮은 탁자(32.1cm)는 최하단에서 닿는다. 최하단 어깨 높이는 바닥에서 약 37cm다.
- 양팔 토크 OFF, 집게 완전히 닫음. 손으로 팔을 움직여 집게 맨 끝을 표적지 십자 중앙에 댄다.
- 끝을 점에 댄 채 자세를 바꿔 6장: 위에서 수직, 앞으로 기울임, 뒤로, 왼쪽, 오른쪽, 손목 돌림.
  ```bash
  rawshot TCP-L-A01 0.00     # A01 ~ A06
  ```
- 표적지 자리를 바꿔 A(가운데 가까이), B(옆 중간), C(가운데 멀리). 오른팔도 같은 방법으로 `TCP-R-…`.
- 끝이 미끄러지면 같은 이름을 다시 쓰지 않고 다음 번호로 찍는다. 표적 양옆 마커 중 하나는 화면에 보여야 한다.

분석은 기존 `analysis/tcp_touch.py`로 한다.
- 손끝 오프셋 `t`(CAD 대비)를 구한다.
- 피벗 잔차를 구한다.
- 카메라로 본 표적점과 손끝 피벗점의 차이(카메라 → 팔 전체 오차)를 구한다.
- 손목 회전 영점 오차는 `t`에 함께 흡수되므로, 구한 `t`가 실제로 쓸 손끝이다.

판정:
- 피벗 잔차가 약 3mm 이하이고 `t`가 CAD와 수 mm 이상 다르면 H2 확정이다. `reference_from_tcp`를 갱신한다.
- 피벗 잔차가 크면(11/17처럼 12mm) 끝이 미끄러졌거나 자세 다양성이 부족한 것이다. 그 자리를 다시 찍는다.

### D. 리프트 단계 측정 (40분) — H3

리프트를 조작하는 것은 현서 도구와 현서 판단으로 한다.

1. 리프트 판(팔 장착판) 앞면에 마커 판을 단단히 붙인다. 먼저 `livecam`으로 **최상단에서도 화면에 보이는지** 확인하고 부착 위치를 정한다.
2. 최하단에서 시작해 한 단계 **35–40mm 이하**로 올린다.
   - 반 바퀴(42mm)보다 작게 움직이면, 한 바퀴 안의 raw 값만으로도 회전수를 헷갈리지 않고 이어 붙일 수 있다.
3. 단계마다 멈추고 리프트 raw가 안정된 뒤 raw 값을 기록하고 `camshot LIFT-U00`, `LIFT-U01`, … 를 찍는다.
4. 최상단에서 같은 방식으로 몇 단계 내려오며 `LIFT-D00` … 를 찍는다(오르내림 차이 확인).
5. 마커 한 변을 캘리퍼로 잰다. 높이는 줄자로 재지 않는다.

분석은 누적 count 대 카메라로 본 판 높이로 한다. 스크립트는 새로 만들어야 한다.
- 기울기(실제 mm/count)
- 직선성
- 최상단까지 실제 전체 행정
- 판 기울기, 오르내림 차이

판정:
- 직선이면 `meters_per_count`와 `travel_m`를 실측값으로 갱신한다. 상단 등록은 실측 전체 행정으로 한다.
- 11/17 값(+3.9%)과 0.5% 이내면 배율은 유지하고 `travel_m`만 갱신한다.
- 직선이 아니면 런타임이 배율 하나만 지원하므로 높이별 구간표가 필요하다(코드 작업). 그때까지는 보정 범위 안 높이만 쓴다.

### E. 점 이동 재시험 (60분) — 종합

- 표적: 손끝 표적지(ArUco). 목표 좌표는 PnP로 정하고 테이프 깊이는 쓰지 않는다.
- 그리퍼에 마커를 붙인 채 한다. 도착 자세에서 마커가 보이면 그 사진만으로 팔 위치 오차를 잴 수 있다.

| 조건 | 내용 | 횟수 |
|---|---|---|
| E1 | 최하단 등록 + 낮은 탁자 (보정 범위 안) | 자리 3곳 |
| E2 | 높은 수납장 + 지금 방식(상단 CAD 등록) | 자리 3곳 |
| E3 (시간 되면) | 높은 수납장 + D 결과로 등록 높이 수정 | 자리 3곳 |

시도마다 기록할 것:
- 도착 후 `camshot` (그리퍼 마커와 표적이 같이 보이게)
- 관절 엔코더 값과 리프트 raw
- 위에서 찍은 사진. 표적지 눈금으로 앞뒤·좌우·위아래 오차를 mm로 읽는다.

판정:
- E1은 작고 E2가 크면 H3(리프트)가 원인이다.
- E1도 크면 H1·H2 쪽이다. C 결과와 비교한다.
- E3가 E2보다 작아지면 리프트 수정 효과가 확인된다.
