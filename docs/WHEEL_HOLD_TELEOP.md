# 현재 자세 고정과 바퀴 전용 텔레옵

발표의 두 이동 구간(시작 위치→책상, 리모컨을 든 책상→침대)에 사용하는 별도 후보다.
v7는 전원 재투입 후 현재 자세를 고정하는 명시적 설정 단계를 포함한다.
기존 바퀴 전용 텔레옵을 재사용하며, 이동 중 팔 경로나 리프트 높이를 바꾸지 않는다.
현재 팔 제어기와 함께 두 프로세스를 실행하는 방식이 아니다. STM32 모드를 전환해
서보 모터 자체가 유지하는 기존 목표값을 보존한다.

## 구현된 동작

- 주행 모드에서는 바퀴 ID 7·8·9에만 속도와 토크 명령을 보낸다. 전후·좌우·회전은 기존 비율을 사용한다.
- 양팔 12축(집게 포함)과 리프트 ID10의 모드, 토크, 가속도·목표 위치·시간·속도를 읽는다.
- 이미 토크 ON인 집게의 **현재 위치를 목표값으로 다시 쓰지 않는다**. 접촉 때문에 목표와 현재 위치가
  다르더라도 기존 목표를 보존하므로 의도한 누름을 소프트웨어가 풀지 않는다.
- 주행 시작 전 13축 토크 ON, 팔 위치 모드, 리프트 정지 상태를 확인한다.
  OFF인 축은 별도의 `hold-here` 명령에서만 현재 자세 고정을 허용한다.
- 목표나 토크가 달라지거나 조회 실패·오래된 피드백을 발견하면 바퀴만 정지한다.
- Space, 종료, SSH 끊김, 잘못된 세션, 400ms 명령 만료에서도 바퀴만 정지한다.
  바퀴 정지 뒤에는 바퀴 토크를 끄지만 팔·집게·리프트에는 쓰기 명령을 보내지 않는다.
- UART polling/IT/DMA 공통 전송 제한은 주행 중 팔·집게·리프트 쓰기를 차단한다.
  자세 고정 단계에서만 해당 축·레지스터·측정값이 일치하는 한 패킷씩 허용한다.
  브로드캐스트는 허용하지 않으며 U/J 리프트 키도 없다. 준비 단계에서만 리프트 모드(33)와
  EEPROM 잠금(55)을 변경할 수 있고, 주행·정지 처리에서는 해당 쓰기를 차단한다.
- 키보드 입력 반복이 300ms 끊기면 정지한다. 브라우저는 키를 놓거나 창을 벗어나면
  정지하고, 250ms 접속 만료 후에는 새로고침으로 다시 연결해야 한다.

`hold_confirmed`는 설정·토크 유지와 리프트 위치 모드 및 목표 대비 실제 위치 편차를 확인한다.
리프트 편차가 96 count(기존 환산으로 약 2mm)를 넘으면 주행을 멈춘다.
응답의 `lift_position_raw`·`lift_target_raw`로 실제 위치를 비교한다.
물체 미끄러짐이나 실제 파지력, 장시간 발열, MCU 전환 중 실제 지지 상태를 증명하지 않는다.

## 전원 재투입 후 현재 자세 고정

같은 v7 펌웨어에서 조회 → 현재 자세 고정 → 바퀴 조작이 가능하며, 중간 재설치가 없다.
자동 실행은 없고, 부팅·INFO·plan-hold는 모터 쓰기를 하지 않는다.

1. `plan-hold`: 바퀴 토크 OFF·목표/현재 속도 0을 확인한다. 양팔·리프트의 모델 ID,
   모드, 토크, 목표와 현재 위치·속도를 읽고 100ms 후 다시 확인한다.
   조회 계획은 팔 위치 모드, 리프트 위치 모드 또는 0속도 모드를 허용한다.
   주행은 리프트 위치 모드로 고정 설정을 완료한 뒤에만 허용한다.
2. `hold-here`: 위 계획을 새로 읽고 일회용 토큰으로 적용한다. 계획은 30초 뒤 만료된다.
   그 전에 바퀴에 0속도와 토크 OFF를 보내고 반복 정지 조회를 통과해야 한다.
   전원 직후 바퀴 토크가 ON이더라도 이 단계로 준비하며 팔·리프트에는 쓰지 않는다.
   `stop-wheels`로 이 단계만 별도로 실행할 수도 있다. 팔 유지 기준이 아직 없는
   초기 상태의 바퀴 정지는 팔 유지 확인을 주장하지도, 그것만으로 오류 잠금을 걸지도 않는다.
   전체 축과 각 축의 쓰기 직전에 다시 읽어 설정 변경 또는 8 count 초과 위치 변화를
   거부한다. 이미 ON인 축의 목표는 그대로 보존한다.
3. OFF인 팔은 첫 쓰기로 그 시점의 측정 위치를 목표로 쓰고 확인한 뒤 토크 ON을 확인한다.
   ON인 팔·집게의 목표는 보존한다. 리프트는 받침이 있는 준비 단계에서 현재 위치를 고정한다.
   속도 모드라면 토크 OFF → 현재 각도 목표 기록 → 토크 OFF 재확인 → 모드 잠금 해제 →
   위치 모드 변경 → 재잠금 순서다. 목표 쓰기가 토크를 켜더라도 이 시점은 0속도 모드이며,
   위치 모드 전환 전에 현재 각도가 기록돼 있어 과거 위치로 이동하지 않는다.
   각 단계 값을 재조회하고, 모드 전환 전후 위치 변화·위치 한계도 확인한다.
   모드 변경 응답이 유실돼도 재잠금을 시도하며 바퀴는 활성화하지 않는다.
   위치 모드에서 새로 읽은 현재 각도를 목표로 기록하고 토크 ON을 확인한다.
   PID·토크 한도·보정 오프셋·관절 범위는 바꾸지 않는다.
4. 일부 축까지 설정한 뒤 실패하면 바퀴는 켜지지 않으며, 설정된 팔의 토크를 자동으로
   끄지 않는다. 하중을 받친 상태로 원인을 확인한다. 요청 재전송·자동 재시도는 없다.

실물에서 정지한 속도 모드 리프트의 위치는 1860~1861인데 속도 보고는 0/50으로
나왔다. 이 경우 속도 한 번만으로 거부하지 않고, 계획·적용 전에 각각 400ms 이상
연속 위치 변화가 8 count 이내이며 속도 보고가 50 이하인지 확인한다. 실제 드리프트,
더 큰 속도 보고, 0이 아닌 리프트 목표 속도는 계속 거부한다. 팔의 기준은 바꾸지 않았다.

현재 자세 고정은 자동 파지나 파지력 복구가 아니다. OFF 집게는 현재 벌림을 유지하는
목표만 설정하며 추가로 닫지 않는다. 물체를 들고 주행하려면 양쪽 손끝 접촉과 실제
지지 상태를 실물에서 확인해야 한다. 고정 과정 동안 팔·리프트·물체를 받쳐 둔다.

## 10분 조작 검토 (2026-11-09)

시간에 따른 자동 종료는 없다. 호스트 명령은 20 Hz이고 10분이면 약 12,000개이므로
32비트 순서 번호 상한과도 거리가 멀다. C 펌웨어 가상 시간 10분에 11,762개 명령으로
방향 전환·정지·간헐적 150ms 전송 간격을 시험했고, MCU 시계 순환 조건도 통과했다.
실제 Python 키보드 실행 루프와 브라우저 상태 처리도 가상 시간 10분을 검증했다.
실물 10분 운전 또는 벽시계 시간 10분 통신 시험을 한 결과는 아니다.

확인된 수신 경합은 수정했다. 호스트 UART는 바이트 단위 polling이므로 명령 수신 중
팔 상태를 읽으면 다음 바이트를 놓칠 수 있었다. 이제 완전한 D 명령을 받은 뒤 ACK 전
한 축을 조회한다. 호스트는 ACK를 받아야 다음 명령을 보내므로 정상 왕복에서 조회와
명령 수신이 겹치지 않는다. 무응답 400ms 정지는 그대로 유지한다.

PC–젯슨 SSH 문자열 왕복 30초/599회(초기 접속 제외)는 중앙값 1.30ms,
99백분위 18.74ms, 최대 22.89ms였다. 이 측정은 모터에 접근하지 않았으며,
이동 중 Wi-Fi 음영이나 시리얼 지연을 보장하지 않는다.

남아 있는 중단 조건:

- 키보드 자동 반복의 첫 지연이 300ms보다 길면 처음 누를 때 잠깐 멈출 수 있다.
  브라우저 방식은 keydown/keyup을 써서 OS 키 반복에 의존하지 않는다.
- 브라우저 요청 200ms 초과 또는 갱신 공백 250ms, 창 전환·화면 잠금은 정지 원인이다.
  만료 후 새로고침이 필요하며 오래된 이동 입력으로 자동 재개하지 않는다.
- 호스트–STM32 명령 공백 400ms, 모터 읽기/쓰기 실패, 기존 목표·토크 변경,
  1.2초 넘게 갱신되지 않은 유지 상태는 정지 원인이다. 단발 모터 조회 실패도
  현재 후보에서는 정지를 유발한다. 이를 무시하도록 바꾸지 않았다.
- USB/전원선 빠짐, 배터리 저전압, 발열, 물체 미끄러짐은 모의 시험으로 검증하지 못했다.

촬영 시 조종 페이지를 전면에 유지하고 PC 자동 잠금·절전을 피한다. 시연용 로그 녹화는
다른 창에서 준비하되 주행 중 조종창을 전환하지 않는다. 실제 설치 후 정지 조회와
짧은 구동 검사를 통과하기 전에는 10분 무중단 운전을 검증했다고 보고하지 않는다.

## 준비 결과와 남은 실물 단계

후보는 교차 빌드와 호스트/C 모의 검사 대상으로 만들었다. 젯슨에 파일을 저장하는 작업은
시리얼 조회, 모터 활성화, 서비스 종료, STM32 리셋·설치를 수행하지 않는다.
기존 `stationary-pick` 경로도 바꾸지 않는다.

설치는 **모터 전원 OFF**, 또는 양팔·리프트·물체를 받치고 모터 전원을 유지한 상태에서
별도로 진행한다. STM32 재시작 후 기존 토크 ON/목표의 연속성을 자동으로 가정하지 않는다.
모터 전원이 이미 꺼진 상태에서는 `install.sh --motor-power-off`로 설치할 수 있다.
이 경우 전원 OFF 상태에서 INFO 응답만 확인하며, 이후 모터를 켜도 바로 바퀴를
활성화하지 않는다. 같은 펌웨어의 `hold-here`로 유지 설정을 완료하고 HOLD 검사를 통과해야 한다.
기존 팔 프로그램이 포트를 점유하고 있으면 설치기는 종료하거나 강제로 빼앗지 않고 중단한다.
이 경우 그 프로그램의 일반 종료가 팔 토크를 끄는지 먼저 확인해야 한다.

설치기는 실행 직전 받침·전원 유지 확인 인자를 요구하며, 현재 펌웨어 전체를 젯슨에
백업한 뒤 쓰기·검증·부트 저널 보존을 검사한다. 설치 중 상태가 검증된 것은 아니므로
받침을 유지하고 `check`가 통과한 후 짧은 바퀴 시험으로 진행한다.
펌웨어 원본 백업은 젯슨에 두며 PC로 복사하지 않는다.

## 실행 방법 — 설치 및 실제 검사 이후

릴리스 폴더에서 `sh control.sh status`와 `help`는 장치를 열지 않는다.
`sh control.sh check`는 INFO와 HOLD 조회만 보내고 바퀴를 켜지 않는다.

```sh
# 젯슨의 해당 릴리스에서, 설치 후 읽기 검사
sh control.sh stop-wheels
sh control.sh plan-hold

# 모터 ON, 현재 자세와 물체를 받친 상태에서 명시적으로 자세 고정
sh control.sh hold-here
sh control.sh check

# 키보드 조작: 시작 시 바퀴를 0속도로 활성화
sh control.sh keyboard
```

W/S 전후, A/D 좌우, Q/E 회전, Space 정지, X/Esc/Ctrl+C 종료.
WASDQE는 한국어 입력기 대신 영문 상태로 사용한다.

브라우저를 쓸 때는 PC에서 SSH에 `-L 18766:127.0.0.1:18766`을 추가하고
젯슨에서 `sh control.sh web`을 실행한다. 출력된 `http://127.0.0.1:18766/#...`
주소를 PC 브라우저로 연다. 서버는 루프백에만 바인딩한다.

집기·놓기 프로그램은 이 후보에서 실행할 수 없다. 분리 촬영을 끝내고 팔 동작으로
돌아갈 때는 물체를 받친 뒤 기존 팔 제어기 복귀 및 상태 확인이 필요하다.

PC에서는 프로젝트의 `sh tools/run/wheel_hold_remote.sh plan-hold`, `hold-here`, `check`,
`web`을 사용한다. `web`은 SSH 터널을 열고 화면에 조종 URL을 출력한다.
모터 OFF 상태에서는 `status`, `info`, `help`만 사용한다.

## 2026-11-09 리프트 하강 후 수정

사용자는 리프트만 내려갔다고 확인했다. v4는 속도 모드의 목표 0과 토크 ON을
높이 고정으로 인정하고 실제 리프트 위치를 지속 비교하지 않았다. v7는 이 판정을 폐기했다.
위치 모드 전환은 모터 EEPROM에 남으므로 이후 리프트 상하 이동은 기존 리프트 도구의
명시적 속도 모드 준비를 거쳐야 한다. 높이의 다회전 절대 기준을 새로 생성하지 않는다.
바퀴 통신 실패와 종료 때 발견한 왼팔 토크 OFF의 선후·원인은 이 수정만으로 확정되지 않는다.
실제 지지 없는 높이 유지 및 주행은 별도 실물 확인 전까지 검증 완료로 표시하지 않는다.
