> 이력 문서: 아래의 현재 상태·다음 순서·승인·배포 조건은 각 기록 시점의 내용이다. 최신 상태는 [현재 상태](../CURRENT_STATUS.md), 개발 방향은 [로드맵](../ROADMAP.md)을 따른다. 과거 승인으로 로봇 작업을 재개하지 않는다.

작성 기준: **2026-11-15까지의 대화와 저장소 기록**, 말미에 11월 16일 PR 정리 시점의 후속 기록 포함. 이후 실물 결과는 [현재 상태](../CURRENT_STATUS.md)에서 확인한다.

이 문서는 반복해서 겪은 문제, 임시 숫자와 보정값, 사용자와 합의한 설계, 실제 검증 범위, 남은 작업을 한곳에서 확인하기 위한 인수인계 자료다. 이 문서를 만드는 동안 로봇 조회·재시작·배포·동작은 실행하지 않았다.

**현재 작업은 사용자 요청으로 일시 중단 상태다.** 최신 베이스 후보는 승인됐지만 실제 이동하지 않았다. 리프트 1cm 상승도 아직 실행하지 않았다. 이 문서는 실행 명령이나 재개 승인이 아니다.

## 1. 읽는 기준과 현재 결론

- **실물 확인**: 실제 장치 로그 또는 사용자 관찰이 있다. 둘은 구분한다.
- **소프트웨어 확인**: 단위 검사·기록 재생·모의 실행으로 확인했다. 실물 성공을 뜻하지 않는다.
- **합의**: 사용자가 원하는 운영 방식이다. 구현·배포가 끝났다는 뜻은 아니다.
- **가설/미확정**: 가능한 설명이지만 원인이 입증되지 않았다.
- **대체됨**: 당시 사용했지만 후속 결정이나 보정으로 바뀐 내용이다.

기존 문서에는 과거 상태와 후속 기록이 함께 있다. 예를 들어 S3 문서 안의 옛 “미완료” 문구는 이후 사용자 완료 판정과 구분해야 한다. 2026-11-16 문서 정리 이후 `CURRENT_STATUS.md`는 최신 확인 상태만 유지한다. 이 문서와 나머지 이력의 앞부분을 현재 상태로 해석하지 않는다. 이 문서는 후속 기록을 우선해 정리했으며, 원본 로그는 지우지 않는다.

## 2. 사용자와 확정한 운영·제품 방향

### 2.1 개발과 실험 방식

1. 기존 텔레옵·진단·촬영·설치 도구를 먼저 활용한다. 없거나 역할이 다를 때만 새 도구를 만든다.
2. 젯슨 작업은 SSH로 진행한다. PC에서 가능한 구현·검사·지도 처리는 로컬에서 하고 검증한 묶음을 배포한다.
3. 사용자가 “시험 직전까지” 요청하면 준비·상태 확인·화면 연결까지만 한다. 반복적인 작은 실물 시험으로 임의 확장하지 않는다.
4. 매번 전원 OFF→ON을 요구하는 것을 기본 절차로 삼지 않는다. 지지 상태와 실제 작업의 영향에 맞춰 기존 승인 범위에서 진행한다.
5. 펌웨어를 바꿀 때 기존 플래시·부팅 기록과 보정값을 보존한다. 다른 개발자가 제어기를 사용하는 동안에는 소유권 충돌을 피한다. 제어기 변경 금지는 이후 사용자에 의해 해제됐다.
6. 실제 동작 전 후보 확인을 요구한 현재 S4b 실험에서는 **베이스 위치·방향·리프트 높이를 먼저 보여주고 승인받는다.** 목표가 의미 있게 바뀌면 다시 확인한다.
7. 인증 창 반복, 사소한 오류마다 전체 재시작, 로그 처리로 통신이 끊기는 흐름은 사용성 결함이다. 정상 운용에 이런 수작업이 계속 필요하면 통합 완료가 아니다.
8. GitHub 작업은 사용자 저자 정보로 처리하고 AI 공동 저자 문구를 추가하지 않기로 했다. 과거 PR 요청이 있었다는 사실과 실제 현재 PR 상태는 구분한다.

### 2.2 주행과 조작의 구분

- Home은 모델 계산과 영점의 기준이다. 중력으로 내려오는 팔을 Home에 계속 놓아야 하는 운영 자세로 취급하지 않는다.
- 실제 받침은 Aloha Mini 1 구조에 붙은 고정 가로대 등이 포함된다. 옆으로 빼낼 수 있는 독립 받침이라고 가정한 안내는 잘못이었다.
- 주행 외형은 바퀴 아래 베이스만이 아니라 **팔 아래 고정 리프트와 장착대 폭**까지 포함한다.
- 사용자는 이동할 때 팔을 접기로 했다. 따라서 접힌 팔 자체는 주행 외형 계산에서 제외하는 운영 가정이다. 아무 팔 자세에서도 통과한다는 뜻이 아니다.
- 주행 전에는 양팔·리프트 상태와 유지 토크를 확인한다. 주행 중에는 바퀴 중심으로 제어·감시하고 팔·리프트를 계속 조회하지 않는 명시적 이동 모드를 사용한다.
- 집기/리프트 작업으로 전환할 때는 정지 후 해당 장치를 새로 확인한다. 주행 중의 오래된 팔 관측을 현재 관측으로 둔갑시키지 않는다.
- 순간 표시 이상을 곧바로 전체 시스템 고장으로 처리하지 않는다. 실제 지속 고장·통신 상실·명령 만료·진행 경로 위험과 단발 이상을 구분한다.

### 2.3 지도와 생활 공간

- 지도는 보기 좋은 그림보다 **Aloha Mini 1이 실제로 통과할 수 있는지**를 표현해야 한다.
- 2D 라이다가 못 보는 탁자 상판·낮은 선반 등은 RGB-D 높이 형상으로 보완한다. 의미 이름만으로 장애물을 채우거나 지우지 않는다.
- 주요 가구는 냉장고·소파·책상·침대·탁상 등이다. 작은 선풍기나 접근 불가능한 소파 아래 바구니까지 주 지도에 각각 이름 붙일 필요는 없다. 실제 충돌 형상은 별도로 유지한다.
- 최초 지도 이후 새 물체는 임시 장애물로 본다. 새 가구를 영구 등록하는 것은 사용자 추가 매핑으로 처리한다.
- **기존 가구가 옮겨졌다면 같은 가구임을 확인하고 새 위치를 저장하며, 그 가구의 옛 점유 기여는 운용 지도에서 제거한다.** 마지막으로 확인한 위치가 재시작 뒤에도 남아야 한다.
- 이미 놓여 있는 새 장애물은 우회한다. 진행 방향으로 갑자기 들어온 가까운 장애물은 정지한다. 경로 밖의 사람이나 일시적인 점 하나로 항상 전체 정지하지 않는다.
- 배터리가 없으므로 현재는 텔레옵으로 구간별 촬영한다. 전선을 옮기며 전원이 끊기는 저장·종료·이어하기를 지원한다. 집 전체 자동 탐색 실물 검증은 배터리 도착 뒤로 미뤘다.

### 2.4 S5 첫 사용 범위

- 텍스트 대화부터 시작한다. PC 로컬 언어 모델을 사용하며 장기 목표는 전체 파이프라인의 온디바이스 최적화다.
- 한 번에 한 물체를 옮기는 작업 하나로 제한한다. 음성·복수 작업 큐·사람 손에 직접 전달은 후속 범위다.
- 목적지는 실제 놓을 가구/지지면까지 구체적으로 받는다. 생략된 목적지를 임의로 채우지 않는다.
- 전체 작업마다 대상·출발·목적지를 보여주고 실행 확인을 한 번 받는다. 내부 정상 단계마다 다시 묻는 흐름은 목표가 아니다.
- 취소는 언어 모델 응답을 기다리지 않고 기존 정지 경로로 전달한다. 언어 모델은 모터 명령을 직접 만들지 않는다.
- 지도 이름·사용자 별칭은 관측 근거와 연결한다. 애매하면 질문하며, 이름을 안다고 위치나 놓을 표면까지 검증된 것으로 취급하지 않는다.

## 3. 제어·통신·주행에서 발생한 문제

### C01. 오른팔 전체 응답 누락과 수신 오류 — 일부 수정, 근본 원인 전부 해결 아님

여러 시점에 오른팔 6개가 동시에 응답하지 않았다. 전원/케이블을 바꾸지 않고 재조회만으로 돌아온 경우, 사용자가 전원선을 다시 연결한 경우, 제어기 재시작 후에도 돌아오지 않은 경우가 모두 있었다.

- `UNAVAILABLE`을 물리 배선 고장으로 바로 해석한 것은 근거가 부족했다.
- 0x2492C 내부 기록에서 완료된 서비스 읽기의 버스 소유권이 남아 있었다. 기존 텔레옵에 있던 소유권 회수 처리가 통합 빌드에 빠진 문제가 확인됐다.
- 0x2492D에서 UART quiet·abort 성공·동일 소유자 조건을 유지하면서 회수 경로를 연결했다. 수정 전 실패/수정 후 통과하는 회귀 검사를 추가했다.
- 수정 직후에도 `RX_TIMEOUT`이 남았고, 이후 10→12→16개 순서로 응답이 돌아왔다. **소프트웨어 소유권 누락은 확인된 원인 하나지만 최초 수신 실패와 모든 재발의 원인은 미확정이다.**
- 사용자가 오류 뒤에 케이블을 다시 연결했다면, 그 뒤 초기화된 모터 설정은 최초 오류 원인의 증거로 사용할 수 없다.

### C02. 속도·moving 표시만 튀어 정상 유지/정지를 거부

바퀴 8번과 리프트 등에서 위치는 그대로인데 순간 속도 또는 움직임 표시가 나왔다. 사용자는 여러 번 실제 움직임·떨림이 없었다고 확인했다. 모드 전환 전후 위치값 변화도 실제 리프트 이동과 혼동됐다.

- 단일 표시 대신 실제 위치와 여러 표본의 정지 근거를 사용하도록 보완했다.
- 리프트 유지 완료와 keepalive 요청이 겹치는 경합에서는 같은 요청·부팅·세션의 신선한 HOLDING 응답으로 실제 완료를 확인하도록 했다. 모든 거부 응답을 성공으로 바꾼 것이 아니다.
- 최하단 원점 등록 전에 유지 관측이 안정되는 순서를 보완했다. 현재 문서상 연속 450ms 확인/최대 3초 준비 대기를 사용한다.
- 이후 이동 모드에서는 팔·리프트 반복 조회 자체를 분리했다(C07). 이는 센서 오류를 고쳤다는 뜻이 아니라 주행과 관계없는 조회 실패가 주행을 끊지 않게 한 구조 변경이다.

### C03. 짧은 전진 명령 뒤 멈추지 않음 — 실제 정지 전달 결함

사용자는 약 20cm 직진 시험에서 로봇이 오른쪽 대각선으로 계속 가고 정지되지 않아 전원을 직접 뽑았다. 이 사건은 “기준이 예민해서 정지했다”는 문제와 반대이며 별도로 다뤄야 한다.

- 기록상 boot 15/0x2491E에서 약 2.51초 동안 비영점 명령 59건이 있었다.
- 출력 스케줄에서 **아직 HAL에 전송하지 않은 예약 패킷**을 실패 완료 처리하면서 버스 소유권/고장 상태가 남았고, STOP 전송까지 막히는 경로를 확인했다.
- 0x2491F에서 미전송 예약의 취소와 실제 전송 시도의 실패를 구분하고, 예약 해제·원래 기한 유지·오류 뒤 STOP 처리를 보완했다. 실제 전송을 시도한 패킷을 무조건 재전송하는 방식은 쓰지 않았다.
- 이후 정지 확인과 실물 성공 기록이 있지만, 이 한 수정이 모든 통신 장애 상황의 정지를 보증한다는 뜻은 아니다.

근거: [S4 실험 기록](S4_PREEXPERIMENT.md)의 정지 전달·전진 수정 절.

### C04. 오른쪽 약 45° 대각선 주행 — 4륜 계산으로 확정하지 않음

로봇은 **3개 옴니 바퀴**다. 기존 텔레옵에서는 방향이 맞았으므로 그 변환을 비교 기준으로 삼았다.

- 텔레옵 직진 예시 `[-200, 200, 0]`과 당시 자율 출력 예시 `[-44, 50, -7]`는 달랐다. 자율 출력에는 지도 목표의 방향 보정 등이 포함됐다.
- 당시 약 -8°의 초기 목표 방향 차이만으로 사용자가 본 약 45° 이탈을 모두 설명할 수 없다.
- “4륜 공식을 사용했기 때문”이라는 가설은 확인되지 않았다. 정지 전달 결함과 방향 문제를 같은 원인으로 단정하지 않는다.
- 기존 3륜 변환·부호·출력 비율을 재사용하고 실제 후속 시험에서 진행 방향 정상이라는 사용자 확인을 얻었다. 이전 사건 전체의 단일 원인 규명과는 구분한다.

### C05. 시간 판정·스케줄 경계 때문에 첫 명령 거부

명령 시작 시각, 주기 경계와 시간 판정 문제로 준비/첫 이동이 거부됐다. 로컬에서 해당 조건을 재현해 보완했다. 촬영·계획에 시간이 걸렸는데 오래된 시작 시각을 재사용하는 문제도 실행 시작 시각 처리로 수정했다. 오래된 명령을 유효한 것처럼 연장하는 방식은 쓰지 않는다.

### C06. 온도 단발 급등으로 반복 정지 — 재확인 정책 수정, 표시 원인은 미확정

대표 기록은 9번 34→89°C/40ms, 8번 34→92°C/80ms, 7번 35→79°C/40ms다. 직후 정상 온도로 돌아온 사례가 있다. 이는 단발 이상값을 의심할 근거이지 독립 온도계로 실제 온도를 측정한 결과가 아니다.

- 기존 확인 정책은 85°C 초과 표시를 즉시 정지시켜 89/92°C 단발값을 구제하지 못했다. 0x24927에서 표시 크기 자체보다 최근 정상 기준과 독립된 다음 응답을 사용하도록 변경했다.
- 바퀴에 한해 최근 유효 온도가 상한보다 최소 10°C 낮고 온도만 20°C 이상 급변하면 같은 모터를 한 번 즉시 재조회한다. 최대 50ms 내 새 응답을 확인하며 이전 표본의 시각을 갱신하지 않는다.
- **70°C 상한은 유지한다.** 연속 고온, 기준 온도가 이미 상한 부근인 상승, 재조회 실패/시간 초과, 여러 필드 동시 오류는 계속 정지한다.
- 초기에는 같은 축의 1초 이내 재확인을 막았다. view-06의 780ms 간격 재발에서 이 조건 때문에 독립 재조회 없이 정지한 것을 확인했다.
- 0x2492B에서 그 1초 제한을 제거했다. 매번 새롭고 충분히 낮은 기준값이 있어야 하며, 연속 고온을 허용하는 변경은 아니다.
- 수정 후 관측 이동 성공은 확인했다. 해당 주행에서 실제 이상값이 다시 발생했는지는 별도 증명하지 않았으므로 “실물 급등 회복을 반복 검증했다”고 기록하지 않는다.

### C07. 이동 도중 팔 조회 실패가 계속 주행을 중단 — 운영 방식 변경 완료

사용자는 “이동은 바퀴만 고려하고, 팔·리프트는 시작 때 확인하고 토크만 유지하자”고 명시했다.

- 0x2492C에 바퀴 전용 이동 모드를 추가했다. 진입 전에 전체 실제 자세·토크·리프트 HOLD를 확인한다.
- 이동 중 팔·리프트 조회/동작은 분리하고, 바퀴 응답·명령 만료·호스트 heartbeat·주행 센서/경로 판단은 유지한다.
- 바퀴 정지는 scope 1로 확인한다. 이 결과는 전체 로봇 정지 증거나 집기 허가가 아니다.
- 이동 중 팔 전원 단절이나 처짐을 실시간으로 감지하는 기능은 이 모드에 없다. 토크 설정 유지와 실제 유지 상태를 계속 측정하는 것은 다르다.
- 다음 조작 전에 새 조회가 필요하다. 오른팔이 시작부터 응답하지 않는 상황을 통과시키는 변경은 아니다.

### C08. 센서 수집·영상 저장과 조종을 함께 하면 연결이 끊김

카메라/라이다 끄기 → 라이다만 → 라이다+RGB-D 수신 → 원본 영상 저장까지 켜는 비교 시험을 순서대로 진행했다. 원본 저장 없이 정상인 경우와 전체 부하에서 조회 실패가 나는 경우를 구분했다.

- 무거운 영상·지도 처리, 파일 기록, 제어 heartbeat의 실행 경로를 분리하고 제한된 큐/별도 작업 흐름을 사용했다.
- 연결 대기·다른 조종창 경고·오류 종료는 화면 세션과 실제 제어기 상태를 구분해 복구했다.
- 실패 로그와 원본을 보존하고 이어서 촬영했다. 이후 전체 센서 저장을 켠 회전·이동 정상 종료를 사용자가 확인했다.
- 원래 하드웨어 통신 문제까지 전부 부하 하나로 설명할 수는 없다.

### C09. Nav2 실패, 요청 거부, 도착 후 오류

| 문제 | 확인한 내용과 조치 |
|---|---|
| `request rejected or response mismatch` | 거부 응답의 요청·출력·상태를 잃어 원인이 감춰졌다. 설치 정책 raw 상한 100과 변환부 참조 상한 200의 불일치를 실제 코어로 재현하고 공통 비율 제한 및 원본 응답 기록을 추가했다. |
| 장애물 상자를 비용지도에서 놓침 | 높이 범위 설정을 확인하고 낮은 장애물도 포함하는 센서 층으로 보완했다. |
| 잘 가다가 `nav2_failed` | DWB 경로 자르기 거리와 local window 조합에서 변환 경로가 비는 조건 등을 확인해 수정했다. 모든 Nav2 실패를 이 원인으로 간주하지 않는다. |
| 지도 여유가 지나치게 큼 | 실제 외형, 추가 여유, 격자 오차를 중복 확장하지 않도록 정리했다. |
| Nav2 성공인데 집기 자리와 차이 | 일반 주행 도착 허용치와 집기용 끝점 검사를 구분했다. 대략 도착을 정밀 정렬 완료로 사용하지 않는다. |
| 마지막 4cm·16°에서 거의 안 움직임 | 사용자는 걸림·헛돎이 없다고 확인했다. 비영 명령의 93.2%가 raw 30 미만이었다. DWB 후보 생성의 최소 속도를 보완했으며 전송 직전에 강제로 출력을 증폭하지 않았다. |
| 도착해 보이는데 오류 문구 | 목적지 도착, 정지 확인, 전체 장치 확인을 구분해 표시해야 한다. 사용자 인상만으로 정지 proof를 만들거나 오류를 성공 처리하지 않는다. |

기존 텔레옵과 Nav2의 실제 구현을 활용한다. 3륜 변환은 유지하고 Jazzy DWB/Navfn 기반 경로·속도 후보를 평가한다. 사용자가 요청한 속도 상향은 전체 검증 없이 임의로 크게 올리는 대신, 우선 너무 작은 출력 때문에 정렬이 멈추는 문제부터 보완했다.

## 4. 모델·Home·집기 문제와 해결 범위

### G01. Home 영점과 실제 받침 자세의 혼동

- 공식 SO101 모델의 기준과 기존 제어 Home 관례를 맞추고, 한 팔씩 자세를 맞춰 영점을 저장했다.
- 각 팔은 모터 전원 OFF→ON 후 저장 보정 유지 여부를 확인했다. 이후 제어기 설치에서도 보정 해시를 보존했다.
- 영점 변경 후에는 실제 관절 범위와 단일 회전 경계를 함께 갱신했다. 가운데 값 2048만 맞추면 모든 관절 범위 문제가 없어지는 것이 아니다.
- 일부 오른팔 범위/방향은 왼팔 기준을 재사용한 설정을 포함한다. 전부 독립 실측한 것으로 기록하지 않는다.
- 새 Home 뒤 집기 위치가 개선됐지만, 과거 아래쪽을 집던 원인이 모두 Home 하나였다고 확정할 근거는 없다.
- 현재 재개에서는 팔 보정을 다시 바꾸지 않는다. 사용자는 높이 보정만 적용하라고 명시했다.

### G02. 고정 손가락을 무시한 대칭 집게 접근

SO101은 한쪽 손가락이 고정되고 반대쪽이 회전한다. 처음에는 충분히 벌리지 않고 접근해 고정 손가락이 리모컨에 먼저 걸렸다. 이후 반대로 너무 멀리 잡아 움직이는 손가락이 위에서 누르는 문제가 생겼다.

- 고정/이동 손가락의 부호 있는 접촉 위치와 벌림 형상을 따로 계산한다.
- 사용자가 **공식 STL 손가락 그대로, 별도 패드 없음**을 확인했다. 과거 패드 기준 폭 표와 STL 기준의 약 4~6mm 차이를 섞지 않는다.
- 접촉 기준은 임의의 손끝 윗면 연결선이 아니다. 모델이 정의한 접촉 단면과 양쪽 접촉점의 중간점을 사용한다. 현재 stock 모델의 단면은 손끝에서 약 6.30mm 안쪽이다.
- 그리퍼의 시각적 중심, 관절 프레임 원점, 실제 접촉 중심을 같은 점으로 설명하면 안 된다.

### G03. 얇은 물체를 기울어진 손목으로 잡음

리모컨 양옆 위치는 맞아도 손목이 기울면 안정적인 측면 접촉이 되지 않았다. 쉬운 자세와 수평에 가까운 닫힘 선을 우선하도록 후보 선정을 보완했다. 사용자는 사용성을 떨어뜨리는 지나치게 강한 일괄 제한은 원하지 않는다.

**닫힘 선이 수평인 것과 접근 방향이 수평인 것은 다르다.** 최신 후보는 닫힘 선을 수평으로 맞추면서도 도구 접근은 아래로 기울 수 있다. 5DOF에서 모든 방향을 독립적으로 지정할 수 없다.

### G04. 들었지만 무거운 쪽으로 미끄러짐

사용자는 리모컨이 들린 뒤 접촉력이 부족하고 무거운 쪽으로 기울어 떨어졌다고 관찰했다.

- 닫힘 여유를 2mm → 4mm → 마지막 요청으로 5mm로 늘렸다.
- 이것은 목표 폭보다 더 닫는 **위치 여유**다. 실제 접촉력이나 뉴턴 단위 힘을 측정·제어한 것이 아니다.
- 형상 중심 가까운 단면과 안정적인 양옆 접촉을 우선한다. RGB-D 외형 중심은 질량 중심 실측이 아니다. 내부 배터리 등으로 실제 무게중심이 다를 수 있다.
- 성공한 S3 전체 집기 기록은 4mm 설정 당시다. 마지막 5mm 변경은 별도 반복 실물 검증 대상으로 남긴다.

### G05. 손가락이 탁자를 끌어 목표까지 못 감

사용자는 목표점 자체보다, 손가락이 먼저 탁자에 닿은 상태로 앞으로 밀어 반발력 때문에 실제 접촉점이 뒤처진다고 지적했다.

- 기존 MoveIt 검사에 STL이 전혀 없었던 것은 아니다. 모델·실물 높이 차이와 실제 접근 경로 문제를 따로 봐야 했다.
- 손가락 전체 STL의 지지 평면 여유를 직접 검사하고, 먼저 목표 위쪽으로 접근한 다음 내려오는 경로를 적용했다.
- 마지막에 탁자에 닿는 것은 허용하지만, 목표에 도달하기 전에 전진하며 끄는 것은 허용하지 않는 것이 사용자 의도다.
- 물체와 탁자 높이를 함께 9.1mm 낮추는 좌표 보정만으로 손가락과 탁자 사이 여유가 늘어나지는 않는다.
- 이후 전체 집기에서 사용자는 “너무 잘 집었고 바닥에 끌리지 않았다”고 확인했다.

### G06. S3 완료 판정과 8mm 오차

전체 집기 trial-09에서 사용자 관찰로 집기·들기 성공을 확인했다. 사용자는 약 8mm 아래쪽을 잡은 것 같다고 했고, 그 오차를 기록한 채 S3 마무리를 수락했다.

- 8mm는 사용자 눈대중 관찰이며 좌표축별 실측 오차가 아니다.
- 중력/기구 처짐은 가설이다. 8mm 고정 보정값으로 모델에 더하지 않았다.
- 9번의 시도가 모두 성공한 것이 아니다. 문서의 9회 시도와 안정 성공 1회를 구분한다.
- S3 수락을 여러 물체의 반복 성공률이나 운반 성공의 증거로 사용하지 않는다.

근거: [Home 보정](../ARM_HOME_CALIBRATION.md), [S3 실물 기록](S3_STATIONARY_LAB.md).

## 5. 높이 오차와 카메라 관측

### H01. 80.91cm 대 80cm: 초기 -9.1mm 높이 보정

초기 탁자는 카메라 계산 80.91cm, 사용자 최종 실측 답변 80cm였다. 처음 답한 81cm는 정정됐다. 사용자 요청에 따라 관측 높이를 9.1mm 낮추는 보정을 적용했다.

이 값은 특정 관측의 높이 차이에서 나온 초기 보정이다. 앞뒤 거리 보정, 집게 힘, 8mm 집기 관찰 오차와 다른 값이다. 이후 높이 전용 모델을 적용하는 경로에서는 다시 빼지 않는다.

### H02. 정지한 같은 장소에서도 높이가 달라짐

거실 낮은 탁자 실측은 **31.8cm**다. 초기에 자세/관측에 따라 약 1.9cm 차이가 났다. 이동 덜컹거림이 후보였지만, 정지 후 오래 지난 영상에서도 차이가 남았다.

- 정지 후 202~212초 구간의 10장에서는 표면 중앙값 약 332.633mm, 범위 1.046mm로 안정적이지만 실측보다 14.633mm 높았다. 흔들림만으로 설명하기 어려웠다.
- 후속 분석에서 같은 정지 영역의 원시 깊이 자체가 약 13~19.5mm 달라지는 경우를 확인했다. 영상 특징점 이동은 약 2px 이내였다.
- SDK align/native depth 차이도 확인했지만, 이것만이 유일한 원인은 아니었다.
- 노출 설정 조회값과 실제 프레임 메타데이터의 노출 시간이 달랐다. 설정값만 읽고 같은 조건 촬영이라고 판단하면 안 됐다.

### H03. 여은 브랜치에서 높이 성분만 사용

사용자 파일과 `yeoeun/extrinsic-calibration`의 커밋 `836d799c3b0a7d250c03ff4caf90b3fd744d8af4`를 참고했다. `fit_best.json`의 `3 +right mount +zeros(shared)` 결과에서 **높이 계산 성분만** 사용했다.

원시 optical 점 `p`에 대한 적용식은 다음과 같다.

```text
height = [-0.021361692866709636,
          -0.6932331285434488,
          -0.7203967709309439] · p
         + 1.0100224280799914 - ground_z_m
model_id = height-2b4512f39d52caae4cae1a10
```

- 단위는 m다. 원시 optical 좌표에 한 번 적용한다.
- 팔 영점, 관절 범위, 팔 장착, 기존 XY 변환, 리프트 보정은 이 작업에서 변경하지 않았다.
- 해당 경로에서 기존 -9.1mm를 중복 차감하지 않는다.
- `SurfaceHeightModel`을 명시적으로 쓰는 호출에 적용한 범위다. 모든 지도·앱·집기 경로가 자동으로 같은 높이식을 쓰는 상태라고 주장하지 않는다.
- 단순히 31.8cm에 맞추는 추가 상수를 더하지 않았다.

### H04. 고정 노출과 정지 다중 촬영

같은 자리의 비교에서 자동 노출 모드와 고정 노출 모드에 따른 깊이 편향/변동 차이를 재현했다. 카메라 내부 알고리즘의 단일 결함까지 규명한 것은 아니다.

| 비교 조건 | 탁자 높이 중앙값 | 구간 내 범위 |
|---|---:|---:|
| 자동 노출 1 | 308.979mm | 5.644mm |
| 고정 8ms | 315.137mm | 3.017mm |
| 고정 16ms | 315.202mm | 1.294mm |
| 고정 33ms | 315.122mm | 1.369mm |
| 자동 노출 복귀 | 306.543mm | 8.858mm |

자동 노출이 항상 실패한 것은 아니다. 다만 높이를 판정하는 정지 촬영에는 **고정 16ms + 약 3초 안정화 + 여러 프레임 비교**를 사용하도록 기존 촬영 도구를 보완했다.

- 마지막 20프레임 결과: 중앙값 315.865mm, 범위 1.551mm, 사용자 실측 318mm 대비 -2.135mm.
- 독립된 고정 16ms 묶음 4개의 중앙값 범위는 약 0.810mm였다.
- 다른 바닥 영역에는 약 -10.711mm 잔차가 남았다. 탁자 한 곳의 결과를 전 공간 ±2mm 정확도로 일반화하면 안 된다.
- `capture_height_window.py`와 선택적 촬영 노출 설정을 사용하며 원래 설정을 복원한다. 모든 주행 카메라의 노출을 무조건 고정한 것이 아니다.
- 품질이 나쁜 프레임은 높이 계산에서 제외한다. 그 자체로 제어기 전체 고장을 발생시키는 정책은 아니다.

### H05. 낮은 물체가 최종 자리에서 카메라 밖으로 나감

최종 집기 자리를 카메라 시야에 억지로 맞추면 팔이 너무 멀어지고 좋지 않은 자세가 될 수 있다. 사용자는 최종 시야 조건을 제거하고 저장한 관측을 활용하기로 했다.

- `recapture_at_goal`: 도착 후 새 촬영을 전제로 하는 방식.
- `stored_target`: 마지막 정지 관측을 저장하고 실제 상대 이동/회전으로 현재 로봇 좌표를 구하는 방식. **최종 시야를 탈락 조건이나 벌점으로 사용하지 않는다.**
- `p_current = inverse(T_observed_current) * inverse(T_map_observed) * p_map`으로 변환한다. 명령한 목표 이동량이 아니라 실제 측정된 상대 변환을 사용한다.
- 과거 1.2cm 도착 잔차를 고정 보정 상수로 더하지 않는다. 그 값은 라이다 추정과 목표의 차이이지 라이다의 진실 오차가 아니다.
- 관측 이후 물체가 움직이지 않고 위치 추정이 이어져야 한다. 지도 좌표 점프·재위치추정·물체 재배치가 있으면 다시 판단해야 한다.
- 현재는 후보 계산과 상대 좌표 변환/재생을 구현했다. **저장 관측을 실제 집기 실행기까지 연결하는 작업은 남았다.** 오래된 사진의 시각을 새로 바꾸어 기존 새 촬영 계약을 통과시키지 않는다.

### H06. 카메라 시야 확대

기존 RGB 640×480 대신 1280×720을 활용하도록 로컬 촬영 경로를 보완했다. 기존 측정 내부값 기준 4:3 RGB 수평 시야는 약 54.8°, 공식 16:9 RGB 명목 수평 시야는 약 69.4°로 기록돼 있다. 수직 시야는 약 42.5°이며 이 변경으로 아래쪽 시야까지 크게 넓어지는 것은 아니다.

- 새 모드에서 실제 SDK 내부값을 읽어야 한다. 과거 내부값을 단순 비례 확대하지 않는다.
- 같은 장치·깊이 프로필·센서 간 변환을 검증하는 프로필 연결을 구현했다.
- 노출·게인·필터는 렌즈 밖 시야를 추가하지 않는다. 최소 깊이 거리 문제와 시야 문제도 별개다.
- **새 SDK 실측 프로필 수집과 젯슨 적용은 아직 하지 않았다.**

근거: [S4b 높이·정지 촬영 기록](S4B_EXECUTION_PLAN.md), [모바일 조작 설계 §14](../MOBILE_MANIPULATION_DESIGN.md).

## 6. 집기 베이스 선정: 잘 도착하는 것과 좋은 자리에 서는 것은 다름

### B01. 6DOF 후보를 5DOF 팔에 그대로 적용할 수 없음

GraspNet의 일반 6DOF 파지 후보를 생성하고 팔이 따라갈 것이라고 가정할 수 없다. 기존 정지 집기가 가능했던 이유 중 하나는 사람이 집기 좋은 베이스 자리를 미리 맞췄기 때문이다.

합의한 순서는 **관측 → 물체 형상/집을 단면 파악 → 5DOF 팔과 고정 손가락에 맞는 베이스·리프트 후보 → 실제 주행 경로 확인 → 정렬 → 새 관측 또는 저장 좌표 추적 → 실제 팔 경로와 집기**다. 후보 단계에서 IK/FK를 써 도달성을 확인하는 것과, 6DOF 최종 파지를 먼저 고정하는 것은 다르다.

### B02. 장축 접근과 비대칭 손가락 반영

사용자는 이전 목표까지는 정확히 왔지만 그 목표 자체가 잘못됐다고 지적했다. 리모컨의 중앙 좌우를 잡으려면 왼팔 도구의 접근 방향이 장축과 평행해야 했다.

- 물체 이름이 아니라 관측 형상의 장축/단면을 사용한다. 둥글거나 방향성이 약한 물체에는 임의 장축을 강제하지 않는다.
- 본체 정면을 장축과 맞추는 규칙이 아니라 **왼팔 도구 접근 방향의 수평 투영**을 장축에 맞춘다.
- 고정 손가락 기준으로 벌림·접촉을 계산한다. 양쪽이 대칭으로 벌어진다고 가정하지 않는다.
- 팔을 끝까지 뻗는 후보보다 어깨-접촉점 거리와 관절 여유가 나은 후보를 선호한다. 이는 순위 비용이며 실측 하중/힘 보증은 아니다.
- 마지막 4cm 접근의 IK와 손가락 STL-탁자 평면을 표본 검사한다. 전체 팔·물체·주변 장면의 연속 충돌 검사를 대신하지 않는다.

### B03. 최신 로컬 후보와 아직 안 한 동작

기록 묶음: `output/s4b-remote-trial-20261115/directional-alignment-05/`.

| 항목 | 최신 계산 결과 |
|---|---|
| 후보 ID | `fixed-left-0-0-60-1` |
| 지도 기준 베이스 | x=-0.201079m, y=0.660279m, yaw=0.778271rad |
| 마지막 정지 추정 위치 대비 | 앞 약 10.63cm, 오른쪽 약 6.62cm, 왼쪽 약 1.03° |
| 검토 경로 길이 | 약 13.39cm |
| 집기용 리프트 후보 | 최하단 +1cm |
| 장축 대비 수평 접근 오차 | 이전 약 17.68° → 새 후보 명목 약 0° |
| 어깨-접촉점 거리 | 이전 약 36.50cm → 약 29.13cm |
| 링크 길이 대비 신전 비율 | 약 88% → 약 70.36% |
| 접촉 폭 / 접근 벌림 | 약 46.49mm / 50.49mm |
| 접근 기울기 | 아래 방향에서 약 27.62°; 수평에서 아래로 약 62.38° |
| 후보 관절각 | 약 [-22.17, 27.38, -23.26, 58.18, -87.15]° |
| 최소 관절 한계 여유 | 약 36.82° |

이 관절각은 **계산된 집기 자세**이며 현재 실물 자세나 실행한 명령이 아니다. 공식 모델 직접 FK와 계산 결과의 일치 및 로컬 검사는 확인했지만 실물 힘·처짐·충돌 성공을 증명하지 않는다. 접근 기울기와 닫힘 선의 수평 조건을 혼동하지 않는다.

사용자는 “베이스부터” 진행을 승인했으나 식사 중이라 나중에 하자고 했다. 따라서 현재 **베이스 이동·힘 켜기·리프트 상승 모두 재개하지 않은 상태**다. 저장 RGB-D `rgbd-329` 기반 계산이며 재개 시 현재 장면과 추적 근거를 다시 연결해야 한다.

## 7. 라이다·지도·시멘틱 매핑 문제

### M01. 라이다는 도는데 데이터가 없음

- USB 어댑터 인식과 실제 라이다 데이터 수신은 다르다. 회전도 정상 패킷 수신의 증거가 아니다.
- 케이블 5핀이라는 외형만으로 데이터 정상 여부를 판단할 수 없었다.
- 기존 라이다의 무수신 원인은 완전히 확정하지 않았다. 같은 기종 교체품은 로컬에서 정상 스캔을 받았다.
- 젯슨에서는 무기한 `.flush()`/`tcdrain` 대기 경로를 확인하고 제거한 뒤 수신이 복구됐다. 하드웨어만의 문제라고 단정했던 설명을 피해야 한다.

### M02. 스캔 수신 간격이 약 0.4초씩 벌어짐

고정 2520바이트 프레임 읽기 방식이 마지막 섹터 누락 시 다음 회전까지 소모하는 문제를 확인했다. 42바이트 패킷 단위 검증·복원을 사용하고 다음 스캔 시작을 보존했다. 허용된 소수 누락은 NaN으로 남기며 이전 거리를 새 스캔인 것처럼 재사용하지 않는다.

개선 기록은 60초 동안 291스캔, 최대 간격 약 0.201263초다. 단순히 건강 기준을 느슨하게 바꿔 정상으로 만든 결과가 아니다.

### M03. 라이다 위치·뒤쪽 가림

사용자는 라이다가 앞쪽 바퀴 케이스 위의 기존 장착 위치에 고정돼 있고, 시각화한 위치/각도가 대략 맞다고 확인했다. 모델과 실물 스캔의 가림/형상을 비교해 설정한 근거를 남긴다.

- 공식 Mini 1 모델에 라이다 장착 위치가 직접 제공된 것은 아니었다.
- 현재 값은 모델·실물 관측·사용자 외관 확인을 조합한 장착 추정값이다. 독립 정밀 측량으로 보정 완료한 값이 아니다.
- 뒤쪽은 본체로 가려지므로 360° 전 방향이 열린 센서처럼 정합하면 안 된다. 실제 가시 영역/자기 가림을 반영한다.
- 리프트 최하단 등 관측 당시 설치 상태도 함께 보존한다.

### M04. 인코더 오차와 라이다 중심 위치 추정

초기 이동 기록에서 약 4.9cm·12° 차이를 논의했다. 이는 현재 모든 주행에 적용할 보정 상수가 아니다.

- 바퀴 적산값만 믿지 않고 라이다 기반 위치 추정을 주로 사용한다. 바퀴 정보는 예측·속도 등 보조 근거로 사용한다.
- 라이다가 항상 실측 정답을 제공하는 것은 아니다. 가림·특징 부족·동적 물체·지도 오차를 구분해야 한다.
- 목표 대비 마지막 추정 잔차와 실제 바닥에서 잰 도착 오차는 별도 지표다.

### M05. 3구간 중간 오류 기록을 버리면 지도에 구멍이 남음

사용자는 연결이 끊겨 복구했던 모든 구간을 사용하라고 요청했다. “오류 종료”라는 세션 상태만으로 그 구간 전체를 버리지 않는다.

- 정상 취득된 라이다·RGB-D·시각/이동 기록은 보존한다. 실제 깨진 자료와 세션 종료 오류를 구분한다.
- 끊긴 경계의 위치 관계를 정합하고 같은 포즈 그래프에 연결한다. 단순 파일 이어붙이기나 각 재시작을 원점 0으로 놓는 방법은 쓰지 않는다.
- 라이다만으로 2D 지도를 재검토한 뒤 RGB-D/시멘틱을 최종 지도 좌표에 다시 결합했다.
- 실내 영상 PC 백업은 사용자가 명시적으로 허용했다. 원본·해시 검증 전에 젯슨 원본을 지우지 않는다.
- 사용자는 최종 전체 지도 이후 젯슨 배포를 원했다. 일부 지도 생성 중에 최종 배포 완료로 처리하지 않는다.
- 젯슨 원본 정리는 요청돼 있지만, 모든 원본이 이미 삭제됐다고 이 문서에서 단정하지 않는다.

### M06. 이동 가능 영역이 실제 통과한 곳까지 막음

초기 시각화는 모든 높이 장애물을 전체 외형 회전 원으로 확장하고 격자 올림/미관측 표시까지 겹쳐 제한이 과했다.

- 높이별 공식 STL 외형을 사용하고 관측 장애물 높이와 해당 몸체 높이를 대응시켰다.
- 베이스만 사용하던 기준을 고정 리프트/장착대 폭까지 확장했다. 반대로 팔을 접고 운용한다는 합의에 따라 팔 자체는 제외했다.
- RGB-D voxel과 SLAM 격자의 원점·셀 면적을 고려하고 이중 팽창을 줄였다.
- 주황 관측 형상, 로봇 중심 제한 영역, 미관측 영역을 구분했다. 제한 영역 전체가 실제 물체인 것은 아니다.
- 최종 라이다 비교본 `navigation-2d-v1`과 RGB-D까지 합친 이동 검토본 `movement-fused-v1`을 구분한다.
- 기록된 1,096개 위치 중 207개에는 당시 검토본에서 외형/깊이 충돌 판정이 남았다. 사용자가 시각화 본을 수락한 것과 전 경로 정답 검증은 다르다.
- 녹색 위치에 가능한 방향이 하나 존재한다는 것은 그곳까지 연속 경로 또는 제자리 회전이 가능하다는 뜻이 아니다.

### M07. 주거 물체 이름과 방 이름의 자동화

- DINO/SAM에 깊이 검사와 선택적 SigLIP2 재분류를 더해 바닥을 탁자로 인식하는 사례 등을 보완했다.
- 가구 종류가 충돌하면 형상은 보존하고 이름을 미확정으로 둔다. 의미 분류 실패 때문에 실제 장애물을 지우지 않는다.
- 대표 사진 60장을 대화에서 비교한 검토는 48개 관측 조각을 가구 후보에 연결하고 주요 지도에 11개 가구를 표시했다. **상시 자동 대형 모델 서비스가 구축된 것은 아니다.**
- 화장대 등은 주변 물건에 따른 용도 추정이다. “침대가 있으니 안방”이나 개인 호칭을 자동 확정하지 않는다.
- 사용자는 별도 유료 모델/API를 보유하지 않았고 배포 제품이 아닌 개인 프로젝트라고 했다. 로컬 모델·대화 기반 검토·필요한 사용자 이름 입력을 활용하는 방향으로 진행했다.
- 이름 정확도 개선과 지도 좌표 정확도 개선을 같은 지표로 합산하지 않는다. 최종 모델의 독립 평가/선정은 아직 남아 있다.

### M08. 옮긴 탁자의 옛 장애물이 남아 겹침 판정

사용자는 실제 탁자와 5cm 이상 떨어져 있는데 외형 충돌로 막힌다고 했다. 이미 이동을 확인한 탁자의 옛 위치를 계속 남겨 두면 안 된다고 지적했다.

- 같은 가구의 기존 라이다 셀 귀속과 RGB-D 형상을 새 위치 기여로 교체하는 정책을 확정했다. 옛 위치 재촬영 전까지 복제본을 남기는 방식은 이 경우 폐기했다.
- 기존 귀속 영역이 가장자리 셀을 빠뜨리고, 서로 다른 격자의 중심점만 비교해 잔상이 남는 문제를 보완했다.
- 해당 기록에서는 기존/추가 귀속을 합치고 옛 점유 42칸 제거·새 위치 5칸 반영, 옛 탁자 귀속 잔상 0을 확인했다. 다른 점유 20,289칸은 보존했다.
- 원본 지도·이력·SQLite 백업은 남긴다. 운용 지도에서 같은 가구의 기여를 교체하는 것이지 원본 전체를 지우는 것이 아니다.
- 현재 귀속은 등록 형상의 XY 영역에 포함된 셀을 활용한다. 모든 다리의 인스턴스를 정확히 분할한 것은 아니므로 겹친 다른 물체에 대한 한계가 있다.
- 새 위치에 다른 실제 장애물/실시간 관측이 있으면 계속 막혀야 한다. 옛 탁자를 지운다는 이유로 해당 영역을 무조건 free로 만들지 않는다.

### M09. 동적 장애물과 가구 이동 실험 결과의 한계

- 미리 놓은 상자 우회 주행과 목적지 도착을 확인했지만, 중간 복구를 포함한 성공과 처음부터 무중단 성공은 구분한다.
- 사용자는 진행 범위에 상자를 넣었을 때 두 번 잘 멈췄다고 확인했다.
- 등록 탁자를 옮긴 뒤 여러 관측 이동과 새 위치 반영/후속 주행을 진행했다. 모든 가구·가림·동일 형태 중복 가구에서 검증한 것은 아니다.

## 11. 남은 일과 우선순위

### 다음 실물 재개 전에

1. 사용자의 재개 요청 후 현재 전원·지지·위치 상태와 최신 센서를 확인한다. 이번 문서 작성으로 자동 출발하지 않는다.
2. 승인된 새 베이스 후보가 현재 장면에도 유효한지 실제 Nav2 경로와 고정 리프트 외형으로 확인한다. 의미 있게 다른 목표가 필요하면 새 후보를 보여준다.
3. 베이스 이동 후 목표 대비 추정 잔차와 정지 결과를 기록한다. 리프트 +1cm는 해당 단계의 승인/준비 상태를 확인해 별도로 실행한다.
4. 넓은 RGB 설정은 실제 새 SDK 내부값을 수집해 연결한 뒤 사용한다. 기존 팔 보정은 바꾸지 않는다.

### S4b 집기 연결에서 반드시 남아 있는 것

1. 저장 관측 → 실제 상대 이동 → 현재 물체 좌표 → 5DOF 실제 팔 경로의 실행 연결을 완성한다.
2. 저장 이후 물체 이동·추적 단절·지도 좌표 점프·불확실성 증가를 다루고 재관측 기준을 정한다. 과거 사진을 새 사진처럼 처리하지 않는다.
3. 손가락 단면/탁자 평면 진단을 넘어 실제 전체 팔·물체·주변 구조의 접근/닫힘/들기/후퇴 경로를 검사한다.
4. 위치 제어 닫힘 5mm의 접촉 상태와 미끄러짐, 목표 단면 오차를 실물에서 확인한다. 힘 증가를 실제 힘 계측이라고 표현하지 않는다.
5. 이동 → 집기 → 운반 → 지정 지지면에 놓기까지 연결하고, 각 단계 실패·취소·재시작 결과를 남긴다.

### 시스템 품질과 후속 범위

- 오른팔 수신 이상 및 온도 바이트 급등의 잔여 원인 조사. 재조회 정책으로 사용성을 개선한 것과 원인 제거는 별개다.
- 장시간 센서·저장·주행 동시 운용, 통신 장애 시 STOP 전달과 실제 정지 확인의 회귀 유지.
- 다양한 물체/위치에서 베이스 선정, 가구 재식별·옛 점유 제거, 지도 위치 정확도 평가.
- 특정 탁자 외의 높이 잔차, 로봇 자세/하중에 따른 카메라·팔 처짐 평가.
- S5 실제 전체 작업 검증과 UI 연결/만료/오류 복구 흐름 정리.
- 전 구간 원본 백업 검증과 배포 산출물을 기준으로 젯슨 저장 원본 정리 여부를 확정.
- 배터리 도착 이후 집 전체 자동 탐색 매핑 실물 검증.

## 12. 다시 혼동하면 안 되는 핵심 구분

1. **전원 ON ≠ 토크 ON ≠ 실제 자세 유지 확인.**
2. **바퀴 정지 확인 ≠ 전체 로봇 정지 확인 ≠ 집기 허가.**
3. **목표까지 잘 도착함 ≠ 집기 좋은 목표를 골랐음.**
4. **라이다 추정 잔차 ≠ 실측 위치 오차 ≠ 보정 상수.**
5. **닫힘 선 수평 ≠ 도구 접근 수평 ≠ 본체 정면과 장축 일치.**
6. **형상 중심 ≠ 실제 무게중심. 닫힘 추가 mm ≠ 측정된 접촉력.**
7. **높이 -9.1mm ≠ S3 관찰 8mm ≠ 과거 전방 30mm.**
8. **이름을 잘 붙임 ≠ 지도 정합이 정확함 ≠ 그곳을 통과 가능함.**
9. **오류로 끝난 세션 ≠ 그 안의 모든 센서 원본이 무효.**
10. **모델/검사 통과 ≠ 젯슨 설치 ≠ 실물 성공 ≠ 반복 신뢰성 검증.**
