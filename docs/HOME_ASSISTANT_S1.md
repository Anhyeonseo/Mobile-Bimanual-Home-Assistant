# S1 — 공통 제어 연결

2026-10-29. **공통 펌웨어 배포와 16개 모터의 실제 읽기 응답을 확인했다. 물리 보정·동작 검증과 S1 전체 통합은 아직 남아 있다.**
계층 책임은 [시스템 설계](MOBILE_MANIPULATION_DESIGN.md#7-계층-사이-계약과-공통-제어)를 따른다.

## 이번 확인

- STM32의 기존 `mobile-base-lift-teleop-v3.1`은 921600 baud에서 INFO에 정상 응답했다.
  일반/느린 전송 3회, 기존 배포 도구로 재연결 5회, 새 진단 도구로 재연결 5회가 성공했다.
  새 도구의 5회 응답은 연결 개방을 포함해 약 4.3–4.7 ms였다. 장시간 신뢰성 시험은 아니다.
- 이 확인 전 보드 리셋·펌웨어 수정·모터 명령을 하지 않았다. 앞선 무응답과 UART 프레이밍
  오류의 원인은 확정하지 못했다. 연결이 돌아왔다는 사실을 원인 수정 완료로 기록하지 않는다.
- INFO의 모터 ID는 펌웨어 선언값이다. 실제 모터의 응답·배선·보정 확인과 구분한다.

## 전환 후 확인

모터 전원 OFF 확인 후 기준 이미지를 기록·검증하고 재시작했다. 기존 512 KiB 전체 flash 백업은 젯슨에 보관했다. 마지막 8 KiB 부팅 기록도 전환 전후 동일했다.

- HELLO: 프로토콜 v2, 펌웨어 `0x00024908`, 양팔 12축 선언 확인.
- 상태 조회 5회: 정지 래치 없음, 오류 상태 없음, 거절 프레임 0.
- 실행기: CLOSED, 제어 출력 0. 모터 송신 진단: 시작 0, 실패 0.
- 모바일 endpoint: 설정되지 않음. 실측 프로필을 넣지 않은 기준 빌드의 예상 상태.

이 확인은 펌웨어의 축 선언과 통신 검증이다. 모터 전원을 켜지 않았으므로 12개 모터가 실제로 응답했다는 뜻은 아니다. 보정 해시도 현재 조립의 물리 보정을 검증하지 않는다. 새 펌웨어는 binary 모드로 대기한다. 기존 촬영용 텔레옵 실행 명령은 현재 펌웨어에서 사용하지 않는다.

## 유지보수용 연결 검사

16개 모터를 읽은 이미지는 아래 기준 빌드에 읽기 전용 조회를 더한 `home-assistant-s1-inventory`,
식별값 `0x00024909`다. **현재는 하단의 양팔 보정 전용 이미지로 전환했다.**
조회 이미지를 사용할 때는 [장치 조회 계약과 사용법](DEVICE_INVENTORY_PROTOCOL.md)을 따른다.
기본 실행은 모터 버스를 건드리지 않고 HELLO·상태만 확인한다.
`--read-motors`를 명시해야 양팔 12개와 바퀴·리프트 4개의 예상 ID를 읽는다.

- 새 이미지 기록·검증 성공, 이전 전체 flash 백업은 젯슨에 보관, 부팅 기록 8 KiB 보존 확인.
- 새 펌웨어 HELLO 및 상태 조회 전후: 정지 래치 없음, 오류 없음, 거절 프레임 0.
- 초기 호스트 검사에서는 모터 읽기·쓰기 명령 0. 이후 전원 ON 및 실제 읽기 결과는 아래에 별도 기록한다.
- 관련 Python/C 실행 테스트 111개, 펌웨어 코어 17개 통과.
  전체 Python 검사: 1,428개 통과·2개 건너뜀, loopback 권한으로 막힌 3개는 별도 재실행 모두 통과.
  기준/조회 ARM 펌웨어 빌드 성공. 실제 모터 버스 응답 검증과는 구분한다.

조회 결과는 실패 블록과 오류를 남기며 읽지 못한 값을 `null`로 표시한다.
모터별 통신 두절을 미설치나 정상 0 위치로 처리하지 않는다. 연결이 중단되면 앞선 결과를 보존한다.
이 조회 기능은 토크·모드·목표값을 변경하지 않는다.

### 실제 장치 읽기 확인

오른팔 배선 수정 후 첫 조회는 제어기의 정지 래치 때문에 모터 읽기 전에 차단됐다.
당시 실행기 CLOSED·제어 출력 0·dispatch 시작/실패 0을 확인했으며,
정지 래치의 발생 원인은 확정하지 않았다. 사용자 모터 전원 OFF 확인 후
펌웨어를 다시 쓰지 않고 STM32만 재시작했다. 이후 호스트 상태 정상 확인과
사용자 모터 전원 ON 확인을 거쳐 아래 결과를 얻었다.

| 그룹 | 응답 ID | 읽기 결과 | 운전 모드 |
|---|---|---|---|
| 왼팔 | 왼쪽 버스 1–6 | 6/6 전체 블록 성공 | 0: 위치 |
| 바퀴 | 왼쪽 버스 7–9 | 3/3 전체 블록 성공 | 1: 속도 |
| 리프트 | 왼쪽 버스 10 | 1/1 전체 블록 성공 | 0: 위치 |
| 오른팔 | 오른쪽 버스 1–6 | 6/6 전체 블록 성공 | 0: 위치 |

모든 응답의 요청/보고 ID가 일치했다. model raw=777, baud code=0,
토크=0, 현재 속도=0, moving=0이었다. 설정 변경·토크 활성화·이동 명령은 보내지 않았다.
모터 위치·offset·설정·피드백은 개인 측정 JSON에 저장했다.
양팔의 현재 위치가 2048과 다르다는 이유만으로 자동 보정하지 않는다.
모터 레지스터 한계 0–4095도 실제 기구의 허용 범위를 보증하지 않는다.

조회 전후 정지 래치는 없었고 상태 오류도 0이었다. 재연결 때 기존 binary 모드에
ASCII 진입 문자 `P`를 보내는 경로에서 거절 프레임 카운트가 0→1 증가했다.
이 경로는 코드와 카운트 변화가 부합하나 개별 오류 사유는 프레임에 없다.
모터 조회 전후 카운트는 1로 동일했다. 따라서 거절 프레임 0이라고 기록하지 않는다.
이번 성공은 1회 읽기 검사이며 장시간 안정성·하중 유지·보정·이동 검증과 구분한다.

`tools/diagnostics/stm32_link_check.py`는 이미 식별한 구형 텔레옵 펌웨어에만 사용한다. **현재 전환된 v2 기준 펌웨어에는 사용하지 않는다.**
새 제어기와 다른 프로토콜을 자동으로 시도하지 않는다. 같은 backend 잠금과 포트 독점 정책을
사용하며, 실행 중인 제어기를 대신하거나 동시에 동작하지 않는다.

```bash
python3 tools/diagnostics/stm32_link_check.py \
  --port /dev/serial/by-id/<확인한-STM32-포트> \
  --expect-firmware mobile-base-lift-teleop-v3.1 \
  --attempts 5 --output output/home-assistant/s1/legacy-link-check.json
```

각 회차마다 포트를 열고 `INFO` 한 번만 전송한 뒤 닫는다. 첫 실패에서 중단하며
시간 초과·부분 전송·잘못된 응답을 재시도로 숨기지 않는다. `ARM`, `STOP`, 모드 전환,
임의 시리얼 명령이나 모터 설정 기능은 없다. 보고서는 이동 허가를 항상 false로 유지한다.
현재 젯슨의 도구는 `robot/releases/s1-link-check-<파일해시>/`에, 결과는
`robot/shared/diagnostics/s1/`에 보관한다. 버전별 도구와 상태 파일을 분리했다.

## 통합의 기준이 될 펌웨어

기존 dual-arm resident 구현을 다음 preset으로 고정했다.

```bash
cd firmware/stm32_g474_single_arm
cmake --preset home-assistant-s1-baseline
cmake --build --preset home-assistant-s1-baseline
```

| 항목 | 기준 |
|---|---|
| 팔 | 양팔 12축, 기존 `BIMANUAL_GRIPPER_TERMINAL_SETTLE_CANDIDATE` |
| 프로토콜 | v2, 호스트 921600 baud, 펌웨어 식별값 `0x00024908` |
| 모바일 ID | 바퀴 7/8/9, 리프트 10을 빌드에 명시. 실물 확인 전 선언값 |
| 부팅 | 기존 모터 자동 설정 비활성 설정 유지 |
| 모바일 초기화 | 실측 `MOBILE_BOARD_PROFILE_HEADER`가 없으므로 비활성 |
| 결과 | `build/s1-common-control/`의 ELF·HEX, 빌드 성공 |

**이 기준 빌드만으로 베이스·리프트가 동작하지 않는다.** 모바일 HELLO/STATUS에서
endpoint가 미연결로 보고되는 것이 이 단계의 예상 상태다. 기능을 활성화하려고
모의 프로필을 실측 프로필로 바꾸거나 기존 촬영의 넓은 관절 범위를 재사용하지 않는다.
빌드에는 기존 미사용 함수 경고가 남아 있다.

## 실물 진행 순서

1. 팔·리프트 지지와 양팔·바퀴·리프트 모터 전원 OFF를 확인한다. 젯슨·STM32 USB는 유지한다.
2. 기준 펌웨어를 전환하고 이미지 검증 후, v2 HELLO·상태만 읽는다.
   기존 텔레옵 실행 명령을 이 펌웨어에서 재사용하지 않는다.
3. 모터 전원·버스 연결 조건을 확인한 뒤 각 장치의 ID·모드·영점·설정을 읽는다.
   미설치 장치와 선언됐지만 응답하지 않는 장치를 구분한다.
4. 바퀴 환산·리프트 원점/높이/하중 유지·양팔 범위와 버스 시간 예산을 실측한다.
   팔 카메라 좌표 보정은 S2로 이어가며, 필요한 공통 프로필 증거를 채운다.
5. 같은 제어기·세션에서 정지 확인, 소유권 전환, 취소·통신 유실을 검증한 뒤 제한된 동작으로 넘어간다.

실측 기록과 배포 해시는 로컬 `output/home-assistant/s1/`에 보관한다.
현재 준비 기록은 `preparation-manifest.json`, 연결 결과는 `jetson-legacy-link-check.json`이다.
현재 전환 결과는 `deployment-status.json`, 조회 펌웨어 상태는 `inventory-host-inspection.json`에 저장했다.
이전 기준 이미지 결과 `baseline-inspection.json`은 이력으로 보존한다.
실물 진행 순서의 1–3번 중 펌웨어 연결과 실제 장치 읽기를 완료했다.
최신 측정은 `motor-inventory-20261029-002.json`, 이전 차단 상태는
`motor-inventory-20261029-001-state.json`, 재시작 후 상태는
`post-reset-host-20261029-002.json`에 보존했다.
다음은 양팔 기준 자세·방향·허용 범위, 리프트 원점/높이, 바퀴 환산의 물리 검증이다.

## 사용자와 조정한 남은 측정 범위

2026-10-29 추가 합의: 이미 한 시험을 전부 다시 요청하지 않는다. 다음은 개발 계획이며,
아직 영점 쓰기·모터 이동·리프트 기준 설정을 실행한 기록이 아니다.

- **양팔:** 사용자가 새 기준 자세를 맞추고 그 자세의 읽기값을 2048로 맞추는 방향이다.
  기존 양팔 방향·가동 범위 표를 재사용하되, 이전 영점/offset과 새 영점의 관계로 환산한다.
  기존 범위의 기준이나 현재 조립과의 관계가 불분명한 관절만 짧게 확인한다.
  `bimanual_operational_limits.c`의 양팔 표와 촬영용 다섯 자세 범위는 다른 근거다.
  과거 raw 범위를 새 영점에 그대로 복사하거나, 2048을 무조건 URDF의 0 rad로 취급하지 않는다.
- **집게:** S1에는 열림/닫힘 방향·사용 가능한 개구 범위와 명령/피드백만 필요하다.
  모든 물체에 공통인 고정 닫힘값을 정하지 않는다. 개구 폭(mm)과 모터값의 대응은 S2에서
  기하와 연결하고, 잡는 위치·방향·접근 깊이·닫힘 정도 및 파지 확인은 S3에서 구현한다.
- **리프트:** 기존 제어의 방향 설정을 출발점으로 원점, 사용할 최저/최고 높이,
  기준점 사이 높이 차이에 대응하는 엔코더 변화량을 잡는다. 소프트웨어 양수=상승 정의와
  실물 방향 확인을 혼동하지 않으며, 높이 기준을 잡는 과정에서 방향을 함께 확인한다.
  사용자는 외력을 크게 가하지 않으면 유지가 잘 되고 주로 가벼운 물체를 사용할 것이라고
  보고했다. 별도의 무거운 추 시험을 현재 단계의 선행 조건으로 추가하지 않는다.
  정상 사용 중 높이 피드백과 정지 상태 확인은 유지하며, 전원 차단 거동 검증 완료로 확대하지 않는다.
- **베이스:** 기존 바퀴 방향·배치와 텔레옵 성공을 재사용한다. 지금 모든 거리/각도를 수동으로
  재측정하도록 요구하지 않는다. 명목 기구 치수로 시작하고 LDS-01 연결 후 라이다 위치 추정과
  명령/엔코더 기록을 비교해 이동 스케일·정지 오차를 검증한다. 라이다 위치 추정과
  목표 속도→바퀴 명령 환산은 별개이므로 후자는 생략하지 않는다. 정밀 확인은 S4a와 연계한다.

사용자에게 우선 필요한 동작은 **양팔 기준 자세 맞추기**, **리프트 원점·최저/최고 위치와
그 높이 재기**다. 모터값 읽기·보존·범위 환산은 도구가 담당한다. 공통 제어와
정지/소유권 전환 검증은 그대로 S1에 남는다.

### 양팔 보정 도구 준비

`home-assistant-s1-calibration` 이미지와 `calibrate_arm_home.py`를 준비했다.
현재 양팔 배선을 유지하면서 한 팔씩 선택하고, 기존 왼팔 보정 절차의 백업·자세 안정성·
중복 쓰기 차단을 재사용한다. [보정 절차](ARM_HOME_CALIBRATION.md)를 따른다.
관련 실행 테스트 86개, 전체 Python 1,448개 통과·2개 건너뜀(소켓 권한 제한 3개는 별도 통과),
기존 공통 조회/새 보정 ARM 빌드 성공.
재연결 당시 공통 제어기의 정지 래치가 있어 모터 읽기 전에 차단된 상태도 보존했다.
이후 사용자 모터 전원 OFF 확인을 받아 보정 이미지를 기록하고 이미지 검증·재시작을 완료했다.
기존 전체 flash 512 KiB는 젯슨에만 보존했고, 부팅 기록 8 KiB가 동일함을 확인했다.
현재 식별값은 `arm-calibration-v1`이며 `LEFT INFO`/`RIGHT INFO` 모두 해당 팔과
ID 1–6, `motion_enabled=false`, 보정 전 `consumed_mask=0`으로 응답했다.
사용자가 양팔 Home 자세를 맞춘 뒤 왼팔·오른팔 순서로 각 6개 모터의 보정 전 값을 백업하고
2048 기준 보정을 수행했다. 양팔 12개 모두 최종 읽기값 2047–2048, 토크 OFF이며,
오프셋 외 EEPROM 값이 유지됨을 확인했다. 이동 명령은 보내지 않았다.
**사용자 모터 전원 재인가 후 양팔 12개 모두 보정 EEPROM 일치와 토크 OFF를 확인했다.**
읽기값도 2047–2048로 유지됐다. 영구 저장 검증 근거는
`left-home-persistence-20261029-001.json`, `right-home-persistence-20261029-001.json`이다.
기존 런타임 관절 범위는 새 오프셋에 맞춰
재산출·검증해야 한다. 현 보정 이미지에서는 이전 v2 진단/텔레옵 명령을 실행하지 않는다.
보정 근거는 `left-home-centered-20261029-001.json`, `right-home-centered-20261029-001.json`이다.
배포 근거는 `arm-home-host-inspection.json`, 상태는 `deployment-status.json`이다.

양팔 새 Home 기준의 조건부 범위 환산과 검증 도구까지 준비했다. 실제 실행용 범위 반영은

오른팔 몸통 회전은 조건부 환산 범위에 새 Home이 포함되지 않는다.
사용자는 재조립 관절을 기억하지 못하며 범위 확정을 뒤로 미루기로 했다. 상위 소프트웨어 개발은 계속한다.

### 관절 범위 보류와 역방향 회전 요구

2026-10-29 사용자는 좁은 예전 범위 때문에 개발이 막히는 것을 원하지 않으며,
가까운 목표에 반대 방향으로 한 바퀴 가까이 도는 동작을 특히 방지하도록 요청했다.
관절 범위 확정은 보류한다. 자연어·작업 실행·인지·지도 개발은 모의 실행/기록 재생으로
진행할 수 있고 관절 범위 검증 완료를 선행 조건으로 두지 않는다. S1 실물 구동 완료와는 구분한다.
현재 펌웨어는 계속 보정 전용이며 실물 무제한 구동은 활성화하지 않았다.

기존 연속 좌표 계산에 200→500(+300), 500→200(-300), 4090→10(+16),
10→4090(-16), 4095↔0, 같은 위치, 정확히 반 바퀴의 모호성 거부 회귀 검사를 추가했다.
허용되지 않은 가까운 경로를 다른 한 바퀴 경로로 자동 치환하지 않는 검사도 통과했다.
이는 좌표 계산 검증이며, 실제 서보가 4095↔0 목표 명령을 어떤 경로로 수행하는지는
아직 검증하지 않았다. 기존 궤적 실행기는 명시된 연속 각도 경로를 실행하므로 이 테스트가
모든 입력 궤적을 자동 최단 경로로 바꾼다는 뜻은 아니다.
다음 실제 구동 경로에서는 시작 피드백에 맞춘 연속 목표와 요청하지 않은 큰 회전의 사전 거부,
속도/한 번의 이동량 제한 및 통신 유실 정지를 함께 확인해야 한다.

기존 통합 모의 작업 실행도 다시 성공했고 실제 모터 명령은 0회였다.
근거: `output/home-assistant/s1/deferred-range-software-demo.json`.

펌웨어의 연속 좌표 범위/목표 변환에 연결했다. 새 검증 이미지는 빌드했지만 배포하지 않았고,

### 2026-10-29 작업 범위 변경: 리프트 실측 우선

사용자 결정으로 양팔 실제 구동(1번), 베이스 실제 구동(3번), 통합 정지·취소·통신
단절의 실물 시험은 미룬다. 해당 항목은 소프트웨어 모의 검증으로 개발을 계속하며,
실물 검증 완료로 표시하지 않는다. 현재 실물 작업은 **리프트 기준점·최저/최고 높이와
높이 환산 실측**이다. 사용자는 리프트를 손으로 조절할 수 있다고 확인했다.

`home-assistant-s1-lift-measurement`는 기존 읽기 전용 점검 이미지에 `LIFT` 조회를
추가한다. ID 10만 읽으며, 부팅 시 모터 통신·토크 변경·이동·EEPROM 쓰기를 하지 않는다.
하위 UART 전송 허용 목록도 모든 모터 쓰기를 거부한다. 기존 팔 보정 이미지에서 전환할
때는 모터 전원 OFF를 확인한 뒤 제어기를 재시작한다. 파일 준비와 실제 플래시는 구분한다.

측정 도구는 `tools/run/measure_lift_range.py`이며 다음 순서다.

1. 전원 재인가 후 ID 10의 모델·모드·토크 OFF를 읽어서 확인하고 연속 기록을 시작한다.
2. 사용할 최저 위치에서 멈춘 뒤 `low`를 기록한다. 바닥부터 리프트 상판의 한 지점까지
   높이를 잰다. 이 위치를 상대 높이 0으로 사용한다. 기계적 끝에 힘을 줄 필요는 없다.
3. 천천히 사용할 최고 위치로 올린 뒤 `high`를 기록하고, 같은 지점의 바닥 기준 높이를 잰다.
   여러 회전의 엔코더 변화량을 누적하므로 두 위치 사이 기록을 중단하면 안 된다.
4. 원하면 같은 최저 위치로 돌아와 `return`을 기록하고 `finish`로 종료한다.
   정지 상태 0.4초 이상·8 raw 이내 흔들림을 확인한 표식만 채택한다.
5. `finalize`는 원본 기록 해시와 모든 표식을 다시 검증한 뒤 높이 차이/엔코더 변화량으로
   방향과 1회전당 높이를 산출한다. 네트워크나 모터에는 접근하지 않는다.

0.5초 초과 샘플 공백, 제어기 재시작, 256 raw 초과 한 번의 변화, 토크 ON,
잘못된 모터 응답은 기록을 무효로 처리한다. 이는 느린 수동 이동을 전제로 한 연속성
검사이며 샘플 사이 관측되지 않은 고속 다회전을 보증하는 장치는 아니다.
실측 결과는 자동 구동 권한을 부여하지 않으며, 현재 점검 이미지로 리프트가 움직이지 않는다.
최저 기준점 설정은 이번 측정 세션 기준이다. 전원 재인가 이후 절대 높이 복원이나 자동
원점 복귀가 검증된 것은 아니며, 기존 자동 원점 찾기 구현을 실물에서 실행하지 않는다.

준비 검증: 새 측정 도구와 기존 점검/휠 유지보수 회귀 122개 통과, 양팔·모바일·리프트·
정지/소유권 관련 소프트웨어 검사 178개 통과, 펌웨어 공통 코어 17개 통과.
집기 요청의 모의 실행도 성공했으며 하드웨어 명령은 0회다. 물리 엔진에서의 충돌·마찰
검증이나 실제 정지 성능 측정으로 확대 해석하지 않는다.


리프트 전환 실행: 사용자 모터 전원 OFF 확인 후 읽기 전용 이미지를 기록·검증하고
STM32를 재시작했다. 현재 식별값은 `mobile-bus-inspection-v2`,
`lift_read_supported=true`, `motion_enabled=false`다. 이전 팔 보정 이미지는 더 이상
활성 상태가 아니다. 이전 전체 플래시는 젯슨에만 백업했고 부팅 기록 8 KiB 보존을
확인했다. 이번 전환 후에는 INFO만 조회했으며 모터 읽기/쓰기 모두 0회다.
근거: `output/home-assistant/s1/lift-reader-host-inspection.json`.
다음은 모터 전원 재인가 후 ID 10 토크 OFF 확인과 수동 높이 측정이다.


리프트 수동 측정 중 읽기 검사가 두 차례 실패했다. 첫 도구가 거부한 응답 자체를 보존하지
않아 근본 원인은 아직 확정할 수 없다. 해당 두 기록은 무효로 보존했다. 정지 후에는
리프트 응답/토크 OFF가 정상으로 돌아왔다. 사용자가 측정한 상판 높이는 최저 27 cm,
최고 89 cm(차이 62 cm)이며, 엔코더-높이 환산은 연속 측정 완료 전까지 미확정이다.

호스트 도구만 갱신했다. 모든 거부 응답을 저장하며, 정상 정체성에서 일부 읽기값이 -1인
경우나 분류된 응답 누락에만 1회 즉시 재조회를 허용한다. 다음 정상 샘플도 기존 시간
0.5초/변화량 256 raw 기준을 통과해야 한다. 연속 실패, 실제 토크/모드 변경, 모호한
오류는 중단한다. 복구 후 표식의 정지 확인 구간은 다시 수집한다. 원본 재생 검증에도
같은 규칙을 적용한다. 도구는 최고→최저 순서도 지원하며 펌웨어/모터 설정은 바꾸지 않았다.
관련 도구·통신 테스트 36개 통과. 실제 이동 중 재조회 복구 여부는 아직 확인 전이다.


세 번째 기록에서는 실제 거부 응답을 보존했다.읽기 실패는 `RX_TIMEOUT`,
`identity_hal_status=3`, 수신 바이트 0이었다. 호스트 재조회 분류가 HAL_TIMEOUT(3)을
빠뜨리고 HAL_BUSY(2)를 포함한 오류를 수정했다. 실제 응답을 테스트 fixture로 보존하고
정상 재조회 복구·시간/변화량 초과·연속 실패 거부 및 원본 재생 검사를 포함해 38개 통과.
이는 호스트 오류 분류 수정이며 모터 통신 시간 초과 자체의 원인 해결을 뜻하지 않는다.
펌웨어 변경 없이 호스트 도구만 갱신했다. 4번째 기록에서 최저 표식은 raw 3897로
첫 최저 3132와 달라 현재 물리 높이를 재확인하기 전 27 cm를 자동 부여하지 않는다.

사용자는 이전보다 의도적으로 더 내려 현재 상판 높이가 26 cm라고 확인했으며,
이 위치를 새 최저 기준으로 선택했다. 4번째 기록의 raw 3897 표식에 260 mm를 연결했다.
기존 270 mm 최저 기준은 이 측정에 재사용하지 않는다. 최고 표식과 연속 환산은 아직 미완료다.

4번째 기록도 연속 RX_TIMEOUT으로 중단됐고 사용자가 상승 중 STM 연결선이 빠졌다고
알렸다. 이 기록은 환산에 사용하지 않는다. 재연결 후 5회 정상 응답·토크 OFF 확인 뒤
5번째 기록을 현재 최고 위치(raw 1979)에서 시작했다. 이전 최고 raw 2690과 달라
이전 89 cm를 자동 적용하지 않고 현재 최고 높이를 확인한다. 최저 선택값은 26 cm다.


사용자는 새 최고 높이를 90 cm로 확인했다(선택 최저 26 cm, 차이 64 cm).
다섯 번째 하강 기록도 중단됐다. 마지막 정상 상대값은 36 raw이며, 이어 응답 헤더 거부
(수신 9바이트), UART 오류 4(`HAL_UART_ERROR_FE`, 프레임 오류)가 연속 관측됐다.
STM32의 호스트 응답 자체는 도착했고 정지 후 ID 10은 raw 3947·토크 OFF로 10회 정상
응답했다. 이것만으로 케이블·전원·수신 타이밍 중 어느 원인인지 확정할 수 없다.
더 큰 재시도/연속성 제한으로 오류를 숨기지 않았고 전체 높이 반복 측정을 중단했다.
원점의 선택 높이와 두 높이 차이는 알려졌으나 엔코더 높이 환산·실물 S1 완료는 아니다.

배선 고정 후 짧은 수동 이동 통신 검사는 통과했다. 약 128초 동안 1,995개 표본에서
읽기 실패 0회, 최대 간격 0.097초, 최대 한 번의 변화 86 raw였다. 중간 상대값은

전체 이동 범위나 높이 환산 완료·하드웨어 원인 확정으로 확대하지 않는다.
근거: `output/home-assistant/s1/lift-short-check-result-20261029-001.json`.


여섯 번째 전체 상승 기록 역시 UART 프레임 오류로 중단됐다. 마지막 정상 raw는
1857, 정지 후 재조회는 2025로 달라 끝 위치를 이전 기록에 붙여 환산하지 않았다.
짧은 구간 통과가 전체 이동의 통신 안정성을 입증하지는 못했다. 전체 높이 반복을 중단하고
