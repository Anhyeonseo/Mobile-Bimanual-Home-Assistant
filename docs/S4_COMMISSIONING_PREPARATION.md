# S4 실물 조작 전 준비 기록

2026-11-12 1차 준비 기록. 사용자가 젯슨·라이다·팔 전원 ON을 확인하고, 승인 질문 없이 직접 조작이 필요한 단계 전까지 진행하도록 요청했다. 소스와 검사 도구를 젯슨에 준비했다. 이 1차 준비에서는 모터 명령, 제어기 리셋, 펌웨어 설치를 하지 않았다. **이후 사용자의 관리자 인증으로 조회용 제어기를 설치한 결과는 문서 마지막에 별도로 기록했다. 주행·SLAM 실물 완료는 아니다.**

## 준비한 것

- 기존 `mobile-bus-inspection-v2`에 `WHEELS` 조회를 추가했다. ID 7/8/9의 위치·속도를 한 블록에서 읽고 각 읽기의 MCU 시작/종료 시각과 순번을 남긴다. 부팅 중 모터 접근은 없으며, HAL의 모든 송신 경로에서 쓰기는 계속 차단한다. 새 허용 읽기는 바퀴 ID의 56번 레지스터 4바이트뿐이다. 팔과 리프트 구동 기능을 넣지 않았다.
- 기존 `probe_mobile_bus.py`가 INFO의 기능 선언과 SCAN의 기기·속도 모드·토크 OFF를 확인한 뒤 1–60초 JSONL을 기록한다. 초기 장치 목록과 완료된 표본을 즉시 보존한다. 부분 전송·읽기 오류·순번 변경은 재시도하거나 정상 0으로 바꾸지 않는다.
- `analyze_wheel_capture.py`는 저장된 엔코더 변화와 보고 속도를 비교한다. 엔코더 wrap, 시각 간격, 순번·호스트 재시작, 양방향 이동량과 분산을 검사하고 환산 **후보**만 출력한다. 정지 데이터로 환산값을 만들지 않는다. 엔코더 기준 속도 단위 확인과 명령 이득·실제 바닥 이동 스케일은 별개다.
- `prepare_s4_commissioning.py`는 공식 CAD와 기존 텔레옵의 ID 7=왼쪽, 8=오른쪽, 9=앞쪽·방향 기록을 재사용한다. 원본 STL의 바퀴 접촉면을 사용한 명목 반경은 약 49.50mm다. 실제 바닥 기준 높이 보정에서 나타난 약 20.70mm 차이를 바퀴 반경에 더하지 않았다. 출력은 검토용이며 실제 반경·배치·명령 환산을 수락하지 않는다.
- 주행 좌표 트리는 `base_footprint → base_link → 센서`로 준비했다. 기존 실제 피드백 주행 어댑터의 `odom → base_footprint`와 부모가 충돌하지 않는다. 관측 전용 트리와 카메라/라이다의 상대 위치는 같다. 실제 바퀴 입력 없이 odom/map 변환을 발행하지 않는다.
- 실제 1280×720 원본 깊이를 기존 주행 깊이 투영 계산으로 검사하는 도구를 추가했다. 최신 정지 캡처에서 유효 깊이점 833,444개, 라이다 측정면보다 5cm 이상 높은 점 494,312개, 해당 XY 격자 106칸(5cm)을 관측했다. 빈 공간 판정·실시간 지도 갱신·주행 허용으로 쓰지 않는다. 자세가 변할 때 가려지는 구역과 이동 중 성능은 별도 검증이다.

## 라이다 시각 수정과 검증

공식 [LaserScan 계약](https://github.com/ros2/common_interfaces/blob/jazzy/sensor_msgs/msg/LaserScan.msg)은 배열 첫 점의 관측 시각과 점별 시각 간격을 정의한다. 이 드라이버의 증가하는 각도 배열은 실제 수신 순서와 반대다. 기존 양수 `time_increment`와 발행 시각 조합을 유지하면 먼저 받은 점을 나중 시각으로 해석하게 된다.

각도·거리 배열과 장착 방향은 유지하고 점별 간격을 음수로 바꿨다. 헤더는 마지막 유효 패킷 수신에서 직렬 전송 시간(42바이트, 8N1, 230400 baud)을 뺀 **호스트 추정 시각**이다. 마지막 패킷 누락 시 RPM과 마지막 섹터 번호로 해당 회전의 시각을 추정하고 다음 회전의 수신 시각을 대신 쓰지 않는다. 오래되거나 미래인 추정은 거부한다. 센서 처리·USB 지연을 직접 측정한 값은 아니므로 하드웨어 동기화나 이동 중 왜곡 보정 완료로 표시하지 않는다.

## 준비된 실행 순서

1. **관리자 인증 후 조회용 제어기 설치.** 현재 `sudo -n`은 비밀번호가 필요하고 ST-Link USB 쓰기 권한도 관리자에게 있다. 사용자를 호출하지 말라는 요청에 따라 인증 창을 새로 띄우거나 설치하지 않았다. 준비된 `s4-inspection-4e8a1c9c6e02`는 S4 주행 펌웨어가 아니라 읽기 전용 유지보수 이미지다. 설치 전 양팔 지지와 최하단/고정 리프트를 유지하고, 기존 포트 소유자가 없어야 한다. 기존 512KiB 전체 백업·이미지 검증·마지막 8KiB 부팅 기록 보존 절차를 재사용한다. 인증이 실패하면 설치 로그 디렉터리를 선점하지 않는다. 전원 유지 설치 옵션을 지원하며 불필요한 OFF→ON을 요구하지 않는다.
2. **정지 상태의 실제 바퀴/리프트 조회.** INFO·SCAN과 짧은 WHEELS 기록으로 응답·모드·시각 예산을 확인한다. 지금 설치된 S3 `0x00024911`에 이 명령을 보내지 않는다. 현재 S3는 정지 래치가 있고 mobile endpoint는 미연결이다.
3. **사용자가 현장을 확인하는 이동 측정.** 바퀴 방향, 보고 속도와 엔코더 관계, 명령 속도 이득, 라이다 이동량과 바퀴 odometry, 바닥 제동·미끄러짐, 팔·리프트 유지 상태를 확인한다. 명목 프로필이나 정지 시각 자료로 이 단계를 대체하지 않는다.
4. **실측 프로필과 앱 연결.** 기존 `prepare_mobile_profile.py`, 공통 제어기, `build_guarded_navigation` 및 작업 실행기를 사용한다. 실제 센서·모터·위치 추정·하중 유지 입력을 확인한 뒤 앱의 자동 탐색을 연결한다. 현재 앱은 모의 입력으로 동작하며 실제 지도 만들기 버튼으로 승격하지 않았다.
5. **실제 집 검증.** 방 매핑, 가구 이동 반영, 저장 후 정상 OS 종료·전원 재연결·위치 재추정·이어하기, 빈 로봇/하중 주행 및 도착 후 집기·놓기를 확인한다. 합성 지도 저장 성공을 실제 전원 차단 시험으로 합산하지 않는다.

재현 가능한 준비 명령:

```bash
python3 tools/setup/prepare_s4_commissioning.py --output output/s4-review-new
cmake --preset home-assistant-s1-lift-measurement -S firmware/stm32_g474_single_arm
cmake --build build/s1-lift-measurement -j 4
python3 tools/setup/package_stationary_pick.py --stage s4-inspection --output output/s4-inspection-new
```

조회 이미지 설치와 식별 확인 **이후** 사용할 기존 도구:

```bash
python3 tools/run/probe_mobile_bus.py --port /dev/serial/by-id/usb-STMicroelectronics_STLINK-V3_005100393235511438363730-if02 --scan
python3 tools/run/probe_mobile_bus.py --port /dev/serial/by-id/usb-STMicroelectronics_STLINK-V3_005100393235511438363730-if02 --sample-wheels-seconds 10 --output wheel-samples-new.jsonl
python3 tools/diagnostics/analyze_wheel_capture.py --capture wheel-samples-new.jsonl --output wheel-scale-review-new.json
```

정지 캡처는 정상 응답과 시각 확인용이다. 환산 후보를 얻으려고 토크를 켜거나 자동으로 바퀴를 돌리는 기능은 없다. 향후 실제 이동 계측은 사용자 현장 조작 조건을 갖춘 뒤 별도로 진행한다.

## 후속 설치와 실제 조회 완료 — 2026-11-12

사용자가 관리자 인증과 조회용 제어기 설치를 명시적으로 요청했다. PC 비공개 비밀번호 창과 SSH로 기존 설치 스크립트를 실행했다. 모터 전원은 유지했고, 기존에 확인한 양팔 지지·리프트 최하단 조건을 사용했다. 비밀번호를 파일이나 채팅에 저장하지 않았다.

`s4-inspection-4e8a1c9c6e02` 설치와 이미지 검증이 완료됐다. 기존 STM32 전체 524,288바이트 백업 SHA256은 `d3cf7e9a3d84d2b32ee6816cb135e52360b33394ba9105cd8379ad283be30e88`이며, 마지막 8,192바이트 부팅 기록 보존도 확인했다. 원본 백업은 젯슨의 `shared/diagnostics/s4-inspection/s4-inspection-4e8a1c9c6e02/`에 있다. 기존 S3 소스 릴리스는 남아 있지만 **현재 STM32는 S3 집기 제어기가 아니라 읽기 전용 유지보수 이미지**다. 모터 쓰기·동작 명령은 보내지 않았다.

설치 전 왼팔 6축·바퀴 3개·리프트는 응답했고 토크 OFF였다. 오른팔 6축은 모두 수신 시간 초과로 상태 조회가 실패했다. 따라서 전체 양팔 사전 검사 통과로 기록하지 않는다. 새 조회 이미지는 오른팔 버스를 사용하지 않으므로 설치 후 오른팔 복구 여부는 확인할 수 없다. 통신 상태인지 배선·전원 문제인지는 아직 알 수 없으며, 팔이나 베이스 구동 전에 적절한 양팔 조회 이미지에서 다시 확인해야 한다.

바퀴 7/9의 위치·보고 속도는 일정/0이었다. **바퀴 8은 위치 범위가 1671–1672(1 count)인데, 1,288개 중 50개 표본에서 속도 ±50 raw가 관측됐다.** 이 값을 임의로 0으로 만들거나 정지 속도 검사를 완화하지 않았다. 환산 단위·원인이 미확정이므로 실제 바퀴 이동과 비교해야 한다. 정지 자료에서 속도 환산·명령 이득 후보는 생성되지 않았다.

첫 동시 센서 검사에서는 새 RGB에 이전 깊이 노출을 재사용한 프레임 쌍 1개 때문에 시각 증가 조건이 실패했다. 원본 실패 기록을 보존하고 기존 `Capture.next_frame`을 보완했다. 연속 수신에서 어느 한 스트림의 번호·시각이 반복되면 기존 제한 시간 안에서 다음 새 쌍을 기다리며 제외 횟수를 기록한다. 시각 역행·프레임 번호 리셋·오래된 노출은 여전히 오류다. 수신 시각으로 노출을 바꾸거나 신선도·50ms 관절 연계 제한을 넓히지 않았다. 수정 후 실제 중복 깊이 1개를 제외하는 동작과 전체 동시 검사를 확인했다. 관련 검사 106개, 카메라 소비자 회귀 123개가 통과했다. 호스트 프로그램만 갱신했고 펌웨어는 재설치하지 않았다.

다음 단계는 오른팔 상태 재확인과 사용자가 현장에서 바퀴를 양방향으로 움직이는 측정이다. 이어서 바닥 이동거리·제동·미끄러짐, 공통 제어기와 앱 연결, 실제 방 지도와 전원 재연결 후 이어하기를 검증한다. 현재 이미지로 자동 주행이나 집기를 실행하지 않는다.

## 오른팔 복구 관측과 바퀴 속도 재조회 — 2026-11-12

사용자가 STM32를 직접 리셋한 뒤 기존 조회 이미지로 다시 10초 기록했다. 바퀴·리프트 응답과 토크 OFF는 정상이었고, 8번의 위치 1671–1672 및 간헐적 속도 ±50은 그대로였다. 리셋만으로 없어지는 현상이 아니었다.

사용자 관리자 인증 후 `s4-inspection-4b60ea01f357`을 설치했다. 기존 전체 524,288바이트 백업 SHA256은 `420c32a6605f5c78759cd292dd89653f1583f8266d571b159a9bf96a0f0c2561`이며 이미지와 8,192바이트 부팅 기록 보존을 검증했다. 관련 Python·네이티브 송신 차단·공유 조회·패키징 검사 74개가 통과했다. 이번 작업에서도 모터 쓰기 명령은 0이다.

### 기존 텔레옵 기준 재사용

사용자가 기존 텔레옵 성공을 상기시킨 뒤 기존 구현과 S1 결정을 대조했다. `HOME_ASSISTANT_S1.md`의 베이스 방침은 이미 바퀴 방향·배치·텔레옵 성공을 재사용하고 LDS-01을 연결한 실제 바닥 이동에서 명령·엔코더와 비교하도록 정하고 있었다. 공중 받침 요청은 철회한다. 다음은 기존 텔레옵의 키보드/웹 조작과 현재 자세 유지·정지 처리를 재사용해 바닥에서 짧게 이동하며 S4에 필요한 수치만 확보하는 경로다. 장치 포트 소유자는 하나를 유지하고, 수신 자료를 얻으려고 별도 직렬 제어기를 동시에 열지 않는다.

`mobile-base-hold-teleop-v7`의 `wait_stopped`와 `WheelSetup_Plan`에는 이번과 같은 속도 ±50 보고가 이미 반영돼 있다. 목표 속도 0·토크 OFF, 속도 크기 ≤50, 연속 400ms 이상 엔코더 범위 ≤8 count를 함께 요구한다. 큰 속도·위치 변화·조회 실패는 거부한다. 이번 8번의 10초 기록(목표 속도·토크 0, 속도 크기 ≤50, 위치 범위 1 count)은 이 기존 기준 범위에 들어간다. **새로 임계값을 넓히거나 원본 속도를 0으로 바꾸지 않는다.** 따라서 이번 속도 표시는 별도 고장 수리나 공중 검사를 선행해야 하는 새 차단 사유로 취급하지 않는다. 센서의 물리적 원인을 확정하거나 새 자율 주행 제어기의 정지를 검증했다는 뜻은 아니다.

현재 STM32는 여전히 조회 이미지다. 기존 텔레옵으로 전환할 때 현재 양팔·리프트 상태를 다시 읽고 유지 설정·정지 확인을 통과해야 한다. 과거 성공을 현재의 유지 상태로 대신하지 않으며, 실제 바닥 이동과 SLAM은 아직 실행하지 않았다.

종료한 뒤 새 프로세스에 복원했으며 지도 셀이 일치했다. 이는 실제 전원 재연결이나
로봇 위치 이동 뒤 재위치 추정의 실물 통과를 뜻하지 않는다.

직접 채택된 자세 시각을 제외한 134개 스캔의 장애물 셀 중심까지 거리는 중앙값
2.23cm, 90백분위 3.78cm였다. 같은 센서 자료를 이용한 내부 일치도이지 외부 실측
정확도가 아니다. 비교 종료 시 바퀴와 SLAM은 위치 약 4.95cm·회전 약 12.0° 차이가
남았다. 이 짧고 회전 위주인 기록만으로 바퀴 반지름·속도 비율을 자동 보정하지 않았다.

상단 D415 원본 중 자세 범위 안의 70프레임을 8픽셀 간격 검토용 투영으로 살폈다.
라이다 평면 위 형상이 평면 지도에서 빈 곳으로 표시된 584셀에 관측됐다. 원본은 모두
유지한다. 이는 높이 정보 보완의 관측 근거이며, 자기 몸체 제거·움직임 보정·최적화된
최종 자세 검증 전이므로 실제 장애물층에 쓰거나 기존 장애물을 지우지 않았다.
가구 이름이나 RGB 인식 결과를 임의로 만들지 않았다.

재사용한 도구:
- `analyze_wheel_capture.py --sensor-capture ... --mapping-output ...`: 인코더/스캔 비교 및 원본 무결성 검사.
- `check_slam_replay.py --recorded-capture ... --teleop ...`: 실제 SLAM 재생, 그래프 저장/프로세스 재시작 복원.
- `review_s4_sensor_capture.py --slam-review ... --trajectory-review ...`: 지도 내부 일치도와 상단 깊이 검토 그림.

다음 실물 입력은 충분한 공간·전원선 여유에서 시작점을 표시하고, 0.5~1m 전후·좌우
이동 및 느린 양방향 회전을 포함해 시작점 근처로 돌아오는 수집이다. 가능한 실제 이동
거리를 함께 기록해야 한다. 현재 모터 전원 재인가가 선행 조건은 아니며, 새 조종 시작은
사용자가 한다. 그 전까지 분석 결과를 실물 보정값이나 자율 주행 허가로 쓰지 않는다.
요약: `config/home_assistant/s4_recorded_mapping.observed.json`.

검증: 관련 Python 검사 66개 통과. 최종 실제 기록 재생에서 회전 처리 옵션이
실제 ROS 파라미터로 true인 것을 확인했고, 두 SLAM 프로세스 정상 종료와 동일 지도
복원을 재확인했다. 기존 합성 스캔의 음수 광선 시각·실제 SLAM·높이 지도·체크포인트·
지도 재발행 검사도 통과했다. 합성 높이 지도 통과를 실물 높이 지도 수락과 혼동하지 않는다.

## 라이다 중심 위치 추정과 저장 지도 재생 검증 (2026-11-12)

위치 추정의 기준은 지도와 라이다의 정합으로 잡는다. 지도 작성 중에는 SLAM이,
저장된 지도를 사용할 때에는 AMCL이 `map → odom`을 보정한다. 바퀴 인코더는
`odom → base_link`의 연속적인 단기 움직임 예측에 유지한다. 기존 4.95cm·12°는
두 추정의 차이이며, 실측 오차나 그대로 적용할 보정값이 아니다. 인코더와의 일치나
완전한 바퀴 보정을 다음 수동 지도 시험의 선행 조건으로 요구하지 않는다.
바퀴 기하·제동·정지·팔/리프트 유지 검증은 자율 주행 수락에 계속 필요하다.

기존 `tools/run/check_slam_replay.py`에 저장 지도 AMCL 비교를 추가했다.
`config/localization.replay.yaml`은 전방향 바퀴용 `OmniMotionModel`을 사용한다.
alpha1~5의 0.2는 초기 잡음 가정이며 실측 보정값이나 센서 간 신뢰도 비율이 아니다.
합성 시험용 0.01 값을 실물에 그대로 채택하지 않는다. 설정 파일은
`ros2_ws/src/home_robot_tasks/config/`에 있으며 아직 실시간 주행 서비스에 활성화하지 않았다.

실제 기록 06과 그 기록으로 만든 지도 03으로 젯슨의 격리된 ROS 영역에서 AMCL을
실행했다. 시작 추정은 X +15cm, Y -10cm, 방향 +10°로 일부러 어긋나게 주었다.
실제 스캔 181개와 기록된 인코더를 재생해 위치 출력 69개를 얻었고, 프로세스는
정상 종료했다. 마지막 SLAM 대비 차이는 2.41cm·3.35°, 마지막 5초의 중앙값은
2.78cm·3.32°였다. 설정된 전방향 모델과 잡음 값도 실행 중 조회해 확인했다.

이는 **같은 자료로 만든 지도에 대한 재생 일관성 검사**다. 실제 위치 정확도,
새 기록에서의 재위치 추정, 처음 보는 방에서의 전역 위치 탐색을 입증하지 않는다.
검사의 15cm·0.2rad 중앙값 기준은 재생 이상을 찾는 진단 기준이며 주행 허가 기준이
아니다. 인코더와 일치하는지는 이 검사 통과 조건에 포함하지 않는다.
원본 결과는 `output/s4-recorded-mapping-20261112/s4-recorded-amcl-20261112-01/`,
추적 가능한 요약과 원본 보고서 해시는 `config/home_assistant/s4_recorded_mapping.observed.json`에 있다.
센서 장치를 열거나 제어기·모터 명령을 보내지 않았다.

재현할 때에는 기존 Jazzy 환경을 활성화하고, 다른 로봇 프로세스와 격리된
`ROS_DOMAIN_ID` 및 `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`를 지정한다.
다음 경로는 보존된 원본 디렉터리로 대체하고 출력은 새 디렉터리를 사용한다.

```sh
python3 tools/run/check_slam_replay.py \
  --recorded-capture CAPTURE_06 --teleop TELEOP_06.jsonl \
  --localization-map SLAM_03/occupancy.json \
  --initial-pose 0.15 -0.1 0.1745329252 --output NEW_OUTPUT
```

이 비교 모드는 지도와 같은 기록의 `report.json` 및 `slam-poses.json`을 참조한다.
새로운 독립 기록의 실물 수락에는 이 동일 기록 비교 점수를 대신 쓰지 않는다.

다음 사용자 조작은 시작 위치·방향을 표시하고, 케이블과 공간이 허용하는 범위에서
0.5~1m 이동·옆이동·느린 양방향 회전 후 시작 표시 근처로 돌아오는 수동 조종이다.
거리를 맞추기 위한 반복 미세 시험 대신 한 번의 새 전체 센서 기록을 얻는다.
저장 지도와 새 관측의 벽 정합, 위치 튐, 시작점 복귀 및 실제 표시와의 차이를 확인한다.
실측 기준 없이 라이다 자체 출력을 정답으로 간주하지 않는다. 라이다/좌표 갱신이
끊기거나 위치를 잃으면 기존 정지·유지 처리를 지키며 인코더만으로 자율 주행을
계속하지 않는다. 이동한 가구는 위치 추정 실패와 구별한 뒤 높이 장애물/지도 갱신으로
처리해야 하며, 이 재생 통과가 가구 변화 처리나 semantic mapping 수락을 뜻하지 않는다.
