## 2026-11-12 라이다 연결 후 점검

사용자가 기존 위치 고정, 본체 전원선·신호선 연결을 확인했다. CP2102 장치와 고정 USB 경로는 인식되고, 공식 드라이버 시작 명령을 보낸 검사 중 회전도 사용자에게 확인했다. 그러나 재연결 후 수동 수신 20초, 공식 ROS 드라이버 30초, 시작 명령을 포함한 직접 수신 20초 모두 거리 데이터를 얻지 못했다. 직접 수신 결과도 **0바이트**이므로 ROS 디코더 이전 수신 경로 확인이 필요하다. 결선, 센서 전원, 센서 출력 중 어느 것이 원인인지는 아직 확정하지 않았다.

검사 종료 때 센서 정지 명령 `e`를 보냈다. 회전 정지는 검사 절차의 일부이며 젯슨·로봇 전원 종료 명령이 아니다. 검사 중 USB 장치가 재연결된 흔적이 있었고 젯슨은 부팅 후 가동 시간을 계속 유지했다. 바퀴·팔·리프트 제어 및 제어기 재시작은 하지 않았다.

현재 상태는 `config/home_assistant/lidar_device.connected.observed.json`에 별도로 기록한다. 11월 5일의 정상 패킷·주기 이슈 기록과 그 해시는 유지한다. 0바이트 수신으로 체크섬 또는 주기 검증에 통과했다고 해석하지 않는다. 기존 위치 고정 확인만으로 미확정 장착 변환을 채우지 않는다.

추가로 젯슨 UTC가 PC UTC보다 약 9시간 뒤쳐져 있음을 확인했다. 젯슨은 NTP 동기화 완료로 표시하므로 어느 컴퓨터의 기준 시각이 잘못됐는지는 단정하지 않는다. 원본 센서 보고서의 대상 시각을 고치지 않고 보존하며, 사용자에게 표시하는 작업 날짜는 클라이언트의 한국 시간 기준으로 기록한다. 서로 다른 컴퓨터의 관측 시각을 합치기 전에는 시각 동기화가 필요하다.

다음은 센서에서 USB 어댑터로 돌아오는 신호 경로와 본체 전원 상태 확인이다. 회전만으로 레이저 측정·데이터 출력까지 정상이라고 판정하지 않는다. 현재는 SLAM·주행 활성화를 진행하지 않는다. 배포된 S4 실행 환경과 기존 S3 활성 경로는 그대로 유지했다.


### 같은 날 소프트웨어 진단 재검토

기존에 쓰던 케이블로 바꾼 뒤 한 번 수행한 20초 직접 수신도 0바이트였다. 이어 실물을 다시 구동하지 않고 11월 5일 정상 원본에서 체크섬·섹터 순서가 유효한 한 바퀴를 추출해 가상 직렬 포트로 재생했다. 검사에 사용했던 원시 수신 스크립트가 50,400바이트·20개 완전 스캔·체크섬 오류 0개를 기록했고, 설치된 공식 ROS 드라이버도 360점 스캔 20회를 발행했다. 공식 드라이버의 종료 코드 255는 정상 재생 후 종료 요청에서도 재현돼, 그 코드만으로 수신 실패를 판정할 수 없다.

요청한 설정은 230400 baud, 8N1, 소프트웨어/하드웨어 흐름 제어 해제이며 시작 `b`와 정지 `e`는 공식 구현과 일치한다. 초기 수동 수신 요약에는 빈 목록에 `min`을 호출하는 오류가 있었지만 원본 파일은 이미 0바이트로 저장돼 있었고, 후속 수신에서는 빈 데이터 처리를 수정했다. 이 요약 오류를 실물 무수신의 원인으로 보지는 않는다.

가상 포트 검증은 실제 CP210x 드라이버·USB/UART 수신, OS에 적용된 포트 설정과 RTS/DTR의 전기적 영향을 검증하지 않는다. pySerial 기본 RTS/DTR은 활성 상태였으나 실제 연결 보드에 미치는 영향은 아직 확인하지 않았다. 마지막 장치 조회에서는 `/dev/ttyUSB0`가 없었으며 이번 검증 중 실물 포트는 열지 않았다. **기본 수신·해석 코드 검증은 통과했지만 소프트웨어 원인을 전부 배제한 것도, 하드웨어 고장을 확정한 것도 아니다.** 배선 교체만 권하기 전에 이 미확인 항목을 분리해야 한다.


### 다른 LDS-01의 로컬 PC 비교

사용자가 같은 기종의 다른 라이다를 로컬 PC에 연결했다. 기존과 같은 수신 코드를 사용해 시작·20초 수집·정지를 한 번 수행했다. 실제 OS 설정에서도 230400 baud, 8N1, 수신 활성화, 흐름 제어 해제, 비정규 입력 모드를 확인했다.

217,950바이트, 완전한 360점 스캔 84회, 체크섬 오류 0회를 수신했다. 관측 스캔 시작 간격 중앙값은 약 0.2007초, 최대 0.2026초였고 회전 속도 중앙값은 298.3rpm이다. 다만 섹터 58 다음에 59 없이 0이 나온 경우가 2건 있어, 완전한 스캔의 연속성이나 실물 주행 준비까지 통과했다고 판단하지 않는다. 검사 종료 시 센서 정지 명령을 보냈다.

같은 수신 코드가 실제 장치에서도 동작함을 확인했다. 그러나 센서와 호스트가 동시에 변경됐으므로 기존 라이다 고장 또는 젯슨 드라이버 문제 중 하나로 단정하지 않는다. 다음 비교에서는 이 라이다와 케이블을 유지하고 젯슨으로 호스트만 바꿔 원인을 분리한다. 로컬 원본은 `output/s4-lidar-connected/local-second-unit/`에 보존한다.


### 같은 교체 라이다의 젯슨 비교와 검사 코드 수정

같은 교체 라이다를 젯슨에 연결했다. 첫 검사에서는 `Serial.flush()`가 커널의 `usb_serial_generic_wait_until_sent`에서 무기한 대기해 20초 수신 구간에 들어가지 못했다. SIGINT 후 정리 경로도 같은 `flush()`에 걸려 해당 검사 프로세스를 종료했다. 이는 검사 코드의 실제 결함이며, 정상 가상 포트 재생과 로컬 USB 검사만으로 발견하지 못했다. `write_timeout`은 `flush()`의 `tcdrain` 대기를 제한하지 않는다.

무제한 drain을 제거하고 1초 제한의 단일 바이트 쓰기 후 읽는 방식으로 변경하자 젯슨에서 234,865바이트·완전 스캔 93회·체크섬 오류 0회를 수신했다. OS에 적용된 230400 baud·8N1·수신 활성·흐름 제어 해제도 확인했다. 최초 부분 스캔에서 40→0으로 초기화한 경우 1건을 제외하면 해당 원시 수신의 연속 섹터 오류는 없었다. 시작 간격 중앙값 0.2008초, 최대 0.2020초였다. 이 결과로 이전 원래 라이다의 0바이트 현상까지 같은 원인으로 확정하지 않는다.

공식 ROS 드라이버도 20초 검사에서 360점 스캔 90회를 발행했다. 중앙 간격은 0.2007초지만 0.35초를 넘는 간격이 2회 있었고 최대 약 0.3993초였다. 기존 주행 건강 검사 한계를 늘리지 않았다. 새 라이다·젯슨의 연결과 ROS 발행은 확인됐으나 연속 주행용 수신, 실제 거리 정확도, 현재 교체 라이다 장착 변환·관측 시각·odometry는 별도 검증 대상이다.

임시 검사 코드를 `tools/diagnostics/lds01_capture.py` 한 도구로 정리했다. 기본은 수신만 하고 `--start`를 지정할 때만 센서 시작/정지 명령을 쓴다. CP210x 식별, 포트 점유 확인, 1–60초 수신, 체크섬·완전 스캔·초기 부분 스캔과 정상 구간 오류 구분을 유지한다. 센서 정지 쓰기 성공과 실제 회전 정지 확인은 구별한다. 무한 drain을 호출하지 않는 수신, 읽기 실패 시 정지 시도, 정지 쓰기 실패 보고, 수동 수신의 무명령 동작, 빈 입력과 손상/누락 섹터 검사를 포함한 7개 회귀 검사가 통과했다. 저장된 로컬 실제 원본 재검사도 84회·정상 구간 누락 2건으로 일치했다.

해당 도구는 젯슨 `/home/hyper/robot/shared/tools/lds01_capture.py`에 별도로 배치한다. 기존 S3 서비스·제어기·활성 소스 릴리스는 바꾸지 않는다. 이번 두 실물 검사 종료 시 센서 정지 명령을 보냈으며 바퀴·팔·리프트 명령은 보내지 않았다.

### 수신 간격 수정본과 다음 좌표 연결 단계

공식 2.1.1의 2,520바이트 고정 읽기는 마지막 59번 패킷이 없으면 다음 회전의 0번 패킷까지 소비했다. 이후 동기화가 다음 회전 전체를 건너뛰어 약 0.4초 간격을 만들었다. 저장된 실제 원본에서 두 번 재현했고, 동일한 가상 직렬 입력으로 원본과 수정본을 비교했다.

| 검증 | 결과 |
|---|---|
| 공식 원본, 마지막 패킷 주기적 누락 | 34회, 최대 0.3968초, 0.35초 초과 5회 |
| 수정본, 동일 누락 | 39회, 최대 0.2037초, 초과 0회, 빠진 6개 각도는 NaN |
| 수정본, 입력 중단 | 오래된 스캔 재발행 없음, `scan_ready=false`, 정상 종료 |
| 젯슨 실제 LDS-01, 정지 60초 | 291회, 최대 0.201263초, 평균 0.200735초, 초과 0회 |
| 실물 디코더 통계 | 완전 스캔 291, 부분·거부·체크섬 오류·입력 적체 초기화 각각 0 |

42바이트 패킷별 체크섬을 검사하고 다음 회전의 시작을 보존한다. 두 패킷까지의 누락은 미관측 NaN으로 남기며, 큰 누락·오래된 회전·잘못된 회전 속도는 거부한다. 입력을 지연시키거나 이전 스캔을 반복해 간격을 맞추지 않는다. 기존 0.35초 건강 검사 한계는 유지했다. 이번 실물 구간에는 누락이 발생하지 않았으므로 누락 복구 자체의 실물 장시간 수락과 혼동하지 않는다.

수정본은 `ros2_ws/src/hls_lfcd_lds_driver`에 원본 BSD 고지와 함께 보관한다. 패치 범위와 원본 커밋은 `PATCHES.md`에 기록했다. 패킷·진단·건강 검사 16개와 배포 묶음 검사 1개가 통과했다. 실제 ROS 가상 직렬 회귀 두 종류는 CI에도 연결했다. S4 패키저는 C++ 소스·헤더와 패키지 LICENSE를 포함하도록 수정했다.

젯슨 ARM64 빌드/설치는 `/home/hyper/robot/shared/runtime/s4-lidar-fix/install`에 있다. 기존 사용자 ROS 환경의 시스템 런타임 참조가 빠진 Boost 및 LTTng 라이브러리를 사용자 prefix에서 연결하고, 빌드는 시스템 Python과 해당 prefix의 `LIBRARY_PATH`를 사용했다. 시스템 패키지와 S3 서비스는 수정하지 않았다. 선택 방법은 다음과 같으며, 환경 선택 자체는 장치를 시작하지 않는다.

```bash
source /home/hyper/robot/shared/runtime/s4-jazzy/env.sh
source /home/hyper/robot/shared/runtime/s4-jazzy/install/setup.bash
source /home/hyper/robot/shared/runtime/s4-lidar-fix/install/setup.bash
```

실물 결과는 `/home/hyper/robot/shared/diagnostics/s4-lidar-gap-fixed/live-60s`와 로컬 `output/s4-lidar-fix/live-60s`에 있다. 실행 파일 SHA256은 `95807be4fae6e60319d32ddbc802458572fcc9bf328862abb2258abf163a60aa`이다. 검사 종료 코드 0과 정지 쓰기 오류 없음이 확인됐으며, 바퀴·팔·리프트 명령은 보내지 않았다.

사용자가 교체 라이다도 기존 위치에 고정했음을 확인했다. 다음은 실제 거리와 베이스 좌표 연결이다. 공식 Mini 1 URDF에는 LiDAR 장착 변환이 없으므로, 시뮬레이션의 임의 좌표를 이 실물에 적용하지 않는다. 라이다 중심 위치·측정창 높이·방향을 확인한 뒤 변환을 연결한다. 베이스 원점과 축은 기존 S2 정의(세 바퀴 축 평균, +X 전방/+Y 좌측/+Z 상방)를 재사용한다. 바퀴 배치와 과거 텔레옵 방향도 재사용하며 전체 치수 재측정을 요구하지 않는다.

이번 패치는 정지 상태의 프레임·주기 검사다. 원본의 발행 시각 및 양수 `time_increment`는 유지돼 있고 각도 배열은 수신 순서와 반대이므로, 이동 시 관측 시각/보정 검증이 남아 있다. 실제 거리·장착 변환·odometry·위치 추정이 확인되기 전까지 `hardware_enabled=false`와 이동 비허용은 유지한다. 합성 odometry를 넣어 실제 SLAM 수락으로 표시하지 않는다.

### 앞쪽 바퀴 케이스 장착 후보 시각화

사용자가 라이다는 앞쪽 바퀴 케이스 위에 있고 리프트는 최하단이라고 확인했다. 공식 ROBOTIS TurtleBot3 LDS-01 STL(커밋 `0c0be84e3f5c3194fb2adea8426a58a96060eab5`)과 라이선스를 확인하고 기존 S2 형상 뷰어를 재사용했다. 원본 Mini 1 삼각형에서 앞쪽 케이스 상단의 수평 면 37개를 찾아 면적 중심을 계산했다. 케이스 상단은 CAD Z 약 115.60mm이며, 섀시 판 상단 64mm와 다르다.

검토용 후보는 베이스 기준 X=150.999mm, Y=-1.710mm, Z=91.202mm이다. 기존 28mm 바닥 여유 기록을 적용한 회전 중심 높이는 약 161.4mm다. 센서 설치면은 STL Z=-17.8mm를 임시 기준으로 썼으며, 실제 지지대/테이프/위치/각도는 확인 전이다. 이 값을 설치 프로필이나 주행 TF에 적용하지 않았다.

최하단 확인 후 새로 10초 촬영한 실제 라이다는 41회, 최대 간격 0.20102초, 간격 초과 0회, 종료 코드 0이었다. 원본 베이스·최하단 이동부 STL과 광선을 교차해 비교했다. 모델이 가리는 87방향은 모두 12cm 미만이고, yaw=180° 후보에서는 87방향 모두 실제 미수신 구간이었다(0° 후보에서는 1개). 작은 구동 모터가 리프트 쪽인 후보를 먼저 보여주되, 미수신 원인은 다중적이므로 이것만으로 정확한 방향을 보정했다고 판단하지 않는다. 유효 측정 범위 안에서 비교 가능한 자체 형상 표면은 0개였으며 거리 보정값은 적용하지 않았다. 팔의 현재 자세도 미확인이므로 형상 비교에서 제외했다.

`tools/diagnostics/s4_lidar_visualize.py`는 기존 뷰어를 사용해 장착부·측면·전체 모델·실제 거리점과 후보 조정 화면을 만든다. 화면은 로봇에 연결하지 않는다. 자세 및 형상 회귀 20개가 통과했고 브라우저에서 형상과 스캔 표시를 확인했다. 요약은 `config/home_assistant/lidar_mount.review.json`, 원본 스캔과 자세 가설 비교는 `output/s4-lidar-fix/lift-low-mount-review` 및 `mount-review.json`에 보존한다. 다음은 사용자의 위치·구동 모터 방향 확인이며, 그 후 외부 평면의 독립 거리 기준과 비교해 거리/설치 오차를 분리한다.
