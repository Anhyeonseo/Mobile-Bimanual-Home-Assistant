## 2026-11-12 라이다 연결 후 점검

사용자가 기존 위치 고정, 본체 전원선·신호선 연결을 확인했다. CP2102 장치와 고정 USB 경로는 인식되고, 공식 드라이버 시작 명령을 보낸 검사 중 회전도 사용자에게 확인했다. 그러나 재연결 후 수동 수신 20초, 공식 ROS 드라이버 30초, 시작 명령을 포함한 직접 수신 20초 모두 거리 데이터를 얻지 못했다. 직접 수신 결과도 **0바이트**이므로 ROS 디코더 이전 수신 경로 확인이 필요하다. 결선, 센서 전원, 센서 출력 중 어느 것이 원인인지는 아직 확정하지 않았다.

검사 종료 때 센서 정지 명령 `e`를 보냈다. 회전 정지는 검사 절차의 일부이며 젯슨·로봇 전원 종료 명령이 아니다. 검사 중 USB 장치가 재연결된 흔적이 있었고 젯슨은 부팅 후 가동 시간을 계속 유지했다. 바퀴·팔·리프트 제어 및 제어기 재시작은 하지 않았다.

현재 상태는 `config/home_assistant/lidar_device.connected.observed.json`에 별도로 기록한다. 11월 5일의 정상 패킷·주기 이슈 기록과 그 해시는 유지한다. 0바이트 수신으로 체크섬 또는 주기 검증에 통과했다고 해석하지 않는다. 기존 위치 고정 확인만으로 미확정 장착 변환을 채우지 않는다.

추가로 젯슨 UTC가 PC UTC보다 약 9시간 뒤쳐져 있음을 확인했다. 젯슨은 NTP 동기화 완료로 표시하므로 어느 컴퓨터의 기준 시각이 잘못됐는지는 단정하지 않는다. 원본 센서 보고서의 대상 시각을 고치지 않고 보존하며, 사용자에게 표시하는 작업 날짜는 클라이언트의 한국 시간 기준으로 기록한다. 서로 다른 컴퓨터의 관측 시각을 합치기 전에는 시각 동기화가 필요하다.

다음은 센서에서 USB 어댑터로 돌아오는 신호 경로와 본체 전원 상태 확인이다. 회전만으로 레이저 측정·데이터 출력까지 정상이라고 판정하지 않는다. 현재는 SLAM·주행 활성화를 진행하지 않는다. 배포된 S4 실행 환경과 기존 S3 활성 경로는 그대로 유지했다.


### 같은 날 소프트웨어 진단 재검토

기존에 쓰던 케이블로 바꾼 뒤 한 번 수행한 20초 직접 수신도 0바이트였다. 이어 실물을 다시 구동하지 않고 11월 5일 정상 원본에서 체크섬·섹터 순서가 유효한 한 바퀴를 추출해 가상 직렬 포트로 재생했다. 검사에 사용했던 원시 수신 스크립트가 50,400바이트·20개 완전 스캔·체크섬 오류 0개를 기록했고, 설치된 공식 ROS 드라이버도 360점 스캔 20회를 발행했다. 공식 드라이버의 종료 코드 255는 정상 재생 후 종료 요청에서도 재현돼, 그 코드만으로 수신 실패를 판정할 수 없다.

요청한 설정은 230400 baud, 8N1, 소프트웨어/하드웨어 흐름 제어 해제이며 시작 `b`와 정지 `e`는 공식 구현과 일치한다. 초기 수동 수신 요약에는 빈 목록에 `min`을 호출하는 오류가 있었지만 원본 파일은 이미 0바이트로 저장돼 있었고, 후속 수신에서는 빈 데이터 처리를 수정했다. 이 요약 오류를 실물 무수신의 원인으로 보지는 않는다.

가상 포트 검증은 실제 CP210x 드라이버·USB/UART 수신, OS에 적용된 포트 설정과 RTS/DTR의 전기적 영향을 검증하지 않는다. pySerial 기본 RTS/DTR은 활성 상태였으나 실제 연결 보드에 미치는 영향은 아직 확인하지 않았다. 마지막 장치 조회에서는 `/dev/ttyUSB0`가 없었으며 이번 검증 중 실물 포트는 열지 않았다. **기본 수신·해석 코드 검증은 통과했지만 소프트웨어 원인을 전부 배제한 것도, 하드웨어 고장을 확정한 것도 아니다.** 배선 교체만 권하기 전에 이 미확인 항목을 분리해야 한다.
